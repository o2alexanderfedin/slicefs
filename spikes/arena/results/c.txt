Spike C: reuse of free space inside arenas, instead of compaction
=================================================================

Machine: macOS 26.2, Intel, 32 threads, APFS. load1 was 17-41 during
the runs (see the load1 line of every table). Raw data: results/c/*.jsonl.
Release build; one process per run; variants interleaved round-robin.

Variants
- RS    the real chunk_store::ChunkStore (packs + compaction).
- V1    spike A arenas (sparse fixed size) + today's compaction rules.
- C1    reuse, allocator V1 next fit, G = 64, V1 arenas (the plan's pick
        rule; see below).
- C2    reuse, V2 size classes (one run at 85 %, to check the simulator).
- C3    reuse, V3 hybrid + evacuation below 10 % live (crash loop only).
- C4    reuse, V4 arena best fit (added by this spike after the first grid;
        not in the plan).
- C4d4  C4 with max_dirty = 4 (left arenas stay dirty up to 4; not in the
        plan).
- `s`   suffix: recovery scan skips holes with SEEK_DATA.

Definitions
- Fill level f: at every GC a fraction f of the store's data is live. The
  store gets 512 MiB of files first; each GC cycle writes
  B = live * (1/f - 1) of new files and deletes files of about the same
  size, in 4 rounds, then GCs with the objects of the remaining files as
  the live set. Same for every variant (sim and disk).
- Space amplification: st_blocks*512 of the data files (pack/arena/idx) /
  record bytes of the live set (stored + 45 per live object; taken from the
  harness, not from the store's index, because a compacting store's index
  still holds dead objects of arenas it kept). amp_pre = just before a GC
  (the peak), amp_post = just after. Mean over the GCs of the second half.
- WA: bytes the store wrote (records + padding + GC copies + idx and
  checkpoint files + dirty-list rewrites) / record bytes of new objects.
  RS has no counters: its WA is from polling pack/idx file sizes (append-
  only), marked "dir-poll". V1 has the same rules and its own counter;
  both agree (1.63 vs 1.64 at 85 %).
- commit_full_syncs: full_sync (F_FULLFSYNC) calls inside sync() per
  commit (8 MiB). gc_full_syncs: total in GC.
- C-B1 runs use 64 MiB arenas, 512 MiB live, 1.5x churn (each run under
  ~1 min). Not steady state for compaction; the simulator covers 10x churn.
  cb1s: scale model with 16 MiB arenas and 2.5x churn (1 rep): its space
  and WA numbers are useful, its sync numbers are not P* numbers (a commit
  is half an arena there).

Not run / limits
- Power loss: not testable here. kill -9 only (page cache survives).
- C-B3 cold cache: `purge` needs root; all reopens are warm-cache.
- C-B5: `tmutil localsnapshot` worked without root; every snapshot was
  deleted afterwards (`tmutil listlocalsnapshotdates /` and `/System/Volumes/Data` list none).
  The free-space numbers are volume-wide, so other writers add noise
  (two C4 runs: 205 and 159 MiB).
- C-B2 "fsync each + one F_FULLFSYNC" is measured only; the store never
  relies on it.
- S3 (mmap under reuse) is not part of this spike.
- relax_during_gc: built, never measured.
- V3 (hybrid + evacuation) on disk: crash loop and tests only, not in
  C-B1 (the simulator showed no gain and 3x the dirty arenas).
- C-B3 kill -9 is simulated: mark_dirty + drop without close (the files
  are as a kill leaves them); the real kill -9 runs are the crash loops.

Noise
- N from spike A (RS vs RS): 11-32 %. So 2N = 22-64 %, which is above every
  stated time threshold (10 %, 5 %). Time-based rules below are applied as
  max(stated, 2N) with N = 11 % (the lower A value for A-B1 wall) and are
  marked "inside noise" when the result depends on N. Byte and call counts
  (WA, space, full_sync per commit) are deterministic and decide.

Decision (spike C)
------------------

C-sim (REDUCE 1 part), 1 GiB live, 10x churn, 64 MiB arenas:
- G* = 64. Padding + unusable at 85 %, file delete: G=64 2.14 % (corpus),
  0.42 % (synthetic); G=256 8.2 %, G=512 16 %, G=4096 67 % / 23 %. The
  same for every allocator at one G. "Unusable" (holes smaller than the
  smallest record) is 0 everywhere, so the other rules break the tie.
- Dirty arenas per 8 MiB commit <= 2: V1 1.89 / 1.68 (mean, corpus /
  synth) and V4 1.60 / 1.64 pass. V2 13.5 / 14.0 and V3 5.8 / 5.4 fail.
- Adversarial (object delete) not worse than compaction, peak space at
  85 %: V1 1.625 vs CMP 1.579 on the corpus (3 % worse, less than one
  arena: the values move in steps of 1/16), 1.512 vs 1.564 synthetic. On
  WA V1 wins by far (1.02 vs 1.78). The rule does not name its metric, so
  V1 is a marginal pass at best. V4 1.250 vs 1.579 and 1.209 vs 1.564.
- V* = V4 (added here; better on every metric). V1 stays the plan-grid
  pick and is in every disk table (C1).
- V3 evacuation is not needed: it copies 1-11 MiB per run, gives no space
  gain over V1, and has 3x the dirty arenas per commit.
- The simulator agrees with the disk: compaction peak space 1.55 (sim) vs
  1.56 (disk, RS and V1); V4 1.23-1.25 (sim) vs 1.24 (scale model); V2
  13-15 dirty arenas per commit (sim) vs 15.7 F_FULLFSYNC per commit (disk).

Accept rules for C on disk (64 MiB arenas; fills 50/70/85/95 %):
- WA <= 1.1: C1 1.018 / 1.032 / 1.055 / 1.146, C4d4 1.013 / 1.023 /
  1.037 / 1.0999. Compaction (V1, RS): 1.34 / 1.40 / 1.63 / 1.61. Most of
  C's WA is checkpoint rewrites (wa_idx up to 0.14 at 95 %).
                                C1 FAIL at 95 %; C4d4 at the limit at 95 %
- Space amplification <= compaction at every fill (peak, amp_pre):
  50 % 2.05 vs V1 2.04 / RS 2.06 (0.4 % above V1, below RS), 70 % 1.46
  vs 1.80, 85 % 1.33 vs 1.56, 95 % 1.10 vs 1.45. Just after a GC at 50 %
  compaction is lower (1.25 vs 2.05): it frees whole arenas at once.
                                   PASS at 70-95 %; a tie at 50 %
- Sync per commit within max(10 %, 2N) of A. Timing (3 reps; RS vs V1 in
  the same tables differ by up to 13 % in sync mean, spike A's N is
  11-32 %, so the time rule alone is inconclusive by the plan): mean
  sync() vs V1: C1 +54 / +92 / +128 / +286 %, C4d4 +24 / +50 / +39 /
  +44 %. The decision rests on the deterministic count of F_FULLFSYNC per
  commit, inside sync() + on the put path (RULE W dirty-list writes; for
  V1 arena creation and seal), without GC:
      V1   1.09+0.38 / 1.10+0.37 / 1.11+0.38 / 1.12+0.18  = ~1.3-1.5
      C1   1.71+0.29 / 2.30+0.59 / 2.50+0.77 / 4.49+1.91  = 2.0-6.4
      C4d4 1.38+0.17 / 1.71+0.47 / 1.38+0.63 / 1.55+1.56  = 1.6-3.1
  At C-B2's 21 ms per F_FULLFSYNC (linear in the number of files) that is
  +11 to +107 ms per commit for C1 and +2 to +38 ms for C4d4. Each
  put-path sync is a stall of ~20-40 ms under the store mutex (as spike
  A's boundary put).                                   FAIL (by count)
- Put throughput within max(5 %, 2N) of A (wall and CPU): CPU per GiB is
  1-17 % lower for C at every fill. Wall MB/s: C1 +2 / -18 / -9 / -43 %,
  C4d4 +9 / -9 / +5 / -19 %. Inside the noise except C1 at 95 %.
                   C1 likely FAIL at 95 % (-43 %), otherwise inconclusive
- Reopen after kill -9 <= 0.5 s: a 64 MiB arena scan costs about 0.105 s
  (warm cache, CPU-bound: CRC + zstd + BLAKE3): 1 dirty 0.13 s, 2 0.24 s,
  4 0.51 s, 5 0.58 s, 8 0.84 s; clean close 0.03 s. SEEK_DATA changes
  nothing for full arenas. "kill -9" here = mark_dirty + drop without
  close (same files as a kill); warm cache. C1 (checkpoint at the next
  sync) has 1-2 dirty arenas: PASS. C4d4 allows 4 listed + the target:
  up to ~0.58 s: borderline FAIL. Crash loop (1 MiB arenas): max reopen
  6-20 ms.
- C-B4 sequential read after churn at 85 % vs a fresh store with the same
  files: C1 452 vs 459 MB/s, C4 439 vs 434, C4d4 418 vs 454, V1 404 vs
  393, RS 422 vs 416 (warm cache; all inside the noise). No measurable
  fragmentation cost at this size.
- GC: CPU 18-76 % lower than compaction (no copies), but wall time
  +36 % to +196 %: after each GC every arena that lost records gets a
  checkpoint (about 3 F_FULLFSYNC each).

Verdict: reject reuse as the plan specifies it (C1 fails WA at 95 % and
the sync count at every fill; throughput at 95 % is likely worse). The
best variant measured (C4d4) is at the WA limit at 95 %, borderline on
reopen, and fails the sync count (5-140 % more F_FULLFSYNC per commit).
Its gains are real: peak disk space -18 to -25 % at 70-95 % fill, WA -25
to -36 %, GC CPU -60 to -75 %.
