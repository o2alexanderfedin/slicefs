## Q1. How the fuser Session is created and run (threads, spawn, clone_fd)

### Takeaway
SliceFS calls the blocking `fuser::mount(MountedFs(Arc<SliceFsFilesystem>), mountpoint, &config)` with a `Config::default()` that never sets `n_threads` or `clone_fd`, so the vendored fuser 0.18.0 runs exactly one dispatch thread (`fuser-0`). On non-Linux (macOS FUSE-T/FSKit) the vendored fuser refuses `n_threads != 1` (a guard with a "TODO: check whether it works on macOS") and `clone_fd`, and its framed stream-socket reader has no lock. So more fuser threads on macOS would need that guard removed in the (already patched) vendored copy plus a receive lock on the framed reader; alternatively SliceFS keeps one reader and dispatches to its own workers. Replies are `Send` and the socket send path is already locked.

### Cited Findings
- `build_mount_options` builds `Config::default()`, sets only `mount_options` and `acl`; `n_threads`/`clone_fd` are never set — [mount.rs:161-185](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/mount.rs#L161-L185)
- The session runs via blocking `mount(crate::fuse_callbacks::MountedFs(fs), mountpoint, &config)` after the background threads start — [mount.rs:447](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/mount.rs#L447)
- `MountedFs(pub Arc<SliceFsFilesystem>)` — "fuser takes the file system by value; this shares it, so the GC thread of the mount can reach it too." All `Filesystem` methods take `&self` (fuser 0.18 API), except `init`/`destroy` (`&mut self`) — [cb.rs:34-46](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/fuse_callbacks.rs#L34-L46)
- Vendored fuser is 0.18.0 with 3 local patches (INIT reply size, framed I/O on FUSE-T stream socket, rename layout) — [vendor/fuser/PATCHES.md](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/vendor/fuser/PATCHES.md)
- `Session::run`: `let n_threads = config.n_threads.unwrap_or(1);` then `if !cfg!(target_os = "linux") && n_threads != 1 { return Err("n_threads != 1 is only supported on Linux") }`; for extra threads it uses `ch.clone_fd()` if `config.clone_fd` (Linux only; else error "clone_fd is only supported on Linux") or `ch.clone()` (same fd); one `SessionEventLoop` thread per channel named `fuser-{i}`; after join it calls `filesystem.destroy()` via `Arc::get_mut` — [vendor/fuser/src/session.rs:246-330](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/vendor/fuser/src/session.rs#L246-L330)
- fuser's own doc: "This read-dispatch-loop is non-concurrent to prevent having multiple buffers ..., but the filesystem methods may run concurrent by spawning threads." — [session.rs:240-245](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/vendor/fuser/src/session.rs#L240-L245)
- FUSE-T stream socket: `receive_framed` reads the 40-byte header then the rest with two `read_exact` calls and **no lock** — [vendor/fuser/src/channel.rs:66-88](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/vendor/fuser/src/channel.rs#L66-L88); the send side has `static STREAM_SEND_LOCK: Mutex<()>` "so concurrent senders cannot interleave bytes" — [channel.rs:141-160](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/vendor/fuser/src/channel.rs#L141-L160)
- `pub(crate) trait Reply: Send + 'static` — reply objects can be moved to another thread and answered later — [vendor/fuser/src/reply.rs:104](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/vendor/fuser/src/reply.rs#L104)
- Issue #22 (open) "run the FUSE session with more than one worker thread": "On FUSE-T (macOS), the transport is a stream socket ... has a send lock ... and framed reads. Test that this is correct with more than one worker." Acceptance: tests pass with >1 worker on Linux and macOS (FSKit) — [#22](https://github.com/o2alexanderfedin/slicefs/issues/22)
- Callback comments state the assumption: "Since SliceFS runs single-threaded (fuser on macOS), there is no actual lock contention" (getlk) and "Since fuser runs single-threaded on macOS, there is no real lock contention — all lock requests succeed as no-ops" (setlk) — [cb.rs:787-788, 817-818, 836](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/fuse_callbacks.rs#L787)

### Inferences
- With two reader threads on one FUSE-T socket, two `receive_framed` calls could interleave header/body reads and corrupt framing. A macOS design must either add a receive lock (and lift the non-Linux guard) or keep one reader and hand requests (with their `Reply`) to a worker pool inside SliceFS. On Linux, `n_threads > 1` + `clone_fd` works out of the box in fuser, but the SliceFS state would break (see Q5).
- Workers would clone the inner `Arc<SliceFsFilesystem>`, which does not affect fuser's own `Arc<MountedFs>` / `Arc::get_mut`. The real constraint: `destroy()` (finalize open handles, commit, close the chunk store — `test_destroy`, [fs.rs:2663-2690](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L2663-L2690)) must not run while requests are still in flight on SliceFS workers, so workers must be drained before `destroy` proceeds.

### Gaps
- Not verified whether FUSE-T delivers requests concurrently (several in flight on the socket) or waits for each reply; this decides how much a worker pool can overlap on macOS.

## Q2. Shared state, locks and threads in slicefs-cli (filesystem.rs and friends)

### Takeaway
`SliceFsFilesystem` uses ~7 `std::sync::Mutex` maps plus atomics and one `Arc<RwLock<()>>` "commit gate". Every callback takes the gate shared; the commit timer and GC start take it exclusively. Per-handle write state (`OpenFileState`) is **moved out of** the `open_files` map for the duration of a write/rebase and put back afterwards. `keep_budget` (#105) can take **another** file's state out of the map; its comment says this is safe only because there is one dispatch thread.

### Cited Findings
**Struct fields** — [fs.rs:191-238](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L191-L238):
- `meta: Arc<DictMetadataStore>`, `io: Arc<Mutex<StoreIo>>` (same Arc as inside meta)
- `open_files: Mutex<HashMap<u64 /*fh*/, OpenFileState>>` (per write handle state)
- `write_alias: Mutex<HashMap<u64,u64>>` (2nd+ write handle of an inode -> owner fh; POSIX shared state)
- `content: Arc<ChunkStore>`; `readers: Mutex<HashMap<u64 /*ino*/, content::Reader>>` (reader cache)
- `handles: Mutex<HashMap<fh, ino>>`, `orphans: Mutex<HashSet<ino>>`, `next_fh: AtomicU64`
- `commit_gate: Arc<RwLock<()>>` — "Shared by FUSE callbacks, exclusive for a timed commit"
- `replaying: AtomicBool`, `dirty_limit`/`dirty_budget: AtomicUsize`, test counters (`rebase_count`, `last_rebase_bytes`, `write_rebase_bytes`, ...: AtomicU64), `rebase_hook: Mutex<Option<..>>`, `write_activity: Arc<AtomicU64>` (GC pacing)

**Per-handle state** — `OpenFileState { ino, write_mode: WriteMode, byte_count, cas_committed, last_committed_root, min_size, modified }`, `WriteMode::Streaming { state: Stream, next_expected_offset, pending: BTreeMap<u64,Vec<u8>> }` or `WriteMode::Overlay(Overlay)` — [fs.rs:130-178](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L130-L178). ### Inferences
- The `open_files` mutex itself is short-held, but the take-out pattern makes the state invisible for the full duration of chunking/rebase. Under concurrency this is effectively a "per-handle lock" whose waiters do not wait — they see "absent" and take a wrong branch.
- `readers` is a global lock held across I/O: with N threads all reads of all files serialize on it.

### Gaps
- Not checked: whether `Overlay` / `Stream` clone sizes make holding `open_files` during `Stream::clone` (read path, gc_start) costly at scale.

## Q3. chunk-store: store lock, out-of-lock lookups, pack writer, retry layer, GC mutex

### Takeaway
`ChunkStore` is already built for concurrent callers (the GC and merge threads run beside the FUSE thread): one `Arc<Mutex<Inner>>` store lock, hashing/compression and index lookups outside it with generation revalidation, a sharded memtable, and one `gc: Mutex<()>`. But every `put` does its `pwrite` (and possibly an 8 MiB early `fsync`, pack seal, memtable flush) under the single store lock, and `sync()` fsyncs under it, so parallel writers would serialize there.

### Cited Findings
- Fields: `index: Arc<Index>` ("for lookups outside the store lock"), `inner: Arc<Mutex<Inner>>`, `merge: Arc<MergeCtl>` (`step: Mutex<()>`, `state: Mutex<MergeState>`, `cv: Condvar`, `stop: AtomicBool`), `merge_thread`, `gc: Mutex<()>` ("One GC at a time: `gc_begin`, `gc_abort` and the whole `gc_finish` hold it. Lock order: this lock, then the store lock."), `zstd_level: AtomicI32` — [cs/lib.rs:599-660](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/lib.rs#L599-L660)
- `put`: hash (`opts.hasher.id(data)`) and `index.get` outside the lock; then under the lock, `unchanged(gen,id)` (`index.gen() == gen && !index.mem_has(id)`) or re-lookup; zstd compression in a thread-local `SCRATCH` outside the lock; then under the lock `inner.check()`, `self.append(...)` (pack `write_at`, seal when `pack_limit` reached), `inner.add_new`, `flush_if_full` (memtable -> run file) — [cs/lib.rs:1092-1160, 913-917, 2179-2184](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/lib.rs#L1092-L1160)
- `read`: lookup outside lock, under lock revalidate generation and take the pack handle; `read_record` (pread, zstd decompress, BLAKE3 verify) outside the lock — [cs/lib.rs:2000-2045](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/lib.rs#L2000-L2045)
- `sync()` holds the store lock across `sync_active` (pack fsync) and `sync_dir` — [cs/lib.rs:2186-2196, 2446-2457](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/lib.rs#L2186-L2196)
- Index: memtable `shards: [Mutex<BTreeMap<ObjectId, Entry>>; SHARDS]`, `runs: RwLock<Arc<Vec<Arc<Run>>>>`, `man: Mutex<Manifest>`, `gen: AtomicU64` — [chunk-store/src/index.rs:232-240](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/index.rs#L232-L240)
- Retry layer: `KEEP_LIMIT = 8 << 20`; `RetryingPack::write_at` keeps a copy of every unsynced write and calls `self.sync()` when `kept > KEEP_LIMIT` — inline, inside `append`, i.e. under the store lock — [chunk-store/src/retry.rs:9-12, 27, 86-94](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/retry.rs#L86-L94)
- GC entry points `gc_begin` / `gc_begin_full` / `gc_abort` / `gc_finish*` take `gc` then `inner` — [cs/lib.rs:1190-1240, 1298-1370](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/lib.rs#L1190)
- Design doc: GC "holds the store lock only for short steps" (start, install), passes 1/2 and the merge read with no store lock; "The longest hold of the store lock is about the same at 10M and at 100M" — [docs/design/chunk-store.md:281-288, 584-586, 823-845](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/docs/design/chunk-store.md)
- Race tests already exist for put/read vs GC/merge (`after_lookup`, `after_merge_write`, `gc_pass_hook` hooks) — [chunk-store/src/race_tests.rs](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/race_tests.rs)

### Inferences
- The chunk store is the most concurrency-ready layer: N threads can hash/compress in parallel; they serialize only on the pack append (+ inline 8 MiB fsyncs and seals). A per-thread or batched pack append, or moving the KEEP_LIMIT sync out of the lock, would be needed for write scaling.
- `Stream` (FastCDC writer) and `content::splice` call `store.put` per chunk/node ([chunk-store/src/file.rs:160, 191, 733](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/file.rs#L160)), so CDC + BLAKE3 + zstd of every written byte runs on the calling (FUSE) thread.

### Gaps
- No measurement of store-lock hold times under multi-writer load exists (all measurements are single FUSE thread).

## Q4. metadata crate: segment/WAL writer locks, metadata maps

### Takeaway
`DictMetadataStore` is a set of independent `Mutex` maps with a documented lock order; every single call is thread-safe, but compound filesystem operations (create+link, rename, install_root, touch_dir, stamp_content) are sequences of separate calls with read-modify-write on inodes and no per-inode or per-directory lock. The WAL is one `Mutex<Option<Box<dyn WalStrategy>>>` held across both appends and `flush_and_sync`, so an fsync blocks all log appends.

### Cited Findings
- Doc: "All state is held in-memory as `Mutex`-guarded maps"; lock order `inode_map`, `io`, `inode_data`, `dir_data`, `manifest_data`, `xattr_data`, `refcounts` (plus `dir_live` before `io`; `inode_map`, `inode_live`, `io`, `inode_data`) — [meta/store.rs:1-14, 120-186](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/metadata/src/store.rs#L1-L14)

- Issue #21 (open) concurrency design: "No global lock on the hot path", sharded inode table, `parking_lot::RwLock` per inode, log append via short mutex or channel to flusher, `durable_lsn` AtomicU64 + condvar, commit+GC one mutex; lock order "inode-table shard, then per-inode lock; for two inodes lock in increasing inode order" — [#21](https://github.com/o2alexanderfedin/slicefs/issues/21)

### Inferences
- Individual map operations will not corrupt memory under multithreading, but two concurrent requests touching one inode/directory can lose updates (e.g., two creates in one dir both `touch_dir`; nlink adjustments in concurrent renames; `install_root` racing a `flush_handle` on the same inode leaving refcounts wrong).
- The `io` mutex (metadata `StoreIo`) and the `wal` mutex are global serialization points.

### Gaps
- Did not audit every `DictMetadataStore` method for internal check-then-act across two locks (e.g., `link` duplicate check vs insert) — only the filesystem-level compounds.

## Q5. Every place correctness depends on single-threaded dispatch; places already safe

### Takeaway
At least 15 code sites (items 1-13, 15, 16 below; item 14 is gate-based) assume that no other FUSE request runs at the same time. The central one is the "take `OpenFileState` out of `open_files`" pattern (writes, settle, setattr, keep_budget), whose absence other paths interpret as "no handle". The second is log order = apply order (inode numbers, write overlap). Background-thread interactions (GC, merge, commit timer) are already designed for concurrency via the commit gate and the chunk store's generation checks.

### Cited Findings — single-thread dependencies (file:line, why)
1. **keep_budget takes another fh's state out** — [fs.rs:1224-1231, 1256-1263](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1224-L1263). Explicit comment: "A mount with more dispatch threads would need the state kept in the map during the step." A concurrent write on that fh would get `EBADF`; a concurrent read would read the old manifest; a concurrent `release` would skip `finalize_write` and lose data; also two writers could both pick the same "largest" fh (the second gets `None` and returns Ok).
2. **test_write takes its own state out** for the whole write (CDC, puts, rebase step, keep_budget) — [fs.rs:1103-1211](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1103-L1211). Doc claims "FUSE serializes per-fh writes" — true only with one dispatch thread (the kernel sends parallel WRITEs; NFS/FUSE-T also, see the `pending` reorder window comment at [fs.rs:133-137](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L133-L137)). A second write to the same fh (or an aliased fh — `owner_fh` maps aliases to the same key) would get `EBADF`.
3. **test_read during a write**: if the writer's state is out of the map, `open_files.values().find(|s| s.ino == ino ...)` misses it and the read returns the committed manifest — stale data, breaking read-after-write across handles — [fs.rs:1446-1490](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1446-L1490).
4. **flush_handle / fsync during a write**: state absent -> `Ok(())` "fsync is a no-op" — fsync could return success without the streamed prefix in the manifest — [fs.rs:1657-1690](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1657-L1690). (Durability is still covered by the write log only if the write's record was appended before the fsync's `flush_wal`, which is not ordered either.)
5. **test_open alias**: finds an owner state by scanning `open_files`; if the owner's state is out of the map, a second independent state is created — reintroducing the "last close wins, other handle's bytes lost" bug that `write_alias` fixed — [fs.rs:2421-2438](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L2421-L2438), [fs.rs:196-200](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L196-L200). Also check-then-insert across two locks (`open_files` then `write_alias`).
6. **test_release heir hand-over and finalize_write**: `write_alias` scan then `open_files.remove(&fh)`/insert under separate locks; `finalize_write` returns Ok if the state is absent ("Already closed") — races with a concurrent write's take-out — [fs.rs:1315-1360](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1315-L1360).
7. **settle_pending / test_setattr_size** take the state out and re-insert (`expect("state is in the map")` at 1812 would panic if another thread had it out) — [fs.rs:984-1002, 1735-1825](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1812).
8. **Write-log order = apply order**: each handler applies, then appends (`Logged::log`) in a separate critical section — [handlers.rs:102-125, 337-352](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/handlers.rs#L337-L352). With two threads, creates can be logged out of inode-allocation order; replay's `advance_next_ino` only goes up and then `got == *ino` fails -> mount refuses ("did not replay") — [oplog.rs:250-262](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/oplog.rs#L250-L262), [meta/store.rs:403-413](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/metadata/src/store.rs#L403-L413). Overlapping writes / rename+unlink in one dir logged in a different order than applied would replay to different content. The design doc relies on this: "it cannot fail if the order is the same" — [write-log.md:68-70](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/docs/design/write-log.md).
9. **install_root / flush_handle / finalize_write refcount RMW**: `get_manifest` -> `set_manifest` -> inc/dec refcount and `last_committed_root` bookkeeping with no per-inode lock — [fs.rs:816-838, 1380-1410, 1690-1725](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L816-L838). Two threads on one inode can double-decrement or leak a root (GC then deletes live data or keeps dead data).
10. **Inode RMW helpers** `touch_dir`, `adjust_nlinks`, `stamp_content`, and the extend branch of `test_setattr_size` (`get_inode` ... `update_inode`) — lost updates of size/mtime/nlink — [fs.rs:1023-1039, 1516-1527, 1757-1768](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1023-L1039).
11. **Multi-step namespace ops** (`simulate_rename`, `simulate_unlink`/`drop_last_link` with `handles` scan then `orphans` insert, `close_handle` remove-then-scan-then-orphan-remove) — check-then-act across separate locks — [fs.rs:577-611, 2118-2296](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L577-L611). E.g., unlink checks "no open handle" while a concurrent open adds one -> inode reclaimed under an open fd.
12. **POSIX locks are no-ops**: getlk returns F_UNLCK, setlk returns ok "since SliceFS runs single-threaded" — [cb.rs:780-838](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/fuse_callbacks.rs#L780-L838). The comment encodes the single-thread assumption (see Inferences).
15. **Write silently not logged**: `handle_write` appends the record only `if let Some(ino) = fs.ino_of_fh(fh)`; `ino_of_fh` looks the fh up in `open_files`. If another thread holds this handle's state out of the map at that moment (a concurrent write, settle, setattr, or `keep_budget` of another writer), a write that succeeded is not logged -> lost on crash replay — [handlers.rs:325-330](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/handlers.rs#L316-L332), [fs.rs:363-366](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L363-L366).
16. **Dirty budget undercounts**: `keep_budget` sums `dirty_cost` of `open_files.values()` plus its own state; states that other concurrent writers hold out of the map are not counted, so the #105 global budget (and the daemon RAM bound of #98) would be exceeded by up to (threads - 1) x per-file cost — [fs.rs:1236-1246](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1236-L1246). Same for `test_dirty_total` and `gc_start`'s root collection (the latter is under the exclusive gate, so fine).
13. **Per-write test counters** `write_rebase_bytes.store(0)` at the start of each write — [fs.rs:1097-1098](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1097-L1098) — benign (tests only) but would mix values across threads.
14. **commit_cut assumes no request in flight** — guaranteed by the exclusive gate, not by single dispatch; stays correct if every request still takes the gate shared — [fs.rs:1533-1540](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L1533-L1540). Same for `gc_start`'s "A rebase runs inside a callback that holds `commit_gate.read()`, so it never straddles `gc_begin`" — [fs.rs:640-650](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L640-L650). **If a rebase moves to a worker outside a callback, this invariant breaks** (issue #108 option 1 notes "the old overlay must stay a GC root until the new base is in the manifest").

### Cited Findings — already safe for concurrency
- Commit timer vs requests: `RwLock` gate (shared per callback, exclusive for commit) — [commit_timer.rs:9-12](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/commit_timer.rs#L9-L12).
- Online GC mark/sweep vs requests: GC roots taken under the exclusive gate; mark/sweep run concurrently with requests, protected by the chunk store's `touched` tracking and generation revalidation — [fs.rs:640-704](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L640-L704), [cs/lib.rs:1092-1160](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/chunk-store/src/lib.rs#L1092-L1160).
- ChunkStore `put`/`read` from many threads (store lock, sharded memtable, `RwLock` runs, merge thread, `gc` mutex; race tests) — Q3.
- Individual `DictMetadataStore` calls (each map behind its own mutex with a lock order) — Q4.
- `next_fh` allocation (`AtomicU64::fetch_add`) — [fs.rs:564-573](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/filesystem.rs#L564-L573).
- Request clock is thread-local (`oplog::Clock`), so per-request time freezing already works per thread — [oplog.rs:58-88](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/oplog.rs#L58-L88).
- fuser reply path: `Reply: Send`, `STREAM_SEND_LOCK` on FUSE-T — Q1.
- `SliceFsFilesystem` is already shared as `Arc` and is `Send + Sync` (used from GC and commit threads) — [cb.rs:34-36](https://github.com/o2alexanderfedin/slicefs/blob/6fd1e11/crates/slicefs-cli/src/fuse_callbacks.rs#L34-L36).

### Inferences
- A minimal-risk first step is "keep one dispatch thread, add workers only for whole-request offload with a per-inode serialization" (e.g., per-inode queue/lock), since items 1-11 are all per-inode or per-directory races plus log ordering. A per-inode lock held across take-out/re-insert would fix 1-7 and 9-10; log order (8) needs the log append (LSN) inside the same critical section as the apply, or per-inode LSN ordering plus a globally ordered allocation of inode numbers.
- `std::sync::RwLock` used as the gate (UNVERIFIED here, from general knowledge of the std futex implementation): a waiting writer (commit timer) may block new readers, so one long shared hold (a rebase step with an inline pack fsync) plus a waiting commit could stall every worker. Today the timer is measured waiting 1-3.7 s for rebases in the #108 runs (cited in Q6).
- The getlk/setlk "single-threaded, so no contention" justification is weak even today: several processes can take POSIX locks on the mount and all get "no conflict". Multithreading does not change this; it only removes the stated reason.

### Gaps
- No existing multi-threaded FUSE test in the repo (only `gc_online_tests.rs` spawns threads in `crates/slicefs-cli/tests`), so there is no harness that would detect the races above.

## Q6. Where time is spent on the request thread (#108 notes, design docs)

### Takeaway
Everything runs on the one FUSE thread: streaming CDC + BLAKE3 + zstd + pack pwrite of every written byte, rebase work for random writes, fsync, and waits for the timed commit / GC start. **Before** bounded rebase steps (#108 investigation, whole 32 MiB `rebase_overlay` inside the write that passed `DIRTY_LIMIT`): ~1.5-2.5 s on-CPU per rebase, slowest single write 5-8 s (17 s at 4 GiB). **After** PR #122 (bounded `rebase_step` of max(added, `REBASE_STEP` = 1 MiB), dirty budget, base read only between extents; now on develop): slowest write 1124 / 1772 ms (1 GiB / 4 GiB, single Docker runs), steps 73-112 ms at p99, and **every write above 400 ms contains an inline 8 MiB `KEEP_LIMIT` pack fsync of 0.35-1.7 s on the FUSE thread**; a timed commit can hold the gate up to ~1.7 s on a slow disk. The 500 ms bound of #108 is still open.

### Inferences
- After PR #122, the dominant tail on the request thread is the inline `KEEP_LIMIT` pack fsync under the store lock, not the rebase CPU. Multithreading alone would not remove it (it holds the store lock that every `put`/`read` needs); moving the sync off the lock or out of the request path is a separate, smaller fix.
- The CPU part (CDC, BLAKE3, zstd, verify) parallelizes well across threads because the chunk store does it outside the store lock; the pack append + inline fsync + seal does not.
- Moving the rebase to a worker (#108 option 1) is a narrower change than full multithreaded dispatch but touches the same invariants: the gate-shared-during-rebase GC invariant (Q5 item 14) and the take-out-of-map pattern.

### Gaps
- No measurement on macOS FSKit of per-request latency with the current pack store (stated as "not measured yet").
- No profile of how much of a plain sequential copy (no rebase) is CPU on the FUSE thread vs waiting on FUSE-T; this sets the upper bound for multithreading gains on macOS.
- The #108 notes are on Linux Docker (OrbStack VM) only; host stalls there may not represent macOS APFS.
