# Kernel FS concurrency, per-inode locking, and global dirty-memory budgets (for SliceFS)

Scope: mechanisms a user-space FUSE FS (SliceFS: per-open-file write overlays, shared dirty budget across files, commit-gate RwLock, write-ahead log) can copy. Sources fetched 2026-11-19. Kernel docs and source are "master" / current unless marked. LWN and mailing-list items carry their own dates.

## 1. Linux VFS: which locks serialize one inode, directories, and lock ordering

### Takeaway
The VFS uses one per-inode `i_rwsem`. Lookups and directory iteration take it shared. Namespace changes (create, unlink, rename, setattr) take it exclusive on the parent and on the affected children. A per-superblock rename lock is taken only for cross-directory rename. Deadlock freedom comes from a strict rank order: the fs rename lock, then directories in ancestor-first order, then non-directories in increasing inode address order. A separate `invalidate_lock` keeps page-cache invalidation (truncate, hole punch) apart from page-cache fill (read, fault).

### Cited Findings
- `->lookup` holds `i_rwsem` shared. `->atomic_open` holds it shared, or exclusive when O_CREAT is set. These hold it exclusive: `create`, `link`, `mknod`, `symlink`, `mkdir`, `unlink`, `rmdir`, `rename`, `setattr`, `fileattr_set`. These take no `i_rwsem`: `getattr`, `permission`, `readlink`, `get_link`, `listxattr`, `fiemap`, `get_acl`. — [Linux docs: locking.rst](https://docs.kernel.org/filesystems/locking.html)
- "->rmdir(), ->unlink() and ->rename() have ->i_rwsem exclusive on victim"; "->unlink() and ->rename() have ->i_rwsem exclusive on all non-directories involved"; "->rename() has ->i_rwsem exclusive on any subdirectory that changes parent"; "cross-directory ->rename() has (per-superblock) ->s_vfs_rename_sem". — [locking.rst](https://docs.kernel.org/filesystems/locking.html)
- On file data: "For blocking changes through write(2) and similar operations inode->i_rwsem can be used". The VFS calls `iterate_shared` (readdir) "with i_rwsem held for reading, and with the file f_pos_lock held exclusively". — [locking.rst](https://docs.kernel.org/filesystems/locking.html)
- `invalidate_lock`: the filesystem "must exclusively acquire invalidate_lock before invalidating page cache" (truncate, hole punch). Its purpose is to "block races between page cache invalidation and page cache filling functions (fault, read, ...)". The VFS takes it shared when it loads pages. — [locking.rst](https://docs.kernel.org/filesystems/locking.html)
- Folio (page) lock: `write_begin()` locks the folio and `write_end()` unlocks it. `read_folio`/`readahead` unlock the folio at I/O completion. `release_folio` runs with the folio locked and not under writeback. — [locking.rst](https://docs.kernel.org/filesystems/locking.html)
- Ordering of non-directories: "When taking the i_rwsem on multiple non-directory objects, we always acquire the locks in order by increasing address." — [Linux docs: directory-locking.rst](https://docs.kernel.org/filesystems/directory-locking.html)
- Same-directory rename: lock the parent exclusive, look up source and target, then lock the non-directory source and target in inode-pointer order. — [directory-locking.rst](https://docs.kernel.org/filesystems/directory-locking.html)
- Cross-directory rename: take the per-fs `s_vfs_rename_mutex` first. Fail if the parents have no common ancestor. Lock the parents ancestor-first; "If neither is an ancestor of the other, lock the parent of source first". Reject the rename if source or target is a descendant of the other. Lock subdirectories (source before target), then non-directories in pointer order. — [directory-locking.rst](https://docs.kernel.org/filesystems/directory-locking.html)
- Rank: "put ->s_vfs_rename_mutex at rank lower than that of any ->i_rwsem on the same filesystem". The proof works like this. Assume a minimal deadlock cycle. All contended locks are then directory locks on one fs, so the cycle must contain a cross-directory rename, and that is impossible. "Note that the check for having a common ancestor in cross-directory rename is crucial." "If no directory is its own ancestor, the scheme above is deadlock-free." — [directory-locking.rst](https://docs.kernel.org/filesystems/directory-locking.html)
- Naming mismatch: locking.rst says `s_vfs_rename_sem`, directory-locking.rst says `s_vfs_rename_mutex`. It is the same per-superblock lock. — [locking.rst](https://docs.kernel.org/filesystems/locking.html), [directory-locking.rst](https://docs.kernel.org/filesystems/directory-locking.html)

### Inferences
- What SliceFS can copy: (a) one RwLock per inode; shared for lookup/readdir, exclusive for namespace changes on the parent and the victim. (b) One fs-wide rename mutex, taken only for cross-directory rename, before any inode lock. (c) When more than one non-directory lock is needed, take them in a total order. Inode number is the natural key in user space; XFS also orders by inode number (see section 2).
- In FUSE the kernel already holds `i_rwsem` for these ops before it sends the request. So a daemon that takes its own per-inode locks in the same pattern adds no new deadlock risk, as long as its lock order matches the kernel's.
- The `invalidate_lock` pattern maps to SliceFS truncate/punch. The overlay or chunk-map invalidation should exclude readers that are filling a cache, but it does not need to exclude all writers.

### Gaps
- locking.rst does not name `lock_two_nondirectories()`. The address-order rule in directory-locking.rst describes what that helper does, but I did not fetch its source.
- No single page documents a global VFS lock order beyond directory-locking.rst. Per-fs comments (XFS below) fill in the rest.

## 2. Parallel writes in ext4, XFS, btrfs, ZFS, and how commits interact with writers

### Takeaway
Writes to different files run in parallel everywhere, because each file has its own lock. Writes to one file mostly serialize on `i_rwsem`. The exceptions are direct-I/O overwrites that do not extend the file (ext4, XFS take the lock shared) and ZFS, which uses per-file byte-range locks. Range locks for buffered writes are still not mainline as of the 2025 discussions. Every journaling or COW fs uses the same commit model. A writer "joins" the open transaction with a cheap hold (jbd2 handle, btrfs `num_writers`, ZFS `txg_hold_open`). Commit closes the transaction to new joiners, which then go to the next one, and waits for current holders to drain. A writer must never wait for a commit while it holds a handle or a lock that the commit needs. This is the same as SliceFS's commit-gate RwLock (writers shared, commit exclusive). The kernel designs add two things on top: a next-generation transaction that new writers join while the old one drains, and a rule that the hold is released before any blocking wait.

### Cited Findings
**XFS**
- XFS inode locks, in addition to the VFS `i_rwsem`: "2 multi-reader locks: invalidate_lock and the i_lock". "The 3 locks should always be ordered so that the IO lock is obtained first, the mmap lock second and the ilock last in order to prevent deadlock." Basic order: `i_rwsem -> invalidate_lock -> page_lock -> i_ilock`. mmap paths: `i_rwsem -> page lock -> mmap_lock` and `mmap_lock -> invalidate_lock -> page_lock`. — [fs/xfs/xfs_inode.c comment above xfs_ilock()](https://raw.githubusercontent.com/torvalds/linux/master/fs/xfs/xfs_inode.c)
- Multi-inode locking: `xfs_lock_inodes()` "assume[s] the caller calls us with the inodes in i_ino order". `xfs_lock_two_inodes()` swaps its arguments so the lower inode number is locked first (from the code, not a comment). — [xfs_inode.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/xfs/xfs_inode.c)
- Range-lock state (Jan 2025 thread "xfs: Remove i_rwsem lock in buffered read"). Darrick Wong said range locks are the preferred fix, but no one has built one that performs well. Dave Chinner proposed a "quasi-range lock": `i_rwsem` shared for non-extending writes, plus a bitmap of offset segments, with one bit per segment (offsets may be hashed to bits). Extending writes take `i_rwsem` exclusive, or the bit that covers EOF serializes extensions. Chinner warned that folio-based shared locking would drop buffered-vs-DIO serialization, which he called unacceptable. — [LKML thread, Jan 2025](https://lkml.iu.edu/hypermail/linux/kernel/2501.1/06354.html); [also](https://lkml.rescloud.iu.edu/2501.1/03372.html)
- 2019 range-lock benchmark (Chinner). DIO IOPS at 4 processes: about 267k with rwsem, about 246k with the XFS range lock, about 183k with Davidlohr's generic range lock. Conclusion: a range lock must scale like a shared rwsem before it is viable. — [Dave Chinner, linux-xfs, 2019-04-16](https://lore.kernel.org/linux-xfs/20190416122240.GN29573@dread.disaster.area/)

**ext4**
- 2019 series (Ritesh Harjani), merged as "ext4: Start with shared i_rwsem in case of DIO instead of exclusive". DIO starts with `i_rwsem` shared. `ext4_dio_write_checks()` restarts the write under the exclusive lock in three cases: (1) the write is unaligned, because partial-block zeroing must be serialized against other DIO in the same block; (2) the write extends the file, because `i_disksize` and the orphan list must change under the exclusive lock; (3) `file_modified()` must change security info. Shared mode is mostly for overwrites with dioread_nolock. — [lore: PATCHv5 2/3](https://lore.kernel.org/linux-ext4/20191226150640.GD3158@mit.edu/t/); [Jan Kara review](https://lore.kernel.org/linux-fsdevel/20191120135514.GD9509@quack2.suse.cz/); [mainline commit mirror](https://github.molgen.mpg.de/mariux64/linux/commit/aa9714d0e39788d0688474c9d5f6a9a36159599f)
- 2023 follow-up (Brian Foster): unaligned DIO that is a pure overwrite (no zeroing needed) may also skip the exclusive lock. I did not verify whether it was merged. — [lore 2023-02-23](https://lore.kernel.org/linux-ext4/20230223191626.263331-1-bfoster@redhat.com/)
- jbd2 handle model (the journal under ext4): handles "are nestable"; "each task can only have a single outstanding transaction at any one time"; "nothing commits until the outermost jbd2_journal_stop()"; "you must treat jbd2_journal_start() / jbd2_journal_stop() as if they were semaphores"; "jbd2_journal_start() can block if there isn't enough space in the journal for your transaction". On credits: "Try to reserve the right number of blocks the first time", and a caller of `jbd2_journal_extend()` "MUST be able to deal cleanly with a failure to extend". — [Linux docs: journalling.rst](https://docs.kernel.org/filesystems/journalling.html)
- Reserved handles: "not attached to any particular transaction and thus doesn't block transaction commit"; reserving one "cannot block on journal commit, checkpointing". — [journalling.rst](https://docs.kernel.org/filesystems/journalling.html)
- Barrier and forced commit: a barrier "locks out any further updates from being started, and blocks until all existing updates have completed". "We can only force the running transaction if we don't have an active handle, otherwise, we will deadlock." — [journalling.rst](https://docs.kernel.org/filesystems/journalling.html)
- ext4 fast commit stores a minimal, idempotent delta in a fast-commit area. A full jbd2 commit runs when that area fills, when fast commit is impossible, or when the commit timer expires. — [ext4 journal docs](https://docs.kernel.org/filesystems/ext4/journal.html)

**btrfs**
- Transaction states: `RUNNING, COMMIT_PREP, COMMIT_START, COMMIT_DOING, UNBLOCKED, SUPER_COMMITTED, COMPLETED`. State changes happen under `fs_info->trans_lock`. `num_writers` counts "total writers in this transaction, it must be zero before the transaction can end". `num_extwriters` counts "total external writers(USERSPACE/START/ATTACH) in this transaction, it must be zero before the transaction is being committed". There are wait queues `writer_wait` and `commit_wait`. — [fs/btrfs/transaction.h](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/transaction.h)
- Extent locking: btrfs must "lock the extents before locking folios to be read from disk" (Goldwyn Rodrigues, 2023 series). Qu Wenruo's `lock_extents_for_read()` locks the whole range, then skips sub-ranges whose ordered extents can safely be skipped. Ordered extents track in-flight writes per range until I/O completes. — [lore 2023 series](https://lore.kernel.org/all/08b4b39eca92493c341831a6cb06836aac7a4967.1677793433.git.rgoldwyn@suse.com/T/); [ordered-data.c](https://android.googlesource.com/kernel/common/+/d39fc9b94dc07/fs/btrfs/ordered-data.c)

**ZFS (OpenZFS)**
- "There are three active transaction group states: open, quiescing, or syncing." "There may be up to three active txgs, and there is always a txg in the open state". Quiescing is "a buffer between accepting new" transactions and syncing. It waits for everyone to "call txg_rele_to_sync() for their open transaction handles". "The txg is guaranteed to stay open until txg_rele_to_quiesce() is called". Hold state is indexed per CPU ("the processor id is simply used as a 'random'" index). — [module/zfs/txg.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/txg.c)
- `dmu_tx_assign`: "If DMU_TX_WAIT is *not* set and we can't assign into the currently open txg without blocking, this function will return immediately with ERESTART." "This should be used whenever locks are being held." "On an ERESTART error, the caller should drop all locks, call dmu_tx_wait(), and try again." Also: "This thread can't hold the dn_struct_rwlock while assigning the tx, because this can lead to deadlock." — [module/zfs/dmu_tx.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/dmu_tx.c)

### Inferences
- SliceFS's commit gate (writers hold the RwLock shared, commit takes it exclusive) is the same as the jbd2 barrier and btrfs `num_writers` drain. Its weakness is that writers stall for the whole commit. ZFS and btrfs avoid this: a new open txg/transaction exists right away, so only the drain (quiesce) blocks new writers, and the sync of the old generation runs in parallel. For SliceFS: give each commit a generation, and swap the WAL segment or overlay generation at gate time. Writers then hold the gate exclusively only for a "swap pointers" step, not for the flush.
- ZFS's ERESTART rule is the key deadlock guard: never block on the gate or the budget while you hold a per-inode or per-overlay lock. Try first; on failure, release your locks, wait, and retry. jbd2 says the same thing ("cannot force commit with an active handle").
- Writes to different ranges of one file: kernels mostly avoid range locks, because they are slow and complex. SliceFS's per-open-file overlay already decouples writers. If finer locking is needed, Chinner's segment-bitmap or hashed-bit lock is a cheap, proven pattern. Extending or EOF writes and truncate stay exclusive.

### Gaps
- ZFS `zfs_rangelock` internals (per-znode AVL range lock, writer and reader ranges, append mode) were not fetched. Per-file range locking in ZFS is from background knowledge and is not cited here.
- The btrfs `__TRANS_*` join-type semantics and `btrfs_blocked_trans_types` table were not retrieved (git.kernel.org returned 403; transaction.h has no join types).
- btrfs btree locking (extent buffer rwsem, `btrfs_tree_lock`) was not covered.
- ext4 `i_data_sem` was not covered by the fetched docs.

## 3. Linux writeback throttling: global dirty budget without a global lock

### Takeaway
Linux has a two-threshold budget. At the background threshold (default 10%), flusher threads start writing. At the hard threshold (default 20%), dirtying tasks are throttled. Since IO-less throttling (Fengguang Wu, 2011), the task that dirties pages pays by sleeping in `balance_dirty_pages()`, for at most 200 ms per pause. It does not write back pages itself. The pause length comes from a smooth control law: `pos_ratio` is a cubic curve around a setpoint, scaled by the estimated per-device bandwidth divided among N dirtiers. Accounting uses per-CPU counters, and each CPU checks the throttle only after it has dirtied a batch (`ratelimit_pages`). FUSE gets an extra cap: each FUSE bdi is "strictlimit" and capped at 1% of the dirty threshold.

### Cited Findings
- `dirty_background_ratio/_bytes`: the dirty-memory level "at which the background kernel flusher threads will start writeback". `dirty_ratio/_bytes`: the level at which "a process which is generating disk writes will itself start writing out dirty data". Ratios are a percent of "total available memory that contains free pages and reclaimable pages". `dirty_expire_centisecs` is the age at which dirty data is eligible for writeout. `dirty_writeback_centisecs` is the flusher wakeup interval; 0 disables periodic writeback. — [Linux docs: sysctl/vm.rst](https://docs.kernel.org/admin-guide/sysctl/vm.html)
- Defaults in source: `dirty_background_ratio = 10` ("Start background writeback (via writeback threads) at this percentage"); `vm_dirty_ratio = 20` ("The generator of dirty data starts writeback at this percentage"). — [mm/page-writeback.c](https://raw.githubusercontent.com/torvalds/linux/master/mm/page-writeback.c)
- `#define MAX_PAUSE max(HZ/5, 1)`: "Sleep at most 200ms at a time in balance_dirty_pages()". — [page-writeback.c](https://raw.githubusercontent.com/torvalds/linux/master/mm/page-writeback.c)
- Freerun: `dirty_freerun_ceiling()` returns `(thresh + bg_thresh) / 2`. Below it, there is no throttling. `setpoint = (freerun + limit) / 2`. `pos_ratio` is about 2.0 well below the setpoint, 1.0 at the setpoint, and 0 at the limit. "the closer to setpoint, the smaller |df/dx|". The wb control line "won't drop below pos_ratio=1/4". — [page-writeback.c](https://raw.githubusercontent.com/torvalds/linux/master/mm/page-writeback.c)
- Per-CPU batching: after a CPU has dirtied `ratelimit_pages`, `balance_dirty_pages_ratelimited` checks whether to throttle. A per-CPU `bdp_ratelimits` stops one CPU from building up too many dirtied pages without checking. Unthrottled dirties from exiting tasks are kept in `dirty_throttle_leaks` and charged to running tasks. — [page-writeback.c](https://raw.githubusercontent.com/torvalds/linux/master/mm/page-writeback.c)
- Approximate counters: per-wb stats are per-CPU. When `wb_thresh < 2 * wb_stat_error()`, the code uses the exact `wb_stat_sum()`. Otherwise it uses the cheap approximate `wb_stat()`. — [page-writeback.c](https://raw.githubusercontent.com/torvalds/linux/master/mm/page-writeback.c)
- `BDI_CAP_STRICTLIMIT`: "a tool preventing mistrusted filesystems from growing a large number of dirty pages before throttling". It uses per-bdi limits, even below global freerun. — [page-writeback.c](https://raw.githubusercontent.com/torvalds/linux/master/mm/page-writeback.c)
- FUSE: `fuse_bdi_init` sets `BDI_CAP_STRICTLIMIT` and `bdi_set_max_ratio(sb->s_bdi, 1)`, which means "For a single fuse filesystem use max 1% of dirty + writeback threshold". It is tunable through `/sys/class/bdi/<bdi>/max_ratio`. The default `max_background` is sized to "1/2^13 of the total memory"; "Congestion starts at 75% of maximum". — [fs/fuse/inode.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/fuse/inode.c)
- FUSE writeback-cache mode (`FUSE_WRITEBACK_CACHE`): writes go only to the page cache; dirty pages are written back by background writeback or reclaim, or by close/fsync/munmap. Partial-page writes make the kernel READ from user space first. — [Linux docs: fuse-io](https://docs.kernel.org/filesystems/fuse/fuse-io.html)
- IO-less throttling design (LWN, 2011-08-31). The old `balance_dirty_pages()` made the dirtier write back pages, which gave "terrible I/O patterns". The new design estimates N active dirtiers (pages dirtied divided by the per-task limit) and gives each about 1/N of the bdi bandwidth (`dirty_ratelimit`), multiplied by `pos_ratio`. The pause is computed from the rate limit and recently dirtied pages, and capped at 200 ms. A "think time" adjustment evens out pauses. — [LWN: No-I/O dirty throttling](https://lwn.net/Articles/456904/)

### Inferences
- For SliceFS's shared dirty budget: (1) Keep two thresholds. At the soft one, wake the background flusher or committer. At the hard one, throttle. (2) Make the writer that adds dirty bytes pay by sleeping in its own request handler. Do not make it do another file's flush, and never block an unrelated writer. (3) Use a smooth delay curve instead of a cliff. ZFS's `scale*(dirty-min)/(max-dirty)` (section 4 below) or the Linux pos_ratio curve both work. (4) Cap each pause (200 ms in Linux) and loop. (5) Use sharded or per-thread atomic counters with a batch threshold, and read the exact sum only near the limit. This bounds contention on the budget.
- In writeback-cache mode, the kernel already throttles writers into the FUSE mount to about 1% of the dirty threshold (strictlimit). The daemon's own budget then covers its overlays and WAL, not the page cache.

### Gaps
- The kernel version where IO-less throttling merged is not stated in the fetched LWN article; it is commonly said to be 3.1/3.2 (2011), but I did not verify this.
- The default `ratelimit_pages` value and the cgroup-writeback (memcg-aware `dtc`) details were not extracted.

## 4. ZFS write throttle: the dirty-data budget and delay curve

### Takeaway
ZFS bounds dirty data per pool with `zfs_dirty_data_max` (default 10% of RAM, capped at min(RAM/4, 4 GiB)). It starts a txg sync at 20% of that. Above 60% it adds a delay to every transaction that grows hyperbolically: `scale*(dirty-min)/(max-dirty)`. At 100% it blocks hard until space frees. Delays are scheduled relative to the last waiter's wakeup, so total throughput is limited no matter how many threads there are. Async write I/O concurrency grows linearly between 30% and 60% dirty.

### Cited Findings
- `zfs_dirty_data_max`: "Determines the dirty space limit in bytes." When it is exceeded, new writes halt. Default `physical_ram/10`, capped at `zfs_dirty_data_max_max`. `zfs_dirty_data_max_percent` defaults to 10. `zfs_dirty_data_max_max` defaults to min(RAM/4, 4 GiB) on 64-bit and is enforced only at module load. — [OpenZFS zfs(4)](https://openzfs.github.io/openzfs-docs/man/master/4/zfs.4.html)
- `zfs_dirty_data_sync_percent` = 20: "Start syncing out a transaction group if there's at least this much dirty data". It should be below `zfs_vdev_async_write_active_min_dirty_percent`. — [zfs(4)](https://openzfs.github.io/openzfs-docs/man/master/4/zfs.4.html)
- `zfs_delay_min_dirty_percent` = 60: "Start to delay each transaction once there is this amount of dirty data". `zfs_delay_scale` = 500000: "controls how quickly the transaction delay approaches infinity". — [zfs(4)](https://openzfs.github.io/openzfs-docs/man/master/4/zfs.4.html)
- Async write I/O depth: below 30% dirty (`..._active_min_dirty_percent`) use `zfs_vdev_async_write_min_active`; above 60% use `max_active`; between them, linear interpolation. — [zfs(4)](https://openzfs.github.io/openzfs-docs/man/master/4/zfs.4.html)
- Delay formula: "min_time = scale * (dirty - min) / (max - dirty)", "capped at zfs_delay_max_ns". "only as the amount of dirty data approaches its limit does the delay start to increase rapidly." Serialization: "If there is already a transaction waiting, we delay relative to when that transaction finishes waiting" (`dp_last_wakeup`). The minimum time per transaction therefore does not depend on the number of threads. — [module/zfs/dmu_tx.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/dmu_tx.c)
- Hard limit: "The hard limit though is rarely reached, so check it unlocked, taking the lock only if we may have to wait". When `dp_dirty_total >= zfs_dirty_data_max`, the thread increments `dp_dirty_waiters` and waits on `dp_spaceavail_cv`. — [dmu_tx.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/dmu_tx.c)

### Inferences
- This is a complete, small design that SliceFS can copy almost directly. Use one atomic `dirty_total`. Read it lock-free on the fast path. Above `delay_min`, sleep `scale*(d-min)/(max-d)` (capped), scheduled after a shared `last_wakeup` timestamp under a small mutex. At `max`, wait on a condvar that the commit/flush signals when it frees bytes. Start a commit at `sync_percent`. Do all of this before the per-file overlay lock is taken, or after it is released (the ERESTART rule).

### Gaps
- The `zfs_txg_timeout` default (commonly 5 s) and `zfs_delay_max_ns` (commonly 100 ms) were in the truncated part of the page and are not verified here.

## 5. macOS / APFS / FSKit concurrency

### Takeaway
There is little public material. Apple's legacy kernel filesystems (HFS+) did their own per-file locking: each cnode has an rwlock taken shared or exclusive, and a separate truncate lock. FSKit, according to an Apple DTS forum answer, delivers all operations over NSXPC on one serial queue. A FSKit module must therefore dispatch work to other queues itself to get any parallelism, and it must make its own per-item locking safe.

### Cited Findings
- HFS+ cnode (older XNU, about xnu-1228 to 2422): `lck_rw_t c_rwlock` plus `c_lockowner` for the exclusive case, and a separate `c_truncatelock` "protects the file from truncation during read/write". `hfs_lock()` takes `HFS_SHARED_LOCK` or `HFS_EXCLUSIVE_LOCK`. Reclaim drops the cnode lock before it calls the cluster layer, because the cluster layer can re-enter the fs (for example `VNOP_BLOCKMAP`) and cause a double-lock panic. — [xnu hfs_cnode.h](https://opensource.apple.com/source/xnu/xnu-2422.90.20/bsd/hfs/hfs_cnode.h.auto.html); [hfs_cnode.c](https://opensource.apple.com/source/xnu/xnu-2050.7.9/bsd/hfs/hfs_cnode.c.auto.html)
- FSKit: "All operations are received over NSXPC, on a serial queue. To improve concurrency, you may want to consider making the first step of any work be dispatching that work to a different queue." (Apple DTS engineer, developer forums. This is not official documentation, and I could not confirm it for the current macOS.) — [Apple Developer Forums thread 831338](https://developer.apple.com/forums/thread/831338?answerId=891228022)
- FSKit has moved from the "operations" protocols to "handler" protocols; the operations protocols are deprecated. — [FSKit updates](https://developer.apple.com/documentation/updates/fskit.md)

### Inferences
- The HFS truncate lock is the same idea as Linux `invalidate_lock`: a lock that keeps truncate apart from I/O, kept separate from the metadata lock.
- For SliceFS on FSKit: per-vnode serialization is not provided for you. The delivery queue is serial, so concurrency must come from SliceFS's own dispatch. A long operation that runs on the serial queue blocks all other operations.

### Gaps
- I found no public docs on APFS internal locking, or on XNU VFS rules for vnode locking around VNOPs (generic `vnode_lock` semantics). Background knowledge says XNU VFS calls VNOPs without holding a vnode data lock and leaves locking to the fs, but this is not verified from a fetched source.

## 6. Failure modes these designs guard against

### Takeaway
The recurring hazards are these: (1) lock-order inversion, guarded by global rank ordering (rename lock, then directories ancestor-first, then non-directories by address or inode number; XFS `iolock -> invalidate_lock -> page -> ilock`); (2) waiting for a commit while you hold a transaction handle or a lock the commit needs, guarded by ZFS ERESTART/drop-locks-and-retry and the jbd2 rule "no force commit with an active handle"; (3) memory-reclaim recursion, where an allocation inside fs code with locks or a transaction held calls back into the fs for writeback, guarded by GFP_NOFS / `memalloc_nofs_save()` scopes; (4) re-entry from a lower layer back into the fs, as in the HFS reclaim double-lock; (5) one untrusted or slow fs holding all the dirty memory, guarded by the FUSE strictlimit 1% cap; (6) writer-initiated writeback causing seek storms and unfair stalls, replaced by IO-less pause-based throttling.

### Cited Findings
- GFP_NOFS keeps reclaim from calling into fs code. From fs code, "calling back into the filesystem risks deadlocking the system". The scoped API `memalloc_nofs_save()/restore()` (`PF_MEMALLOC_NOFS`, nestable) makes every allocation in a region NOFS. It follows the model of `memalloc_noio_save()` (3.9, 2013). The article dates from 2017-01-04, kernel 4.10-rc2 era, when there were over 1,300 GFP_NOFS uses. — [LWN: Scoped GFP_NOFS](https://lwn.net/Articles/710545/)
- jbd2: "there a couple of ways the journal layer can cause a deadlock"; "you must complete the transaction at the end of each file/inode/address etc. operation"; treat start/stop "as if they were semaphores"; force-commit with an active handle "will deadlock". — [journalling.rst](https://docs.kernel.org/filesystems/journalling.html)
- ZFS: must not hold `dn_struct_rwlock` while assigning a tx ("can lead to deadlock"); on ERESTART, drop all locks, `dmu_tx_wait()`, then retry. — [dmu_tx.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/dmu_tx.c)
- Directory rename deadlock freedom depends on the common-ancestor check. — [directory-locking.rst](https://docs.kernel.org/filesystems/directory-locking.html)
- XFS orders its three locks "to prevent deadlock". — [xfs_inode.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/xfs/xfs_inode.c)
- HFS reclaim drops the cnode lock before calling cluster code that may re-enter through VNOP_BLOCKMAP. — [hfs_cnode.c](https://opensource.apple.com/source/xnu/xnu-2050.7.9/bsd/hfs/hfs_cnode.c.auto.html)
- strictlimit exists "to prevent mistrusted filesystems from growing a large number of dirty pages before throttling"; FUSE caps each fs at 1%. — [page-writeback.c](https://raw.githubusercontent.com/torvalds/linux/master/mm/page-writeback.c); [fuse/inode.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/fuse/inode.c)

### Inferences (SliceFS mapping)
- Lock rank for SliceFS: commit gate (shared) → rename mutex → directory inode locks (ancestor-first) → file inode locks (by inode number) → overlay/range lock → chunk-store/WAL internals. The budget wait and the commit-gate wait must happen with no inode or overlay lock held (ZFS ERESTART pattern). Otherwise a writer holding an overlay lock waits for budget, the committer needs that overlay to free budget, and nothing moves.
- The FUSE analog of reclaim recursion: the daemon's own memory pressure, or a kernel writeback of FUSE pages, sends WRITE requests back to the daemon. If every daemon thread is blocked on the budget, waiting for a commit that itself needs a worker thread, the system deadlocks. Mitigations: keep the commit and flush on dedicated threads that are never throttled (like ZFS sync or the Linux flusher), and exempt flush/fsync-path requests from the throttle (like `DMU_TX_NOTHROTTLE` / reserved jbd2 handles).
- Make the throttle per writer (the writer pays) and smooth (pos_ratio / ZFS curve). Then one heavy writer cannot starve light writers through a single global stall.

### Gaps
- Writeback deadlock with FUSE specifically (for example, temp-page copying in fuse writeback and the removal of `NR_WRITEBACK_TEMP` in recent kernels) was not researched in this pass.
