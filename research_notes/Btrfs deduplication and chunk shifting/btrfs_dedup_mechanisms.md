# Btrfs Deduplication Mechanisms (status as of Nov 2026)

## Does mainline Btrfs have in-band (inline) dedup, and what happened to the in-band dedupe patch series?

### Takeaway
No. Mainline Btrfs is out-of-band only, as of the current docs (latest kernel listed is 7.3, Oct 2026). The Fujitsu in-band dedupe series (Qu Wenruo, later Lu Fengqi) went through about 15 versions from 2015 to 2018 and was never merged. The maintainer put it on hold in Nov 2018 because the design was not finished: only an in-memory hash backend existed, with no persistent on-disk hash tree. In 2019 (v5.4-rc1) the leftover hooks were removed from the tree because "it's unlikely in-band dedupe is going to land".

### Cited Findings
- Official docs (current): "BTRFS implements **only out-of-band** type". Duplicates "have to be actively looked for and deduplicated by the user application." — [btrfs docs: Deduplication](https://btrfs.readthedocs.io/en/latest/Deduplication.html)
- The Kernel-by-version changelog runs to 7.3 (Oct 2026). It has no in-band dedupe entry. — [btrfs docs: Kernel-by-version](https://btrfs.readthedocs.io/en/latest/Kernel-by-version.html)
- HISTORICAL: v14.5 of "Btrfs In-band De-duplication" (14 patches) was posted by Lu Fengqi on 12 Dec 2017, rebased on v4.15-rc3. Qu Wenruo is the author of several patches. The v11 changelog says: "Remove other backend and props support to focus on the framework and in-memory backend. Suggested by David." The v3 changelog: "Increase dedup block size up limit to 8M." — [LWN repost of the v14.5 cover letter](https://lwn.net/Articles/741224)
- HISTORICAL: v13 was posted in Sept 2016. — [lore: PATCH v13 00/15](https://lore.kernel.org/all/20160910002259.GR5316@wotan.suse.de/T/). An earlier version was covered by LWN in 2016. That article describes a dedicated hash B-tree (lookup by hash and by extent bytenr). It also says the in-band code did *not* byte-compare: if the hash matched, the extents were assumed identical. — [LWN 679031](https://lwn.net/Articles/679031/) (summary from search snippet; full article not fetched)
- HISTORICAL: v15 was rebased on v4.20-rc1 (6 Nov 2018). — [lore: v15 cover](https://lore.kernel.org/linux-btrfs/20181106064122.6154-1-lufq.fnst@cn.fujitsu.com/)
- HISTORICAL: David Sterba replied on 13 Nov 2018. Per the search snippet, he said the work was on hold because the design phase was not finished. The code was still only the in-memory backend, and the persistent hash tree had to be at least drafted or prototyped before btrfs could claim in-band dedupe. — [lore: Sterba reply](https://lore.kernel.org/linux-btrfs/20181113134545.GY24115@twin.jikos.cz/) (direct fetch returned 403; the content comes from the search-engine summary)
- A matching btrfs-progs series (v10.5, Sept 2018) added a `dedupe-inband` command group. Its draft man page says kernel support starts in 4.19, but that kernel side never landed (see the removal commit below). — [lore: btrfs-progs v10.5](https://lore.kernel.org/all/20180904070728.5495-6-lufq.fnst@cn.fujitsu.com/T/)

Its message says "It's unlikely in-band dedupe is going to land so just remove any leftovers - dedupe.h header as well as the 'dedupe' parameter to btrfs_set_extent_delalloc." — [openSUSE kernel-source patch copy](https://code.opensuse.org/kernel/kernel-source/blob/042e8ebb8c7c150b62a6060b5b063b2916bae4de/f/patches.suse/btrfs-Remove-leftover-of-in-band-dedupe.patch); [mirror of commit](https://lab.nexedi.com/kirr/linux/-/commit/330a582790452a159686c5dab8f4286babd9c00e) (both blocked direct fetch; the text comes from search snippets)

It also says the feature is not actively developed, though some patches have been posted. — [archived btrfs wiki: Deduplication](https://archive.kernel.org/oldwiki/btrfs.wiki.kernel.org/index.php/Deduplication.html)

### Inferences
- The reasons it was blocked: the design was incomplete (a persistent hash store was needed), RAM cost, and hash-only matching with no byte-verify. Later dedup work moved to userspace tools plus kernel helpers (for example, the 7.2 checksum-read ioctl, below).

## What kernel interfaces exist for out-of-band dedup (FIDEDUPERANGE, FICLONERANGE), and what are their exact semantics and constraints?

### Takeaway
FIDEDUPERANGE (the VFS form of the old BTRFS_IOC_FILE_EXTENT_SAME, generic since Linux 4.5) locks both ranges and byte-compares them in the kernel. If they are identical, it remaps the destination to share the source extents, so it is safe against races. FICLONERANGE/FICLONE (reflink) shares extents with no comparison. Start offsets must be aligned to the fs block size. The length is rounded down to a block multiple, except for a partial EOF block that ends at EOF in both files. The VFS caps one request at 1 GiB. Btrfs internally processes it in 16 MiB pieces (the man page says the per-call limit is "typically 16 MiB" and is enforced silently). Same-file dedupe is allowed (since 4.2), but overlapping ranges in one file are not. Btrfs needs matching checksum/NOCOW status on both files. Since kernel 7.2, a new ioctl exposes raw data checksums to userspace as a dedupe hint.

### Cited Findings
- FIDEDUPERANGE does "compare and share if identical". Both files must be on the same filesystem. — [ioctl_fideduperange(2)](https://man7.org/linux/man-pages/man2/ioctl_fideduperange.2.html)
- Struct: `file_dedupe_range {u64 src_offset, src_length; u16 dest_count; reserved...; file_dedupe_range_info info[]}`. Each info has `dest_fd, dest_offset`, the output `bytes_deduped`, and `status` (FILE_DEDUPE_RANGE_SAME / FILE_DEDUPE_RANGE_DIFFERS / negative errno). The whole argument must fit in one page, so there is one source and many destinations per call. — [ioctl_fideduperange(2)](https://man7.org/linux/man-pages/man2/ioctl_fideduperange.2.html)
- "If even a single byte in the range does not match, the deduplication request will be ignored". "Deduplication is atomic with regards to concurrent writes". Maximum src_length is "filesystem-dependent and is typically 16 MiB", "enforced silently by the filesystem". "Disk filesystems generally require the offset and length arguments to be aligned to the fundamental block size". "Neither Btrfs nor XFS support overlapping deduplication ranges in the same file". The call was previously `BTRFS_IOC_FILE_EXTENT_SAME` (Btrfs-private) and became generic in Linux 4.5. — [ioctl_fideduperange(2)](https://man7.org/linux/man-pages/man2/ioctl_fideduperange.2.html)
- Errors: EBADF (src not readable / dest not writable or append-only), EINVAL, EISDIR, ENOMEM, EOPNOTSUPP, EPERM (immutable), ETXTBSY (swapfile), EXDEV (different filesystems). — [ioctl_fideduperange(2)](https://man7.org/linux/man-pages/man2/ioctl_fideduperange.2.html)
- VFS checks (`generic_remap_checks`): "The start of both ranges must be aligned to an fs block" (`-EINVAL` otherwise). "Dedupe requires both ranges to be within EOF". Otherwise the count is `ALIGN_DOWN(count, bs)`. The partial-EOF-block rule: "For deduplication we accept a partial EOF block only if it ends at the [EOF of both files]". "Don't allow overlapped cloning within the same file". — [fs/remap_range.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/remap_range.c)
- `generic_remap_file_range_prep` with REMAP_FILE_DEDUP calls `vfs_dedupe_file_range_compare()` (the in-kernel byte compare) and returns `-EBADE` if the ranges are not identical. — [fs/remap_range.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/remap_range.c)
- `vfs_dedupe_file_range`: "Arbitrary 1G limit on a single dedupe request, can be raised" (`len = min(len, 1<<30)`). The source must be FMODE_READ. Permission on the destination (`may_dedupe_file`) is granted if any of these holds: CAP_SYS_ADMIN, the file is open for write, the caller owns the inode, or the caller has inode write permission. So a non-root user can dedupe into files they own even if the fd is read-only. — [fs/remap_range.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/remap_range.c)
- Btrfs: `#define BTRFS_MAX_DEDUPE_LEN SZ_16M`. `btrfs_extent_same()` loops over 16 MiB pieces plus a tail (`tail_len = olen % BTRFS_MAX_DEDUPE_LEN`). `btrfs_remap_file_range()` accepts only REMAP_FILE_DEDUP | REMAP_FILE_ADVISORY. Dedupe goes to `btrfs_extent_same()` and clone goes to `btrfs_clone_files()`. The dest range is locked "to serialize with concurrent readahead()". A NODATASUM mismatch is rejected ("Don't make the dst file partly checksummed"). Inline extents "always have to start at file offset 0". — [fs/btrfs/reflink.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/reflink.c)
- Note: the man page says the ~16 MiB limit is silent. Current kernel code shows Btrfs loops internally in 16 MiB pieces up to the VFS 1 GiB cap. The man-page statement may reflect older Btrfs behavior. Callers should always check `bytes_deduped`. — [man page](https://man7.org/linux/man-pages/man2/ioctl_fideduperange.2.html) vs [reflink.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/reflink.c)
- Btrfs doc: the kernel compares blocks byte by byte and does not trust hashes. Extent pages are locked during dedupe, which blocks buffered/mmap writes. Files must have the same COW status (both COW with csums, both NOCOW, or both COW+NODATASUM). Send cannot start while dedupe runs. Dedupe can increase metadata use. — [btrfs docs: Deduplication](https://btrfs.readthedocs.io/en/latest/Deduplication.html)
- NEW (kernel 7.2, Aug 2026): a new ioctl returns raw data checksums to userspace. It "can be used for mkfs and deduplication optimizations". Per the Dedup page, tools can use it as a hint to skip reading blocks. Checksums are not used for the final comparison. Compressed and inline extents do not expose raw checksums through it. — [Kernel-by-version](https://btrfs.readthedocs.io/en/latest/Kernel-by-version.html); [Deduplication](https://btrfs.readthedocs.io/en/latest/Deduplication.html)
- Version history: 3.6 cross-subvolume clone (reflink). 4.1 clone within the same file. 4.2: "deduplication on the same inode works", "deduplication does not change mtime/ctime", "EXTENT_SAME ioctl: handle unaligned length". 5.2: "send and dedupe can't be run at the same time". 5.7: reflink works on inline extents. 5.18: "allow reflinks/deduplication from two different mounts of the same filesystem". 6.4: a backref fix broke a LOGICAL_INO_V2 mode used by dedupe tools. 7.1/7.2: reflink/flushoncommit deadlock fixes. — [Kernel-by-version](https://btrfs.readthedocs.io/en/latest/Kernel-by-version.html)
- Support ioctls that dedupe tools use: TREE_SEARCH_V2 (scan metadata, filter by `min_transid`) and LOGICAL_INO / LOGICAL_INO_V2 (map a physical extent to inode/offset backrefs; v2 added in 4.15). — [bees how-it-works](https://github.com/Zygo/bees/blob/master/docs/how-it-works.md); [archived wiki](https://archive.kernel.org/oldwiki/btrfs.wiki.kernel.org/index.php/Deduplication.html)
- `xfs_io` can call the VFS dedupe ioctl on btrfs (`dedupe` command). — [archived wiki](https://archive.kernel.org/oldwiki/btrfs.wiki.kernel.org/index.php/Deduplication.html)

### Inferences
- The dedupe unit is the fs block (sectorsize, normally 4 KiB). Any duplicate that is not at the same offset modulo 4 KiB in both files cannot be shared, because both start offsets must be block-aligned. Btrfs therefore cannot dedupe content that is shifted by a non-block-multiple (for example, an insertion of a few bytes). This matters for "chunk shifting".
- FICLONERANGE uses the same alignment rules (same `generic_remap_checks`) but skips the compare. dduper's fast mode depends on this.

- I did not find the name or exact interface of the 7.2 checksum ioctl. The docs I fetched do not name it.

## How do the main tools work (duperemove, bees, dduper, jdupes/rmlint/fdupes)?

### Takeaway
- **duperemove**: extent-granular by default. It hashes extents (plus optional per-block hashes at the -b block size, default 128K) and whole files. It stores hashes in an sqlite hashfile, rescans only changed files, and submits FIDEDUPERANGE.
- **bees**: a whole-filesystem daemon. It hashes 4K blocks into a fixed-size, mlocked, LRU-bucketed hash table of physical addresses (16 B/entry). It crawls new extents incrementally by transid and extends matches around a hit. It rewrites partially-matching extents via temp copies so that whole extents can be freed.
- **dduper**: reads the btrfs csum tree (needs patched btrfs-progs) instead of reading data, and compares in 128KB chunks by default.
- **jdupes/rmlint**: whole-file duplicate finders that call FIDEDUPERANGE on whole files. fdupes is only a finder.

### Cited Findings
**duperemove**
- Hashes files "on an extent by extent basis". "Optionally, a per-block hash can be applied". It submits matches with FIDEDUPERANGE. It "will only compute hashes for those files which have changed since the last run" when a hashfile is used. The example output shows "Using 128K blocks" and "Using hash: murmur3". libxxhash ≥0.8.0 is a dependency. — [duperemove README](https://raw.githubusercontent.com/markfasheh/duperemove/master/README.md)
- Man page (dated 01 Mar 2025): `-b` blocksize "Defaults to 128K". "Larger blocksizes will fragment less but may not save you as much space". "Duperemove by default works on extent granularity", so identical files with different extent layouts may not be deduped. `--dedupe-options`: `partial` (off by default, a CPU-intensive comparison of extent portions whose semantics "may change"), `same` (on, same-file dedupe), `only_whole_files` (off). `--hashfile` is an sqlite3 database that is transactional and rescans only changed/new files. `-B/--batchsize` defaults to 1024 files. It "does not concern itself with the underlying representation of the extents" (compression is left to the kernel). Works on btrfs and xfs only. — [duperemove(8)](http://markfasheh.github.io/duperemove/duperemove.html)
- The archived wiki describes it as file-based, incremental, comparing by extent boundary by default. — [archived wiki](https://archive.kernel.org/oldwiki/btrfs.wiki.kernel.org/index.php/Deduplication.html)
- The official docs class duperemove as "file based", comparing within a given file list, incremental. — [btrfs docs](https://btrfs.readthedocs.io/en/latest/Deduplication.html)

**bees**
- It is block-oriented and whole-filesystem only (no include/exclude lists), and needs CAP_SYS_ADMIN. It "Works with btrfs compression", and dedupes snapshots and reflinks. The hash table is persistent and constant-size: "as little as 1 GB hash table per 10 TB unique data". It "Recovers more free space from btrfs than naive dedupers". — [bees README](https://raw.githubusercontent.com/Zygo/bees/master/README.md)
- Granularity: "4K filesystem data block size / clone alignment" is the tested configuration. Non-4K block sizes "should work if recompiled". "Non-equal hash (SUM) and filesystem data block (CLONE) sizes" are untested. — [bees btrfs-other.md](https://github.com/Zygo/bees/blob/master/docs/btrfs-other.md)
- Hash table: "Hash table entries are 16 bytes per data block". "bees only needs to find one block in common between two extents in order to be able to dedupe the entire extents". Sizing: 128MB per 1TB unique data gives about 128K average dedupe extent (recommended). 1GB/TB gives about 16K and 4GB/TB about 4K. Compressed filesystems need 2-4x. Scan mode 4 "extent" is the default (kernel ≥4.15). It processes extent size classes from largest (≥32M+1) to smallest (≤128K, "including all compressed extents"). — [bees config.md](https://github.com/Zygo/bees/blob/master/docs/config.md)
- The table stores physical block addresses, which are resolved on demand via TREE_SEARCH_V2 + LOGICAL_INO. It is mlocked in RAM, uses LRU lists with random insertion position, and trickle-writes to `beeshash.dat` at 128KiB/s. Progress is checkpointed every 15 min to `beescrawl.dat`. After a full pass, scans use `min_transid` with TREE_SEARCH_V2 to see only new data ("can complete in less than a millisecond on an idle filesystem"). On a hit, neighboring blocks are examined to grow the duplicate run. Only FILE_EXTENT_SAME modifies data. It maps the newer extent onto the older one. Otherwise it copies unmatched data to a temporary file, because "btrfs cannot partially overwrite extents--the _entire_ extent must be replaced". Zero blocks are replaced with holes. For compressed extents, "bees avoids splitting the extent in the middle" (this hurts the ratio and triggers a kernel bug). — [bees how-it-works](https://github.com/Zygo/bees/blob/master/docs/how-it-works.md)
- Gotchas: deduping a snapshot-shared extent forces metadata COW of the "entire metadata page in the snapshot subvol (16KB by default)" in every snapshot. "For 100 snapshots this can mean a 100x growth in metadata size and bees scanning time". Space is not freed until the last snapshot reference is processed. LOGICAL_INO calls over 5 s CPU are blacklisted as "toxic" extents (older kernels). A full balance invalidates the hash table. — [bees gotchas](https://github.com/Zygo/bees/blob/master/docs/gotchas.md)

**dduper**
- Works by "fetching built-in checksum from BTRFS csum-tree, instead of reading file blocks and computing checksum itself". The default chunk size is 128KB (`--chunk-size`). `--analyze` reports savings per chunk size. The default mode uses FIDEDUPERANGE ("100% safe"). `--fast-mode` uses FICLONERANGE with no kernel verify, followed by a SHA256 check. `--skip` disables the check. It is "beta quality". It started crc32-only and now has initial xxhash64/blake2/sha256 support. Same-file block dedupe is not supported. — [dduper GitHub](https://github.com/Lakshmipathi/dduper)
- It needs a btrfs-progs patch for csum access, and works on files and blocks. — [archived wiki](https://archive.kernel.org/oldwiki/btrfs.wiki.kernel.org/index.php/Deduplication.html)

**Whole-file tools**
- rmlint with `handler=clone` uses FIDEDUPERANGE and writes a reviewable `rmlint.sh`. jdupes (an fdupes fork) "includes support for BTRFS deduplication when it identifies duplicate files". fdupes is only a finder whose output other tools (for example, duperemove) can consume. — [archived wiki](https://archive.kernel.org/oldwiki/btrfs.wiki.kernel.org/index.php/Deduplication.html)
- The current docs list only bees (block-based) and duperemove (file-based) as "up-to-date, maintained and widely used". — [btrfs docs](https://btrfs.readthedocs.io/en/latest/Deduplication.html)

### Inferences
- All of these tools find duplicates only at fixed, block-aligned offsets: bees at 4 KiB, duperemove at extent or 128K-block granularity, dduper at a chunk size made of 4 KiB csums. None use content-defined chunking, so shifted data (inserts/deletes not aligned to 4 KiB) is invisible to them. This limit comes from both the tools and FIDEDUPERANGE's alignment rule.
- dduper's approach is now partly built into the kernel through the 7.2 checksum ioctl, with no need for patched progs (inference from the docs' description).

### Gaps
- bees's hash function is not stated in the docs I fetched.
- duperemove's current default hash (xxhash vs murmur3) is not stated explicitly. The README example shows murmur3, but the dependency list includes xxhash.
- I did not find the current maintenance state of dduper (no release dates fetched).

## How does dedup interact with snapshots, compression, and the bookend extent problem?

### Takeaway
Btrfs frees an extent only when no file references any byte of it. If dedupe replaces part of an extent, the remaining "bookend" references keep the whole original extent allocated, so naive block-range dedupe can save little or nothing. bees handles this by copying the unmatched remainder of a partially duplicated extent to a new extent so that the whole old extent can be released. Compressed extents are at most 128 KiB, which caps the dedupe unit there. bees avoids splitting them. Dedupe across snapshots unshares metadata pages and can greatly increase metadata use.

### Cited Findings
- "btrfs cannot partially overwrite extents--the _entire_ extent must be replaced". bees therefore copies unmatched portions to a temporary file for rescanning. — [bees how-it-works](https://github.com/Zygo/bees/blob/master/docs/how-it-works.md)
- bees claims it "recovers more free space from btrfs than naive dedupers". — [bees README](https://raw.githubusercontent.com/Zygo/bees/master/README.md)
- Bookend waste: an openSUSE bug says random-IO workloads can leave large unreachable space from "btrfs bookend extents", and that compsize does not measure bookend waste. A 2012 linux-btrfs thread shows the effect (18K wasted in an example), and Chris Mason preferred splitting the original extent when creating bookends. — [openSUSE bug 1222313](https://lists.opensuse.org/archives/list/bugs@lists.opensuse.org/thread/WPD7ZRBI45FL6I2GA2O62GXL5NQM6ZWV); [lore 2012](https://lore.kernel.org/all/20120412121623.GI29506@shiny/) (both from search snippets, not fetched directly)
- Compression: data is split into 128KiB chunks before compression. — [btrfs docs: Compression](https://btrfs.readthedocs.io/en/latest/Compression.html). bees puts "all compressed extents" in the ≤128K size class. — [bees config.md](https://github.com/Zygo/bees/blob/master/docs/config.md). bees avoids splitting compressed extents in the middle. — [bees how-it-works](https://github.com/Zygo/bees/blob/master/docs/how-it-works.md)
- Compressed and inline extents do not expose raw checksums through the 7.2 csum ioctl, so checksum-assisted dedup does not apply to them. — [btrfs docs: Deduplication](https://btrfs.readthedocs.io/en/latest/Deduplication.html)
- Snapshots: deduping an extent shared by snapshots forces a 16KB metadata page COW in each snapshot, up to "100x growth in metadata size" with 100 snapshots. Deduping before snapshotting avoids this. Space is freed only after the last reference is processed. — [bees gotchas](https://github.com/Zygo/bees/blob/master/docs/gotchas.md)
- Send cannot run at the same time as dedupe (since 5.2), because send needs a stable extent layout. — [Kernel-by-version](https://btrfs.readthedocs.io/en/latest/Kernel-by-version.html); [Deduplication](https://btrfs.readthedocs.io/en/latest/Deduplication.html)
- Dedupe requires matching COW/csum status. NOCOW files cannot be deduped against COW+csum files. — [btrfs docs](https://btrfs.readthedocs.io/en/latest/Deduplication.html); [reflink.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/reflink.c)

### Inferences
- A file-range deduper (duperemove partial/block mode, dduper) that dedupes only the matching blocks of a large extent can increase total space use temporarily. Both the old extent (pinned by the bookend refs) and the referenced target stay allocated. Space is recovered only when every block of the old extent has been remapped. This explains duperemove's default of whole-extent matching.
- Uncompressed extents can be up to 128 MiB. The bookend penalty for a partial match is therefore much larger for uncompressed data than for compressed data (≤128 KiB). I did not find a fetched source for the 128 MiB figure.
