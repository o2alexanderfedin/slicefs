## Draft 1: note for #20 (post with the FSKit large-copy result)

A correction to the evidence comment above, after the changes of #98 (Phase 14):

- Item 2 (rename after `fsync` of the directory): since 33b0ebd the default write-log mode (per-op) keeps a rename even with no sync after it. So the Docker check 05c passed with or without the `fsync` of the directory. 05c now runs with `--wal-strategy flush-on-fsync`, and its control (a rename with no sync after it) must be lost, or the check fails (#116).
- Item 4 (large copy): Buffered mode does not exist now; an out-of-order write goes to an overlay with a fixed dirty limit (#98). The peak RSS check now also covers the final commit at the unmount. Current values (Linux, Docker, debug build, #116): VmHWM 32 MiB after cp, 55 MiB after the out-of-order write, 56 MiB at the unmount (cap 512 MiB).
- macOS FSKit (WLOG-02): the large copy now runs in the macOS CI workflow (#134). CI run 44517381182: file size 1,073,741,824 bytes, daemon peak RSS 64 MiB, `cmp` after the copy ok, `cmp` after the remount ok.

## Draft 2: new issue (superseded: fixed by #137, index 59.6 to 39.5 B per object)

Title: storage: the on-disk chunk index adds about 60 B for each object on disk

From #85 (PR #109). With the on-disk index, the store needs about 164 B for each object, against 104 B with the #66 layout (+58 %). The index runs hold (ObjectId, Loc) in 4 KiB pages: 32 B of ID and the Loc for each entry, plus the per-run filter and fences (`docs/design/chunk-store.md`, section "Index results (#85)").

To examine:
- Store a shorter key in the runs (for example the first 8 or 16 bytes of the ID) and confirm a hit with the `.idx` entry of the pack, which has the full ID.
- A smaller Loc encoding (pack number and offset with fewer bits).
- The cost in lookup time of each change (`benchmarks/index-bench`, 10M and 100M).

Measure: disk bytes for each object, hit and miss time, before and after.

## Draft 3: new issue (superseded: cold cache measured by #135; 100M on Linux, macOS cold and HDD not possible here)

Title: benchmarks: index numbers with a cold page cache and on an HDD

The #66 and #85 numbers use a warm page cache ("cold open" means a new process), on an SSD. A cold page cache, and an HDD, can change the open time and the lookup times much, because a hit reads one 4 KiB page of a run file.

To do:
- `index-bench` open and lookup steps after a drop of the page cache (Linux: `echo 3 > /proc/sys/vm/drop_caches` in the Docker VM; macOS: `purge`), at 10M and 100M objects.
- The same on an HDD, if one is available.
- A Linux 100M run on a host with about 25 GB of free RAM (the Docker VM had 12.6 GB).

Record the numbers in `docs/design/chunk-store.md`, next to the warm-cache tables.
