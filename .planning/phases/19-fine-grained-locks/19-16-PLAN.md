<objective>
Measure, document and close (orchestrator decision G6, gap closure).

The serialize-off lock-stats harness runs again on macOS and in Docker Linux. The runs must show that the hold maxima of the store lock, `readers`, the WAL append and writer locks, `dir_live` and `inode_live` no longer include disk I/O (ROADMAP criterion 3, LOCK-01). Then the docs, the deferred list and the draft #21 body are brought in line with the code of 19-12..19-15.

Thresholds (planner choice, stated before the runs). They apply to the six sites store, readers, wal_queue, wal_writer, dir_live and inode_live, in each mode of each run:
- Linux (Docker, debug): hold p99 at most 500 us and hold max at most 2000 us.
- macOS (debug): hold p99 at most 500 us and hold max at most 5000 us.
  - A disk wait behind an F_FULLFSYNC was 20-60 ms, so 5 ms separates it from scheduler noise of a debug build with 4 workers, a commit thread and seal threads.
  - The Linux baseline (spike 19g) had one 144 ms outlier, so a single max above the bar can be noise.

Outlier rule (stated before the runs). The cause decides, not the count, because LOCK-01 is about disk I/O, a hash or a wait in a hold, and a CPU-only hold in a debug build (for example `encode_index` in a seal) can pass a bar in every run:
1. Any site and mode over its bar (p99 or max) in any run starts attribution on that system. Apply the spike 19g probe locally (`runs/spike-19g-probe.patch`, adapted to the current code, with its hold threshold set to the bar; never committed). Run it up to 5 times, until it captures holds of that site at or above the bar.
2. A captured hold whose span is disk I/O (fsync, F_FULLFSYNC, pwrite, file create, directory sync, a pack, segment or run read from disk) or a wait on another lock that holds such I/O fails the site.
3. A captured hold with no I/O span (CPU, scheduling) is a residual. The SUMMARY lists it with its value, mode, run and span.
4. If 5 probe runs capture no hold of that site at or above the bar, the miss is unattributed. The site passes only if the miss was in at most 1 of the 3 measurement runs; otherwise it fails, because its cause cannot be shown.
5. A failed site leaves LOCK-01 unmarked. The SUMMARY names the site and its path for the orchestrator (Rule 4).

Known residuals to watch, not hidden: the re-lookup in `locked_lookup` under the store lock can read a run page (a page-cache read, from 19-02); the GC copy loop, `gc_begin`, `close`, `rotate` (offline), destroy and the commit cut (exclusive gate) keep locked I/O and are off the request paths.

LOCK-04: its code part is closed (19-10 tests and 19-13 mkdir). Its last clause, "the #21 body is updated to match", needs the orchestrator to apply the draft body with `gh issue edit`. The executor does not run `gh issue edit` and does not mark LOCK-04. The orchestrator marks it after it applies the body and its live-body checks pass.

Purpose: the verifier gets numbers and text that match the code.
Output: two run logs, the updated doc sections, the draft body, the requirement marks the evidence supports.
</objective>
