<objective>
Close the store-lock part of LOCK-01 (ROADMAP Phase 19 criterion 3). Spike 19g measured two disk waits in the store lock hold: the second phase of `ChunkStore::sync` (an F_FULLFSYNC, 20-62 ms) and the record pwrite of a put (19-39 ms on macOS behind any F_FULLFSYNC on the volume). After this plan neither runs with `ChunkStore::inner` held.

Orchestrator decisions implemented here (gap closure, reversible internals):
- G1: in `ChunkStore::sync` phase 2 (and in the index flush), under the store lock only join the seal, take a sync handle and its mark; fsync and directory sync with no lock; set `failed` under the lock on an error. `RetryingPack` gets a real `sync_handle`, so its retry copies clear after a sync.
- G2 (store half): the record pwrite leaves the lock: under the lock the write is registered at the pack end, the pwrite runs with no lock, the result is published under the lock; a record is invisible before its publish, and a sync covers only published writes. F_FULLFSYNC vs fsync semantics do not change.
- G2 supersedes D-14 (decided autonomously in CONTEXT: "a page-cache pwrite under ChunkStore::inner is not disk I/O"). Spike 19g shows that such a pwrite waits about 20 ms behind any F_FULLFSYNC on macOS. The append doc comment that cites D-14 and the 19-02 threat T-19-03 ("the record write stays under the lock") are updated here.

Planner choices (reversible, recorded for the SUMMARY):
- One record write in flight per active pack. This is the G2 pending entry with at most one entry. A later put waits for it with no lock (it waited on the store lock before). Reason: the pack never has a hole, so `scan_pack` (stops at the first bad record), `resync_scan`, `covers` and the hwm rule need no change. More than one write in flight would need hole handling in all three scanners.
- The dirty flags are cleared after the unlocked fsync by mark (the 19-04 `SyncMark` pattern), not before it. If they were cleared before, a second sync would return before the first fsync ended. A seal that started in between would also skip its pack sync (`SealJob` syncs only a dirty pack).
- The RetryingPack sync handle repairs a short error itself (re-write the copies, sync again, with backoff) with no store lock held. So `a_short_sync_error_is_repaired_and_the_data_is_durable` stays green, and `failed` is set only after the retries end (G1).

Purpose: the store lock covers memory work only on the put, read and sync paths.
Output: unlocked phase-2 and flush syncs, the RetryingPack sync handle, the unlocked record write, and the tests.
</objective>

retry.rs: move the copy state of `RetryingPack` into a shared `Arc` of a small `Rank::Store` mutex:

- kept;

`RetryingPack` and its sync handles both use this state.

`RetryingPack::sync_handle()` returns a handle only when the inner file has one. The handle remembers the sequence of the newest copy at the time it is taken. Its `sync()` runs the inner handle sync with no lock of the pack state held. On success it records "synced up to that sequence" in the shared state. On an error it repairs as `repair` does today: take clones of the copies up to its sequence (copies are cheap to clone if stored as `Arc<[u8]>`), re-write them at their offsets through a `&self` positional write of the inner file (`FilePack`: positional write on its file; `MemPack`: as `write_at`), sync again, with the `backoff` waits. It holds no lock across these writes. After the last attempt it marks the state broken and returns the error.

`RetryingPack` drops the copies up to the recorded sequence at the start of `write_at`, `sync`, `sync_soon` and `settle`, and lowers kept. `Flight.covers` becomes a sequence number too, so drops by a flight and by a handle compose.
