<objective>
Close the write and read part of LOCK-05 (ROADMAP Phase 19 criterion 1).

19-11 Finding 5 found locked fallbacks: after a dropped or concurrent step, a write runs its first-write content check, its stream steps, its overlay switch or its rebase step with the cell locked, and a read settles pending writes with the cell locked after a drop. While one runs, a reader of the file waits for a writer's I/O.

Orchestrator decision G3 (gap closure, reversible internals), write and read paths: no writer I/O (chunk, hash, store put) with a `FileCell` locked; replace "retry with the cell locked" with unlocked retries; at the hard cap the writer waits with no lock held (bounded) for the step in flight, or runs its own unlocked step, and applies its write only once under the cap; the per-file memory bound still holds. G5: the operational debug lines that run in a cell hold move out of it.

This honors D-02 (user decision, read while write): "a write does its rebase step outside the file lock ... publishes the result only if the file generation did not change; otherwise it drops the result and retries later. Readers hold the file lock only for memory copies (copy the overlay view or clone the stream), and then read with no lock."

Planner design (reversible, recorded for the SUMMARY):
- A per-cell step token (`stepping`, replaces the rebase-in-flight flag): at most one I/O step of a cell in flight.
  - In stream mode a writer waits for the token, with the cell released, before it changes the stream (a push, a pending insert, the overlay switch). So stream steps are not dropped by other writes. Only these can drop one: a size change or a truncate (19-15 makes size changes wait for the token too), the retire of the cell, an fsync that installs a newer stream snapshot (it moves `last_committed_root`, which the overlay switch checks; at most once, because no write can follow while the step is in flight, and a second fsync with no write in between installs nothing), or a forced drop.
  - In overlay mode writes are memory-only and do not wait. Only rebase steps take the token. The hard cap stops writes from changing the generation without bound, so a step at the cap publishes.
  - Writers waiting for a writer's I/O is allowed; readers never wait for the token.
- A flush (fsync) takes no token: it does not change the stream, and its publish rule (`last_published_gen`) already orders it.
- Reads compose pending writes from memory instead of settling them. The bytes are the same as after a settle: stream prefix, zeros in gaps, pending bytes on top, up to `byte_count`.

Out of this plan (19-15): release and finalize, the setattr size change of an open stream, the transient cell of a closed-file size change, and the forced-drop lock rows. 19-15 removes the locked fallbacks of finalize. Until then finalize may still call the locked forms.

Purpose: a reader of a file never waits for a writer's chunk, hash or store put on the write path.
Output: the step token, unlocked retries on the write path, composed stream reads, the hard-cap gate, the debug lines out of the hold, and the tests.
