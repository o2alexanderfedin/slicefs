<objective>
Log the write-path records under the same cell lock as their apply, and add `O_APPEND` handles whose end-of-file offset comes from the current size under the cell lock. Show the POSIX.1 2.9.7 rules with several handles in read-only, read-write and `O_APPEND` modes.

Decision IDs are numbered in 19-01-PLAN.md (objective). This plan implements:
- D-08 (write path) the log record append (memory copy plus LSN) happens under the same locks as its apply; disk write and sync happen outside the locks.
- D-12 the daemon takes the end-of-file offset of an append from the current size under the file lock.
- D-17 `O_APPEND`: no extra macOS CI probe; per-handle append flag, EOF under the cell lock, the log carries the effective offset.
- D-11 (test part) handles in read-only, read-write and `O_APPEND` modes; visibility across handles, all-or-none reads, appends that never overlap (the harness mode is Plan 11).

RESEARCH: "O_APPEND" daemon rules 1-4 (rule 5, the macOS probe, is not done per D-17), Pattern 3 last bullet (Release/Flush only when effective, two-handle replay test, Truncate inside the open's cell hold), Inventory C dependencies 8 (write path) and 15 (unlogged write when the handle is gone).

Purpose: ROADMAP criteria 5 (write path) and 6.
Output: logging inside the cell lock, the append flag and `handle_write_flags`, the multi-handle POSIX tests and two replay tests.
</objective>

Facts (verified at 2c39d65; grep the names, lines moved in Plans 01-07):
- `handlers.rs`: `Logged { _clock, time }` and `logged()` freeze the clock for one request; `Logged::log(fs, op)` calls `fs.log_record(Record { time, op })` after the apply returned. `handle_write` calls `fs.test_write`, then looks up the inode of the handle and logs `Op::Write { ino, offset, data }` (skipped silently when the handle is gone). `handle_open` logs `Op::Truncate { ino }` for a write open with `O_TRUNC`; `handle_release` and `handle_flush` log `Op::Release`/`Op::Flush` when the handle was a write handle.
- `filesystem.rs` `log_record` calls `meta.log_op` unless `replaying` is set (`replay_guard`); from Plan 04 the store has `log_append(bytes) -> Option<Lsn>` and `log_write_out(Option<Lsn>)`.
- `oplog::Op::Release` doc: "Release of a write handle: it finalizes the content and sets times"; replay keeps one handle per inode and finalizes at the first `Release` (`oplog.rs` near 245).
- `fuse_callbacks.rs` `write(.., _write_flags: WriteFlags, _flags: OpenFlags, ..)` ignores the flags; `open` logs `O_APPEND=` only; init requests `FUSE_ATOMIC_O_TRUNC` and `FUSE_BIG_WRITES`, no writeback cache (RESEARCH "O_APPEND"). On Linux the kernel passes `O_APPEND` in OPEN and WRITE flags and sets the WRITE offset from its cached size; the daemon must not depend on that.
- `MAX_FILE_SIZE` = 1 TiB; `test_write` returns EFBIG when `offset + len` passes it (`checked_add`).
- After Plan 05 `Handle { ino, write, append }` exists with `append = false`; after Plans 06-07 every apply that changes content is in a Phase C or a single cell-lock hold.
- `write_log_replay_tests.rs` has `new_fs_with`, `reload_and_replay`, `dump`, `dump_open`, `check`, `check_with`.
