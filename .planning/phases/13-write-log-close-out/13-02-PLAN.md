DEVIATION FROM D-04 (read this first). D-04 says "write it in reverse 1 MiB blocks with `dd seek=N conv=notrunc`" and "require VmHWM below 512 MiB". The code makes these two parts contradict each other:
- One `dd` per block opens the file again for each block. The file then has content, so `fresh` is false in `test_write` (crates/slicefs-cli/src/filesystem.rs, about l.733). The handle goes to Buffered mode at once and loads the whole committed file into RAM. Then each close hashes 1 GiB again: 1024 times 1 GiB.
- A full reverse on one handle is no better. The first block, at 1023 MiB, is more than REORDER_WINDOW (64 MiB) ahead, so the gap is streamed as zeros and the stream moves to the end. The next block is behind the stream, and the handle switches to Buffered (whole file in RAM, l.780-796).
So a literal reverse pass cannot meet any cap below the file size. This plan keeps the intent of D-04: out-of-order writes that the 64 MiB reorder window absorbs (what NFS and SMB clients send), with the cap "about 8x the window and well under the file size". It uses one python3 process with one open handle and 1 MiB blocks in reverse order inside each 16 MiB group. Each jump stays far inside the window. The section also counts "switches to Buffered" lines in mount.log, so a pattern that leaves the window fails the check and is not a silent pass. The SUMMARY and the #20 comment state the real scope of the bound. Rated reversible: it is a script detail.

Purpose: WLOG-01 (real `kill -9` evidence for the rename and torn-tail items) and WLOG-02 (the "786 MB over FUSE-T NFS" item, restated for libfuse).
Output: three new sections in one script, plus measured numbers (VmHWM, step times, `docker stats`) in the SUMMARY for the #20 comment.

- The image `slicefs-fusetest` (rust:1-bookworm) has python3 (/usr/bin/python3), perl 5.36, and coreutils 9.1 (`sync FILE` calls fsync on the path; for a directory the kernel sends FUSE FSYNCDIR; `truncate -s -3`; `sort -V`).
- Mount defaults: `--commit-interval` 30 s, `--cache-size` 0, `--wal-strategy` per-op. Per-op syncs Op records only on fsync or commit. Until then they wait in an 8 KiB BufWriter in the daemon, so `kill -9` loses them.
- filesystem.rs prints `... switches to Buffered (offset=...` with eprintln when a handle leaves Streaming mode.
- Segment files: `<store>/segments/segment-NNNNNN.seg`. The record frame ends with a 4-byte CRC32C, so a 3-byte cut leaves a torn record that the reader drops.
- A mount after a crash replays the log, commits (which deletes the old segments), and prints `Replayed N request(s) from the write log (M skipped).`
- No logger is installed in the daemon, so fuser request logs do not reach mount.log. The proof that `sync <dir>` mattered is the second, unsynced rename (Task 2).
