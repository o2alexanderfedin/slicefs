    **Step 2 — Generalize intern_* functions (write path):** Change all `intern_*` functions from taking `&mut Dictionary` to taking `&mut impl StorageAdd`. Since `Dictionary` implements `StorageAdd`, all existing call sites compile unchanged. The functions just call `State::push_all(storage, &bytes)` which already accepts `&mut impl StorageAdd`.

    Files and specific changes:
    - `inode.rs`: `intern_inode(dict: &mut Dictionary, ...)` -> `intern_inode(storage: &mut impl StorageAdd, ...)`
    - `inode_map.rs`: `intern_inode_map(dict: &mut Dictionary, ...)` -> `intern_inode_map(storage: &mut impl StorageAdd, ...)`
    - `manifest.rs`: `intern_manifest(dict: &mut Dictionary, ...)` -> `intern_manifest(storage: &mut impl StorageAdd, ...)`
    - `xattr.rs`: `intern_xattrs(dict: &mut Dictionary, ...)` -> `intern_xattrs(storage: &mut impl StorageAdd, ...)`
    - `directory.rs`: `create_dir_entries`, `add_dir_entry`, `remove_dir_entry`, `lookup_dir_entry` all change `dict: &mut Dictionary` to `storage: &mut impl StorageAdd`
    - `directory.rs` internal helpers: `entry_key`, `intern_entry_list` also need generalization

    For each function, update the import from `blockset::Dictionary` to `blockset::StorageAdd` (keep Dictionary import if still needed for other purposes). The function body remains unchanged since `State::push_all(dict, &bytes)` already uses `&mut impl StorageAdd` generic.

    **Step 3 — Generalize load_* functions (read path):** Change `load_*` functions from taking `&Dictionary` to taking `&mut impl Io`. These functions currently use `GetData::new(dict, &digest256)` and `GetBytes::new(get_data).collect()`. After migration, they must use `file_storage_get(io, &digest224)` to get raw bytes, then deserialize.

    The new pattern for each load function:
    ```rust
    pub fn load_inode(io: &mut impl Io, key: &Digest224) -> Result<InodeMeta, MetaError> {
        let bytes = file_storage_get(io, key)
            .ok_or(MetaError::Corrupted(format!("missing node for inode {:?}", key)))?;
        deserialize_inode(&bytes)
    }
    ```

    Apply this pattern to:
    - `inode.rs`: `load_inode` — bytes -> `deserialize_inode`
    - `inode_map.rs`: `load_inode_map` — bytes -> deserialize inode map
    - `manifest.rs`: `load_manifest` — bytes -> deserialize block list
    - `xattr.rs`: `load_xattrs` — bytes -> deserialize xattr pairs
    - `directory.rs`: `list_dir_entries` and internal `load_entry_list` — bytes -> deserialize entry list

    Note: `lookup_dir_entry` and `add_dir_entry`/`remove_dir_entry` call both `load_entry_list` (read) and `intern_entry_list` (write). These functions will need both `&mut impl StorageAdd` for writing AND `&mut impl Io` for reading. The simplest approach: since in Plan 02 the `StoreIo` will serve both roles, have these functions take `storage: &mut impl StorageAdd, io: &mut impl Io` as two parameters. The call sites in store.rs (Plan 02) will pass the same `StoreIo` instance (wrapped in `FileStorageAdd` for the storage param).

    ALTERNATIVE (preferred if possible): Since `directory.rs` functions do both reads and writes in a single call, and `FileStorageAdd` holds `&mut Io`, we can pass just `&mut FileStorageAdd<T>` since it implements `StorageAdd` and has access to `Io` internally. However, `FileStorageAdd` does NOT expose the `Io` for reads. So the two-parameter approach is necessary.

    Actually, the cleanest approach: make directory functions that do both read+write take a single `io: &mut impl Io` parameter and construct a local `FileStorageAdd` internally for writes. But `FileStorageAdd::new` takes `&mut Io`, and we also need `&mut Io` for `file_storage_get` — these conflict. So instead, use a temporary `Dictionary` for writes within the function scope, then flush it. Wait, that re-introduces in-memory state.

    SIMPLEST approach: Have mixed-mode functions (add_dir_entry, remove_dir_entry, lookup_dir_entry) take `storage: &mut impl StorageAdd` for writes and `io: &mut impl Io` for reads. In Plan 02, store.rs will acquire the Io lock once, create a FileStorageAdd from it for writes, and pass a separate mutable reference to io for reads. But you can't have two &mut references to the same Io...

    RESOLUTION: The `load_entry_list` internal function needs to read from FileStorage. But `FileStorageAdd` already has `&mut Io`. So we can either:
    1. Read-path uses a SEPARATE Io instance (clone the StoreIo — just another PathBuf wrapper)
    2. Read before creating FileStorageAdd, then write

    Given the constraints, the cleanest approach for THIS plan is: keep load_* functions accepting `&Dictionary` for now (they will be updated in Plan 02 to use `&mut impl Io`). This plan focuses on generalizing the WRITE path only (intern_*) and fixing snapshots. The load_* read path change is coupled to the DictMetadataStore rewrite in Plan 02.

    REVISED approach:
    - intern_* functions: generalize to `&mut impl StorageAdd` (this plan)
    - load_* functions: keep as `&Dictionary` for now (Plan 02 will change them)
    - directory mixed functions (add_dir_entry etc): generalize write param to `&mut impl StorageAdd`, keep read param as `&Dictionary` for now (Plan 02 will update)

    This allows existing code to compile and tests to pass after this plan. Plan 02 handles the full Io migration.

    Update all existing tests in these files to continue passing. The tests use `Dictionary` directly, which implements `StorageAdd`, so they should compile without changes.

    pub fn find_snapshot(&self, reference: &str) -> Option<SnapshotEntry> {
        if let Ok(version) = reference.parse::<u64>() {
            self.snapshots_by_version.lock().unwrap().get(&version).cloned()
        } else {
            let by_name = self.snapshots_by_name.lock().unwrap();
            let &version = by_name.get(reference)?;
            drop(by_name);
            self.snapshots_by_version.lock().unwrap().get(&version).cloned()
        }
    }
