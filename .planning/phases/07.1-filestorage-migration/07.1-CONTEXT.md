# Phase 7.1: FileStorage Migration - Context

**Gathered:** 2026-03-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Switch DictMetadataStore from in-memory Dictionary (BTreeMap<Digest224, Branches>) to file-backed FileStorageAdd/file_storage_get from data-id. Eliminates ~67 GB RAM for 1 TB stores by storing Merkle tree nodes as batched files on the host filesystem. Structurally solves FIX-03/FIX-04 (snapshot O(1) lookup).

No production instances exist — this is a clean break, not a migration.

</domain>

<decisions>
## Implementation Decisions

### Merkle Node Storage
- Use data-id's `FileStorageAdd` to write Merkle tree nodes as **batched files** (~128 nodes per file)
- Each batch file is named by the root node's base32-encoded Digest224
- Files stored under `<backing_store>/vt0/` (top-level roots) and `<backing_store>/vt0/.` (internal batches) — follows data-id's existing convention
- NOT one file per node (would create 500M tiny files for 1 TB — host FS inode exhaustion)
- NOT in-memory (current approach uses ~67 GB RAM for 1 TB)

### Io Trait Implementation
- Create a real filesystem `Io` implementation for SliceFS that wraps the backing store path
- `read()` and `write()` delegate to `std::fs` operations under the backing store directory
- `args()` returns empty iterator (no-op) — SliceFS doesn't use CLI args through Io
- `print()` is a no-op — SliceFS doesn't use CLI output through Io
- No changes to data-id's `Io` trait definition needed

### Dual Consumer Access
- Create one `Io` implementation instance, wrap in `Arc<Mutex<Io>>`
- Shared between `DictMetadataStore` and `SliceFsFilesystem`
- **Remove** `dict: Arc<Mutex<Dictionary>>` from `SliceFsFilesystem` entirely
- Both FUSE reads and metadata ops go through the shared `Arc<Mutex<Io>>`
- `file_storage_get(io, root)` replaces `dict.lock().get(key)` for content reads
- Mutex contention acceptable since disk I/O dominates

### WAL + Segment Strategy
- **No DictEntry records in WAL** — FileStorage files on disk ARE the durable state
- **fsync node files before writing RootUpdate to WAL** — crash-safe ordering guarantee
- Segments now only contain: RootUpdate, RefcountUpdate, SnapshotRecord, InodeMap entries
- If crash occurs after RootUpdate but before node file flush: impossible (fsync ordering prevents this)
- If crash occurs after node file write but before RootUpdate: orphan files are harmless (unreferenced, GC-able)
- Segment compaction strips any legacy DictEntry records

### Legacy Code Removal (No Migration Needed)
- **No production instances exist** — clean break, no migration path required
- Remove DictEntry record type from segment format entirely
- Remove segment replay-into-Dictionary logic
- Remove DictEntry WAL write logic from commit path
- Existing test stores will be re-seeded
- Git history preserves old code if ever needed

### Claude's Discretion
- Exact `Io` implementation details (error handling, path construction)
- Whether `FileStorageAdd`'s batch threshold (currently 0x80 = 128) needs tuning
- How to handle `file_storage_get` failures (corrupt batch file, missing file)
- Whether to add an LRU cache layer later for hot-path reads (start without, measure first)
- fsync strategy details (individual file fsync vs directory fsync)

</decisions>

<specifics>
## Specific Ideas

- User identified that blocks are already stored as files named by hash — the host filesystem IS a hash table. Dictionary should follow the same principle rather than living entirely in RAM.
- data-id already has the implementation (`FileStorageAdd`, `file_storage_get`, `Io` trait) — this is wiring it in, not building from scratch.
- No backward compatibility concerns — no production deployments yet. Clean break preferred.
- Memory estimate for 1 TB at 4KB chunks: Dictionary alone consumes ~67 GB RAM (500M entries × ~135 bytes BTreeMap overhead). With FileStorage, this drops to near-zero (OS page cache for hot nodes).

</specifics>

<code_context>
## Existing Code Insights

### Reusable Assets
- `FileStorageAdd` (data-id/blockset/src/file_storage.rs:14-96) — implements `StorageAdd` via batched disk files, groups ~128 nodes per file
- `file_storage_get` (data-id/blockset/src/file_storage.rs:98-128) — reads file content by walking tree from batched disk files
- `Io` trait (data-id/blockset/src/io.rs:3-13) — read/write/args/print abstraction
- `VirtualIo` (data-id/blockset/src/test_common.rs:28) — test Io impl using in-memory HashMap, pattern for real impl
- `LocalDiskStore` (cas-local/src/disk_block_store.rs) — hash-named files with 2-byte directory sharding, pattern reference

### Established Patterns
- `Dictionary = BTreeMap<Digest224, Branches>` — type alias in data-id, implements `StorageAdd`/`StorageGet`
- `StorageAdd` trait: `add(&mut self, left, right) -> Digest256` + `end(&mut self, x) -> Digest224`
- `StorageGet` trait: `get(&self, key: &Digest224) -> Option<Branches>`
- `FileStorageAdd` uses `vt0/` prefix for top-level, `vt0/.` for internal nodes
- Batch threshold: `map.len() >= 0x80` (128 entries) triggers flush to disk file

### Integration Points
- `DictMetadataStore.dict: Mutex<Dictionary>` (metadata/src/store.rs:48) — primary consumer, must be replaced
- `SliceFsFilesystem.dict: Arc<Mutex<Dictionary>>` (slicefs-cli/src/filesystem.rs:77) — must be removed
- `SliceFsFilesystem::new()` (filesystem.rs:99) — takes `dict: Dictionary` parameter, needs new signature
- `load_store_from_segments()` (metadata/src/segment/mod.rs:54) — currently returns `(Dictionary, ...)`, must change
- All `dict.lock().unwrap()` calls in filesystem.rs (~20 occurrences) — must be replaced with `file_storage_get`
- All `dict.lock().unwrap()` calls in store.rs (~15 occurrences) — must use FileStorageAdd
- `DictMetadataStore::commit()` — currently serializes into in-memory Dictionary, must use FileStorageAdd
- Segment `DictEntry` record type — to be removed
- `compact_segment()` — should strip DictEntry records
- GC, scrub, stats commands — currently access Dictionary directly, must go through Io

</code_context>
