# Phase 7.1: FileStorage Migration - Research

**Researched:** 2026-03-29
**Domain:** Rust — blockset FileStorageAdd/Io trait, DictMetadataStore refactor, WAL segment cleanup
**Confidence:** HIGH — all findings derived directly from reading the existing codebase

## Summary

Phase 7.1 replaces the in-memory `Dictionary` (a `BTreeMap<Digest224, Branches>`) in `DictMetadataStore` with file-backed storage using the existing `FileStorageAdd`/`file_storage_get` API from the `data-id/blockset` crate. This eliminates approximately 67 GB of heap memory for 1 TB stores and structurally satisfies FIX-03/FIX-04 (O(1) snapshot lookup via filesystem path resolution instead of linear scan through an in-memory Vec).

The migration is a clean architectural refactor with no backward compatibility burden — no production deployments exist. The primary challenge is threading a concrete `Io` implementation through all call sites that currently hold `Mutex<Dictionary>`. The secondary challenge is getting the WAL/segment strategy correct: `FileStorage` files on disk become the durable state, so `DictEntry` records in the WAL become vestigial and must be removed. The crash-safety guarantee inverts: instead of "write WAL then update dict", the ordering becomes "fsync node files then write RootUpdate to WAL".

The `Io` trait is a four-method interface (`read`, `write`, `args`, `print`). Two of the four methods are no-ops for SliceFS (`args` returns empty iterator, `print` does nothing). A `SliceFsIo` struct wrapping a `PathBuf` for the backing store root is the only new type that needs to be created from scratch. All other moving parts already exist.

**Primary recommendation:** Create `SliceFsIo`, replace `Mutex<Dictionary>` in `DictMetadataStore` with `Arc<Mutex<SliceFsIo>>`, update all `intern_*` call sites to use `FileStorageAdd`, update all `load_*` call sites to use `file_storage_get`, remove `DictEntry` from WAL/segment format, and re-seed test stores.

## Architecture Patterns

### Recommended Store Layout After Migration

```
<backing_store>/
  segments/              # WAL: RootUpdate, SnapshotRecord, InodeMap, RefcountUpdate
    segment-000001.seg
  vt0/                   # FileStorage top-level node batches (root-to-content)
    <base32-name>        # one file per batch of ~128 nodes
  vt0/./                 # FileStorage internal node batches
    <base32-name>
  mount.lock
```

No `dictionary.bin`, no `vt0/` files in the old format (they didn't exist before this phase).

### Pattern 1: SliceFsIo — The New Io Implementation

**What:** A struct wrapping `PathBuf` (the backing store root) that delegates `read`/`write` to `std::fs::read`/`std::fs::write`.

**When to use:** Constructed once during mount/seed; shared via `Arc<Mutex<SliceFsIo>>`.

```rust
// New file: crates/metadata/src/io.rs  (or crates/slicefs-cli/src/io.rs)
use std::io;
use std::path::PathBuf;
use blockset::Io;

pub struct SliceFsIo {
    base: PathBuf,
}

impl SliceFsIo {
    pub fn new(base: PathBuf) -> Self {
        Self { base }
    }
}

impl Io for SliceFsIo {
    type Args = std::iter::Empty<String>;

    fn read(&mut self, filename: &str) -> io::Result<Vec<u8>> {
        std::fs::read(self.base.join(filename))
    }

    fn write(&mut self, filename: &str, data: &[u8]) -> io::Result<()> {
        let path = self.base.join(filename);
        // Ensure parent directory exists (e.g., vt0/ and vt0/./)
        if let Some(parent) = path.parent() {
            std::fs::create_dir_all(parent)?;
        }
        std::fs::write(path, data)
    }

    fn args(&self) -> Self::Args {
        std::iter::empty()
    }

    fn print(&mut self, _text: &str) {}
}
```

**Confidence:** HIGH — matches `VirtualIo` pattern exactly; `type Args = std::iter::empty()` is standard Rust.

### Pattern 2: Replace Dictionary in DictMetadataStore

**What:** The `dict: Mutex<Dictionary>` field becomes `io: Arc<Mutex<SliceFsIo>>`. All operations that previously called `intern_*(dict, ...)` now call `FileStorageAdd::new(&mut io_guard)` then invoke the `StorageAdd` method, then call `.end()` to get the root `Digest224`.

**Critical insight from reading the code:** The current pattern is:

```rust
// OLD pattern in store.rs (e.g., create_inode):
let mut dict = self.dict.lock().unwrap();
let prev_keys: BTreeSet<Digest224> = dict.keys().copied().collect();
let digest = intern_inode(&mut *dict, &full_meta);
let new_entries: Vec<_> = dict.iter()
    .filter(|(k, _)| !prev_keys.contains(*k))
    .map(|(k, v)| (*k, *v))
    .collect();
// ... then log_new_dict_entries(new_entries)
```

The `prev_keys` / `new_entries` pattern exists solely to collect WAL entries for `DictEntry` records. Since we are removing `DictEntry` from the WAL entirely, this entire diff-tracking pattern disappears. The new pattern is simpler:

```rust
// NEW pattern:
let mut io = self.io.lock().unwrap();
let mut fsa = FileStorageAdd::new(&mut *io);
let digest = intern_inode(&mut fsa, &full_meta);
// No WAL logging of dict entries needed — files on disk ARE the state
```

### Pattern 3: File-Backed Read Path

**What:** All `load_*(dict, digest)` calls are replaced with `file_storage_get(io, digest)` plus deserialization of the returned bytes.

**Critical constraint:** `load_*` functions in the current code take `&Dictionary` and call `GetBytes`/`GetData` to reconstruct data. After migration, `file_storage_get` returns `Option<Vec<u8>>` directly (the raw byte content). The `intern_*`/`load_*` helper functions in `inode.rs`, `directory.rs`, `manifest.rs`, etc. must be updated to accept a generic `StorageGet`-like interface rather than `&Dictionary` directly, OR the `FileStorageAdd` wrapper provides a `get()` adapter.

**Read deeper:** The current `load_inode(&dict, &digest)` calls `GetData::new(dict, &digest256)` then `GetBytes::new(get_data).collect()`. After migration, `file_storage_get(&mut io, digest)` returns the same `Vec<u8>`. The deserialization logic is unchanged — only the source of bytes changes.

### Pattern 4: Crash-Safe Ordering (fsync Before WAL RootUpdate)

**What:** FileStorage writes must be durable before the RootUpdate WAL entry is written.

**Why:** On crash between RootUpdate and node file flush — impossible under the new ordering. On crash after node file write but before RootUpdate — harmless: orphan files exist but are GC-able. On crash after both — clean.

**How:** After `FileStorageAdd::end()` writes the top-level batch file, call `std::fs::File::open(path).sync_all()` or rely on OS durability. Then write RootUpdate to WAL.

**Discretion note from CONTEXT.md:** Exact fsync strategy (individual file sync vs directory fsync) is Claude's discretion. Individual `File::sync_all()` on the batch file written by `FileStorageAdd` is the safest and simplest approach.

### Pattern 5: Snapshot Lookup O(1) Fix (FIX-03 + FIX-04)

**Current code** in `store.rs`:
```rust
// O(N) linear scan — FIX-03 and FIX-04 require O(1)
pub fn find_snapshot(&self, reference: &str) -> Option<SnapshotEntry> {
    let snaps = self.snapshots.lock().unwrap();
    if let Ok(version) = reference.parse::<u64>() {
        snaps.iter().find(|s| s.version == version).cloned()  // O(N)
    } else {
        snaps.iter().find(|s| s.name.as_deref() == Some(reference)).cloned()  // O(N)
    }
}
```

**New pattern** — replace `Mutex<Vec<SnapshotEntry>>` with dual-index:
```rust
// In DictMetadataStore struct:
snapshots_by_version: Mutex<HashMap<u64, SnapshotEntry>>,
snapshots_by_name: Mutex<HashMap<String, u64>>,  // name -> version

// find_snapshot becomes O(1):
pub fn find_snapshot(&self, reference: &str) -> Option<SnapshotEntry> {
    if let Ok(version) = reference.parse::<u64>() {
        self.snapshots_by_version.lock().unwrap().get(&version).cloned()
    } else {
        let by_name = self.snapshots_by_name.lock().unwrap();
        let version = by_name.get(reference)?;
        self.snapshots_by_version.lock().unwrap().get(version).cloned()
    }
}
```

### Anti-Patterns to Avoid

- **Creating `FileStorageAdd` per-call without sharing the `Io`:** `FileStorageAdd<'a, T: Io>` takes `&'a mut T` — it borrows the `Io` mutably for its lifetime. Do not create a new `FileStorageAdd` for reads and another for writes on the same `Io` instance simultaneously. The `Arc<Mutex<SliceFsIo>>` ensures single-threaded access already.

- **Keeping `DictEntry` in WAL as a "backup":** The decision is clear — FileStorage files ARE the durable state. Keeping `DictEntry` in WAL creates a dual-source-of-truth problem that causes correctness bugs on crash recovery.

- **Forgetting to create parent directories in `SliceFsIo::write()`:** `FileStorageAdd` uses paths like `vt0/<base32>` and `vt0/.<base32>`. The `vt0/` and `vt0/./` directories must exist before writing. `create_dir_all` in `write()` handles this idempotently.

- **Keeping `prev_keys`/`new_entries` diff-tracking in store.rs:** This entire pattern exists to log `DictEntry` WAL records. Once `DictEntry` is removed from the WAL, all 7+ occurrences of the `prev_keys` collection can be deleted entirely.

- **Not updating `set_wal()` bootstrap:** `set_wal()` currently logs all existing `dict` entries when a WAL is attached. After migration, this bootstrap loop must be removed (there are no dict entries to bootstrap).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Batched node file storage | Custom batch writer | `FileStorageAdd` (already in `data-id`) | Handles SHA-224 naming, 128-node batching, dedup check (read-before-write), internal vs top-level routing |
| Content-addressed file reads | Custom tree walker | `file_storage_get` (already in `data-id`) | Handles recursive external-node resolution via stack-based traversal |
| Crash-safe file writes | Custom atomic write | `std::fs::write` + `File::sync_all` | OS guarantees atomicity of writes at block level; fsync provides durability |

**Key insight:** `data-id` already solves the hard problem. This phase is plumbing, not invention.

## Common Pitfalls

### Pitfall 1: FileStorageAdd Takes Mutable Borrow of Io

**What goes wrong:** `FileStorageAdd<'a, T: Io>` holds `&'a mut T`. You cannot hold a `FileStorageAdd` reference across a lock drop-and-reacquire. You also cannot create two `FileStorageAdd` instances on the same `Io` simultaneously.

**Why it happens:** The borrow checker enforces single mutable access. The `&mut io` borrow in `FileStorageAdd::new(&mut *io_guard)` ties the FSA lifetime to the lock guard.

**How to avoid:** Create `FileStorageAdd` within a single lock scope, complete the `add()/end()` sequence, drop the FSA, then drop the lock. Never store `FileStorageAdd` in a struct — always construct it locally.

### Pitfall 2: `intern_*` Functions Currently Take `&mut Dictionary`

**What goes wrong:** Functions like `intern_inode`, `intern_manifest`, `intern_xattrs` etc. are written to take `&mut Dictionary`. `Dictionary` implements `StorageAdd` directly. `FileStorageAdd` also implements `StorageAdd`. However, the call sites use `impl StorageAdd` or generic bounds — they must be updated to accept `&mut impl StorageAdd` rather than `&mut Dictionary` specifically.

**Why it happens:** The helper functions were written before `FileStorageAdd` existed as a consumer path.

**How to avoid:** Change `intern_*(dict: &mut Dictionary, ...)` signatures to `intern_*(storage: &mut impl StorageAdd, ...)` (or `intern_*<S: StorageAdd>(storage: &mut S, ...)`). This is a mechanical change.

### Pitfall 3: `load_*` Functions Take `&Dictionary` (StorageGet)

**What goes wrong:** Read-path helpers (`load_inode`, `load_manifest`, etc.) call `GetData::new(dict, &digest256)`. After migration, content lives in FileStorage batch files, not in the in-memory Dictionary. Calling `GetData::new(old_dict, ...)` on a dict that no longer holds the nodes returns empty data.

**Why it happens:** The read path queries the in-memory BTreeMap. After migration, only the Io layer has the data.

**How to avoid:** The `load_*` functions must be updated to use `file_storage_get(&mut io, &digest)` to get the raw bytes, then deserialize. OR: maintain a thin in-memory `Dictionary` only as a read-cache populated from FileStorage on demand. The decision says "start without LRU cache" — so the read path goes directly to disk via `file_storage_get`.

### Pitfall 4: Segment Replay No Longer Restores Dictionary

**What goes wrong:** Current `load_store_from_segments` returns a `Dictionary` built by replaying `DictEntry` records. After this phase, `DictEntry` records are gone. If `load_from_root` still calls `GetData::new(&dict, ...)` to read root record bytes, it will fail because the `dict` is now empty.

**Why it happens:** `load_from_root` uses the Dictionary to reconstruct inode_data, dir_data, etc. by following the Merkle tree from the root digest.

**How to avoid:** After migration, `load_from_root` must use `file_storage_get(&mut io, root)` to fetch the root bytes, then recursively use `file_storage_get` to fetch child nodes. This is the core semantic change in the read path.

### Pitfall 5: Background GC Still References Dictionary

**What goes wrong:** `background.rs::spawn_background_gc` calls `meta.snapshot_roots()` and `meta.dict().lock()` to get the live set for GC. The offline `gc.rs` calls `load_store_from_segments` and passes the returned Dictionary to `GarbageCollector::run_gc(dict, roots)`. After migration, there is no Dictionary to pass.

**Why it happens:** The GC was designed around the Dictionary as the authoritative live-set index.

**How to avoid:** GC's live-set computation (`collect_live_set`) must be rewritten to walk the FileStorage files starting from live roots, rather than scanning an in-memory Dictionary. This is a significant sub-task within the phase.

### Pitfall 6: `DictMetadataStore::new()` Bootstraps Into Dictionary

**What goes wrong:** `DictMetadataStore::new()` calls `intern_inode(&mut dict, &root_meta)` and `create_dir_entries(&mut dict, 1, 1)` to initialize the root directory. After migration, these must write to FileStorage. But `SliceFsIo` requires a backing store path — and during `seed`, the store directory is being created fresh.

**Why it happens:** `new()` currently has no path context; it produces an in-memory store.

**How to avoid:** Update `DictMetadataStore::new(io: Arc<Mutex<SliceFsIo>>)` to take the `Io` at construction time. The `seed` command creates the store directory, then passes the `Io` to `DictMetadataStore::new()`.

### Pitfall 7: `compact_segment` Currently Filters DictEntry by Live Set

**What goes wrong:** `compact_segment()` in `compaction.rs` keeps `DictEntry` records whose key is in `live_set` and drops others. After removing `DictEntry` from the format, this compaction logic operates on a segment that only contains `RootUpdate`, `SnapshotRecord`, and `InodeMap`/`RefcountUpdate` entries.

**Why it happens:** Compaction was designed to prune dead nodes from the WAL.

**How to avoid:** Strip all `DictEntry` handling from `compact_segment`. The function simplifies — it only needs to keep `RootUpdate` and `SnapshotRecord` records (plus any new entry types). `entries_kept`/`entries_removed` stats change meaning.

### SliceFsIo — Complete Implementation

```rust
// Source: models VirtualIo at data-id/blockset/src/test_common.rs:28-50
use std::{io, path::PathBuf};
use blockset::Io;

pub struct SliceFsIo {
    base: PathBuf,
}

impl SliceFsIo {
    pub fn new(base: PathBuf) -> Self { Self { base } }
}

impl Io for SliceFsIo {
    type Args = std::iter::Empty<String>;

    fn read(&mut self, filename: &str) -> io::Result<Vec<u8>> {
        std::fs::read(self.base.join(filename))
    }

    fn write(&mut self, filename: &str, data: &[u8]) -> io::Result<()> {
        let path = self.base.join(filename);
        if let Some(parent) = path.parent() {
            std::fs::create_dir_all(parent)?;
        }
        std::fs::write(&path, data)?;
        // fsync for crash safety — node files must be durable before RootUpdate WAL entry
        let file = std::fs::File::open(&path)?;
        file.sync_all()
    }

    fn args(&self) -> Self::Args { std::iter::empty() }
    fn print(&mut self, _text: &str) {}
}
```

### Snapshot Index — O(1) After FIX-03/FIX-04

```rust
// DictMetadataStore struct fields (replace Vec):
snapshots_by_version: Mutex<HashMap<u64, SnapshotEntry>>,
snapshots_by_name: Mutex<HashMap<String, u64>>,

// set_snapshots:
pub fn set_snapshots(&mut self, snapshots: Vec<SnapshotEntry>) {
    let mut by_ver = self.snapshots_by_version.lock().unwrap();
    let mut by_name = self.snapshots_by_name.lock().unwrap();
    *by_ver = snapshots.iter().map(|s| (s.version, s.clone())).collect();
    *by_name = snapshots.iter()
        .filter_map(|s| s.name.as_ref().map(|n| (n.clone(), s.version)))
        .collect();
}

// find_snapshot — O(1):
pub fn find_snapshot(&self, reference: &str) -> Option<SnapshotEntry> {
    if let Ok(version) = reference.parse::<u64>() {
        self.snapshots_by_version.lock().unwrap().get(&version).cloned()
    } else {
        let by_name = self.snapshots_by_name.lock().unwrap();
        let &version = by_name.get(reference)?;
        drop(by_name);
        self.snapshots_by_version.lock().unwrap().get(&version).cloned()
    }
}
```

## State of the Art

| Old Approach | New Approach | Impact |
|--------------|--------------|--------|
| `dict: Mutex<Dictionary>` (BTreeMap) in `DictMetadataStore` | `io: Arc<Mutex<SliceFsIo>>` with FileStorageAdd writes | ~67 GB RAM eliminated for 1 TB store |
| `DictEntry` records in WAL segment | No `DictEntry` in WAL; FileStorage batch files are durable state | Simpler WAL; crash safety via fsync ordering |
| `load_store_from_segments` returns `Dictionary` | Returns `Option<Digest224>` (last root) + snapshots only | Segment replay now just scans for roots |

## Open Questions

1. **How does GC traverse the live set without an in-memory Dictionary?**
   - What we know: `collect_live_set(dict, roots)` in `gc/mod.rs` currently does a BTreeMap walk
   - What's unclear: After migration, the live set must be computed by walking FileStorage files from live roots. This requires a new `collect_live_set_from_file_storage(io, roots)` function.
   - Recommendation: Implement `collect_live_set` as a DFS over `file_storage_get` calls. This is O(N) disk reads but only runs during GC, not during mount.

2. **Should `DictMetadataStore` keep a thin in-memory Dictionary as a write-buffer?**
   - What we know: `FileStorageAdd` already buffers in-memory until the 128-node threshold, then flushes. This is the correct buffering strategy.
   - What's unclear: Whether additional in-memory caching of hot nodes is needed for read performance.
   - Recommendation: Start without any additional cache (OS page cache covers hot nodes). Measure first if performance regressions are observed.

3. **What happens to `stats.rs` which uses `dict.len()` for `physical_bytes`?**
   - What we know: `physical_bytes = dict.len() * 92` in `stats.rs`. After migration, there is no in-memory Dictionary.
   - What's unclear: How to count physical bytes without iterating the Dictionary.
   - Recommendation: Walk the `vt0/` directory to count files, or remove the metric temporarily. The physical byte count can be replaced with the total size of `vt0/` + `vt0/./` directories.

4. **What happens to `scrub.rs` which iterates `dict.iter()` to verify SHA-224 hashes?**
   - What we know: `verify_dictionary(dict)` iterates all `(key, branches)` entries and re-derives keys.
   - What's unclear: After migration, entries live in FileStorage batch files, not an in-memory Dictionary.
   - Recommendation: Scrub must be rewritten to iterate FileStorage files, deserialize each batch, and verify the hash invariants. This is a meaningful sub-task.
