<objective>
Measure the [Step limit] of plan 21-04: the S7 run must stay under CAP_MIB 320 again at 4 writers, and the memory at the writer counts of the bench (1, 2, 4, 8, 16) is recorded, with the research CAP(N) rule and its 64 MiB stop rule.

Decisions that this plan implements (labels of 21-CONTEXT.md):
- [Step limit]: "The S7 run must stay under CAP_MIB 320 again, at 4 writers and at the worker counts of the bench."
- [Bench]: throughput AND peak memory per worker count; "if 16 scales and memory stays bounded, a later change can raise the default cap of 8". This plan gives the in-process memory part.
- Research Q7 and Open Question 8: keep 320 as the 4-writer cap; `CAP(N) = Pm(N) + F + R`; if Pm(8) is more than one budget (64 MiB) above Pm(4), stop and report before the default cap of 8 ships.

Two readings meet here, and this plan does not choose between them silently. CONTEXT says "under CAP_MIB 320 ... at the worker counts of the bench"; research says "320 is a 4-writer cap; record CAP(N) for more". So: 4 writers are asserted (the harness assert, R1), and a miss there is a hard stop. At 8 and 16 writers a run above 320 (R2) or a rise above 64 MiB (R3) is recorded with its cause and goes to the owner before the default cap of 8 ships (research: "stop and report to the owner before the default cap of 8 ships"); plans 21-06 and 21-07 do not need the answer, so they go on. The S7 process itself holds memory per writer (a 1 MiB block-version model, a 1 MiB write buffer, 1 MiB check reads, a thread stack and its allocator arena), so part of a rise with the writer count is the harness, not the daemon: the notes give that term. The SUMMARY names this point.

Purpose: evidence that peak memory does not grow with the number of writers.
Output: one Docker log and its notes.
</objective>
