<objective>
ROADMAP criterion 5 and POOL-05: "Parallel I/O on different files scales with the number of workers on Linux, and the measured result is recorded." The bar is fixed here before any run.

Decisions that this plan implements (labels of 21-CONTEXT.md):
- [Scale bar] (user answer, 2026-11-23): "POOL-05 passes when throughput at `--workers 4` is at least 1.5x the `--workers 1` value in the Linux Docker bench (parallel I/O on different files). If it misses, the phase records the numbers and the cause, a follow-up issue is opened, and the pool still ships." The follow-up issue is opened by the orchestrator, not by the executor.
- [Bench]: "A Docker Linux run of parallel I/O on different files at 1, 2, 4, 8 and 16 workers, with throughput AND peak memory (VmHWM) per worker count; if 16 scales and memory stays bounded, a later change can raise the default cap of 8 ...; also one macOS CI run at 1 and 2 workers, recorded, to decide whether the macOS default can be raised later."
- [Step limit] (orchestrator reading of the user answer, 2026-11-23): the daemon VmHWM must stay at or under 320 MiB at 1, 2, 4 and 8 workers; 16 is reported only.
- Research Q7 (workload, the trace-off pair, the arena run) and Open Question 7. The metric "write phase or read phase" is the research reading of "throughput"; the SUMMARY names it for the owner.

The bar (stated here, before the runs; do not change it after):
- Metric: aggregate MB/s (16 clients x 64 MiB / wall time) of the sequential write phase and of the read phase, with the trace lines on (the default), median of the 3 runs per worker count.
- PASS: median write(4) >= 1.5 x median write(1), or median read(4) >= 1.5 x median read(1); and every run has 0 content mismatches.
- MISS: neither ratio reaches 1.5 (with 0 mismatches). A mismatch in any run is not a miss: it is a stop (Rule 4).
- Memory bar (orchestrator reading of [Step limit], 2026-11-23): in every run at 1, 2, 4 and 8 workers (trace on and off), vmhwm_a and vmhwm_b are at or under 320 MiB: `mem_bar=pass`, else `mem_bar=miss`. A miss keeps POOL-05 and the [Step limit] item open (plan 21-09 does not mark them); the pool still ships. At 16 workers (above the default cap of 8) the largest VmHWM is recorded as `mem16_max_mib=<v>` and reported to the owner; it does not block. The arena run is not judged.
- Recorded, not judged: the metadata and random-write phases, the throughput at 2, 8 and 16, the trace-off throughput, the largest queue wait.
- Rule for a later rise of the default cap of 8 (recorded only): the median at 16 workers is at least 1.1 x the median at 8 in some phase, and the largest VmHWM at 16 is under CAP(16) of plan 21-06.

Purpose: the scaling claim rests on a bar that was set first.
Output: the bench scripts and workflow, lock rows at unmount for a lock-stats build, the bench log and its notes.
</objective>
