<objective>
ROADMAP criterion 3: "A worker panic aborts the daemon; the next mount replays the write log, and no request is served after a half-done update." This also fixes a gap that research found in the code today, with one thread too: a panic on the fuser reader ends the session with an error, fuser drops its `FilesystemHolder`, and that drop runs `destroy()`, which commits the half-done state (research Q4).

Decisions that this plan implements (labels of 21-CONTEXT.md):
- [Panic]: "A panic in a worker aborts the process (`std::process::abort` from a catch or a panic hook for worker threads); no reply is sent for the half-done request; the next mount replays the write log. A test shows a remount after an injected worker panic gives the replayed state." The panic hook is the mechanism (research Q4: a `catch_unwind` runs after the unwind, which drops the no-poison locks and sends EIO through `ReplyRaw::drop`).
- [Waits]: the submit limit of 21-01 ends in an abort; this plan tests that path (research Open Question 1).
- Research Open Question 2 (Claude's discretion, reversible): only request threads abort; the flusher, the GC and the commit timer keep the Phase 20 behaviour. Plan 21-08 lists "abort on a flusher panic too" as a deferred item.

Purpose: no request is ever served on a half-done update, and no half-done update is committed.
Output: `install_abort_hook`, child-process tests, a debug-only injection, a live-check block and its Docker log.
</objective>
