<objective>
Run the layout and constants benchmark on the real matrix and take the decision by the pre-registered rules (PMAP-01, D-02, D-03, D-05, D-08). The owner delegated both choices ("Test both, then decide"); the rules are in `scripts/prolly-bench/decide.py` since plan 25-06, and they are repeated here word for word:

- Rows. "Small" rows: for each source (Boost; synthetic 1M; synthetic 10M) the K=1 row (Boost `scatter` k=1, synthetic `one`) and the K=100 row (Boost `scatter` k=100, synthetic `mixed` k=100): 6 rows. "Large" rows: per source the K=1,000 row (Boost `scatter` k=1000, synthetic `mixed` k=1000) and the insert/delete row (`insdel` k=1000): 6 rows. Per row and layout the value is the median over its commits; nodes = nodes_read + nodes_written; CPU = cpu_user_s + cpu_sys_s.
- Layout (decided at the Dolt config 4096/16384): an arm X in {b, c} qualifies against a iff the mean over the small rows of nodes(X)/nodes(a) is at most 0.80, the mean over the small rows of CPU(X)/CPU(a) is at most 1.25, the largest bytes_written(X)/bytes_written(a) over the large rows is at most 1.10, and the 1B node count of X is not larger than that of a. If both qualify, take the lower node ratio; within 0.02 of each other, take c. If none qualifies, take a.
- Constants (for the chosen layout): N1B(C) = the 1B node count; W(C) = the mean of the median bytes_written over the rows synthetic 10M `one`, synthetic 10M `mixed` k=100 and Boost `scatter` k=1; T(C) = the same mean of the median CPU; F(C) = forced cuts / nodes of the 10M base build. A config is eligible iff F(C) <= 0.005. A config C other than Dolt D (4096/16384) replaces D iff it is eligible, N1B(C) <= 0.65 x N1B(D), W(C) <= 2.5 x W(D) and T(C) <= 2.0 x T(D). If more than one qualifies, take the smaller NODE_MAX, then the smaller N1B. Else keep D.
- 1B extrapolation (D-05), per tree, from the synthetic 10M base build: entries per leaf e = entries / leaves; fanout f = leaves / (nodes of level 1); entries scaled by 1,000,000,000 / n; leaves' = ceil(entries' / e); each level above = ceil(previous / f) until 1; nodes = the sum; depth = the number of levels.

Why these numbers (planner's confirmation of RESEARCH A2, as the orchestrator asked): a one-change commit touches three maps (inode, manifest, refcounts); layout b/c can save at most about one path in three (the inode and manifest records of a file share a leaf), so a real gain is near 25-33% and 20% is the smallest gain worth the cost of a combined key space (a kind dispatch in the GC mark, per-kind range counts); 1.25 on CPU allows for the noise of a shared host (ten commits of a few ms per row, rows at different times), while a real CPU regression of the combined key would be larger; 1.10 on bytes guards the large commits where adjacency helps least. For the constants, each node is one chunk-index object (D-08), so a 35% smaller node count at 1B is worth up to 2.5x bytes and 2x CPU on a small commit, which stay a few hundred KB and a few ms and do not touch the PMAP-07 goal; the forced-cut limit keeps the "boundaries depend on keys only" property.

Task 1 (tracer) runs the real path end to end on a pilot: the Docker case with the real Boost data, one Boost row and one synthetic 1M row, and records the pre-registration commit and the time per row. Task 2 runs the full matrix (the pilot rows are reused). Task 3 runs the decision, checks determinism and writes the owner report into the SUMMARY.

Decisions this plan implements: D-02 (the test), D-03 (the layout, by the rule), D-05 (the extrapolation result), D-08 (the constants, by the rule). Plan 25-08 pins the constants and writes the doc.

Purpose: ROADMAP criterion 1 (decided by a test) and criterion 3 (the constants of the rule).
Output: `runs/layout/*` and the owner report in the SUMMARY.
</objective>
