## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Header file
- [Header] Keep the existing text marker `<store>/FORMAT` (`crates/slicefs-cli/src/content.rs`) and grow it into the header. Text, one item per line, so a person can read it and an error can name a flag. It stays written durably (synced temp file, rename, directory sync) as `write_marker` does today.
- [Number] The first line becomes `slicefs-store 7 ...`. Reason: a format-6 binary ignores unknown lines, so it would ignore an incompat flag. The number change makes every older binary refuse a format-7 store. A format-6 store is refused with the existing "made by an older SliceFS" message (no migration, as decided).
- [Flags] Three line kinds, for example `compat <name> <release>`, `ro_compat <name> <release>`, `incompat <name> <release>`: a flag is a short kebab-case name plus the lowest release that knows it. So an old binary can name both in its error ("needs SliceFS <release> or later"). The exact line syntax is the planner's choice, documented.
- [Parse order] (review 2026-11-24) Read all lines; check the incompat and ro-compat flags first, so an old binary names the flag that stops it; only after that is an unknown line kind an error. Rule for later phases: a new setting line always comes with a flag.
- [Number parse] Parse the format number from the first line (`slicefs-store <n> ...`); do not compare the whole first line as today (`starts_with(FORMAT)`).
- [Hash line] The `hash <name>` line stays a store setting (not a flag) in this phase. Phase 23 decides whether a new hash also adds a flag.
- [Initial flags] Format 7 starts with an empty flag list. Tests use test-only flag names (for example written by a test helper) to prove the three rules; no fake flag ships.
- [Release numbers] Do not write a real release number in the doc, the messages or the tests: the tag name for this milestone is still open with the owner. Tests use test-only values. The policy states that the format is not frozen yet.

#### Open rules
- [Durable first] For a new store the header is written durably before `packs/` or `segments/` exist, so a crash cannot leave data with no header.
- [New store] The header is written only when the store is new: no `packs/` data and no `segments/` (or the directory is missing or empty). Today `content::open` writes a marker for any store without one; that changes: a store with data and no header is refused with a clear message that names the missing file.
- [Incompat] Any unknown incompat flag: refuse every command that opens the store (mount, gc, stats, scrub, snapshot, seed into an existing store). The message names the flag and its release.
- [Ro-compat] Any unknown ro-compat flag:
  - `mount` mounts read-only (FUSE `RO`) and prints one line that names the flag and why;
  - in that mode the daemon writes nothing to the store: no write-log replay, no flusher, no commit timer, no online GC, chunk store and index opened read-only (the `read_only` open of `Index::open` exists);
  - if the write log has records to replay, refuse the mount (a newer binary must replay them) with a message that says so;
  - commands that write (gc, seed, snapshot create) refuse; read commands (stats, scrub without repair) run.
- [Compat] Unknown compat flags are kept as they are when the header is written again (for example by `select_hash`), never dropped.
- [Where] One module owns the header (parse, write, check). The check runs at the open points, not in each command: inside `content::open`, `open_read_only`, `store_io` and `store_io_read_only`, and before anything writes (today `select_hash` in `mount.rs` ~101 and `seed.rs` ~38, and `create_dir_all` in `open`, write before `check_format` runs). Today `check_format` is called by mount, gc, stats and scrub only; `snapshot.rs` (create, list, switch: lines ~64 and ~161) calls `store_io` with no check. `stats` and `scrub` already open read-only (`store_io_read_only`). The planner picks the module and the crate.
- [Mount lock] `mount.lock` (`crates/metadata/src/mount_lock.rs`) is a file in the store root that marks a mount in progress; a lock left by a crash triggers write-log replay. It is crash detection, not exclusion. A ro-compat (read-only) mount does not create it. If it exists at a ro-compat mount (a crash, or a writer daemon now running), the mount is refused (a newer binary must replay first).
- [Ro tracer] The read-only mode must be proved in the daemon, not only by FUSE `RO` (the kernel gives EROFS as soon as `RO` is set; snapshot mounts set it today and still reuse the writable store handle). Tracer and must-have: an in-process test (runs on macOS CI too) that opens a store with an unknown ro-compat flag through the mount path's own setup, reads files, and shuts down as `destroy` does; the store tree is then unchanged (file list, sizes, content hashes). It must be red with only `RO` set. Expected write paths to close: the commit in `destroy`/`shutdown`, the write-log segment open, the `gc-tmp` cleanup of a writable open, index rebuild or flush, the marker rewrite in `select_hash`, `auto_snapshot`, atime updates, and `mount.lock`.

#### Output
- [Stats] `slicefs stats` prints the format number and each flag set (with `--json`, as fields).
- [Doc] `docs/design/store-format.md`: header layout with an example, the three classes and what an old binary does with each, the flag list (empty now, with the rule for adding one), every error message, and the format policy: the format number changes only when an old binary cannot parse the header safely; any other change adds a flag; the format number is separate from the release number. The README gets one line and the link.

## Summary

SliceFS has one text marker today, `<store>/FORMAT`, owned by `crates/slicefs-cli/src/content.rs`. Its first line is `slicefs-store 6 (...)`, an optional second line is `hash <name>`, and the check is a whole-prefix compare (`starts_with(FORMAT)`) [VERIFIED: crates/slicefs-cli/src/content.rs:25-34, 120-123]. `content::open` writes a marker for any store that has none, even one with data [VERIFIED: content.rs:154-159]. The phase grows this file into a header (format 7, three flag classes) and moves all checks into one function that every open point calls first.

The hard part is the read-only daemon. Today a snapshot mount only pushes `MountOption::RO`; it still takes `mount.lock`, opens a new write-log segment, opens the chunk store writable (which removes `gc-tmp/`), runs the commit timer and the segment GC thread, and `destroy` still commits and closes the store [VERIFIED: crates/slicefs-cli/src/mount.rs:77-116, 356-387, 450-470; filesystem.rs:5253-5282]. Spike 1 (below) ran the mount path's own `load_store` + reads + `shutdown()` in process and showed the tree changes: `gc-tmp/` removed, `segment-000001.seg` and `-000002.seg` deleted, `-000003.seg` and `-000004.seg` created. A second spike opened the same store with `content::store_io_read_only`, no WAL and no lock, then read and called `shutdown()`: the tree did not change, and the commit failed as a backstop (`commit_ok=false`). So the read-only mode is small: one `Access` value chosen by the header check, which selects the read-only load path and gates the replay, the four background threads, `destroy`'s commit, and the `RO` mount option.

**Primary recommendation:** Add one module `crates/slicefs-cli/src/header.rs` (parse, write, check, `Access`). Split `run_mount` into `mount::start` (everything after the mountpoint and backend checks, before `fuser::mount`) and `Started::stop`, so a unit test in `mount.rs` can run the real setup, read, call `fuser::Filesystem::destroy` on the real `MountedFs`, stop, and compare the store tree. Make that test the tracer (plan 21.1-01).

### How the snapshot mount differs today

`run_mount` calls `load_store` before it looks at `snapshot_ref` (`mount.rs:352`). So a snapshot mount gets every write of W1-W8 and W12-W14; it only skips W9-W11. It reuses the writable `io` (`mount.rs:361, 378`) and adds `MountOption::RO` (`mount.rs:365, 382`). `destroy` commits the snapshot's metadata store: that store has no WAL (it was loaded fresh, no `set_wal`), so no root is logged, but the commit still puts nodes and `content.close()` seals the active pack.

### Proposed wiring: one flag from the open decision

```rust
// crates/slicefs-cli/src/header.rs (sketch; names are the planner's choice)
pub enum Want { Read, Write, Mount }          // what the caller will do
pub enum Access { ReadWrite, ReadOnly(Flag) } // the decision; Flag = the first unknown ro_compat flag
pub struct Opened { pub header: Header, pub access: Access }
/// The one check. Reads FORMAT (bounded). A new store with `Want::Write`
/// or `Want::Mount` gets a format-7 header first (durable). Refuses: no
/// header with data, another format number, a bad line, an unknown
/// incompat flag; an unknown ro_compat flag with `Want::Write`.
pub fn check(store: &Path, want: Want) -> std::io::Result<Opened>;
```

Carry `Access` (one value) from `mount::start`:

1. `let opened = header::check(store, Want::Mount)?;` before `load_store` (so before W3).
2. `ReadWrite`: today's `load_store` (keep its signature; about 25 test calls use `(meta, _io, _lock)`).
   `ReadOnly(flag)`: a new `load_store_read_only(store) -> (DictMetadataStore, Arc<Mutex<StoreIo>>)`:
   refuse if `mount.lock` exists (M8); refuse if `scan_store_with_log(segs)?.2.len() > 0` (M7); `load_store_from_segments`; `content::store_io_read_only`; `load_from_root`; `set_snapshots`; no WAL, no lock. Print the one line M6.
3. `let writable = opened.access.is_read_write() && snapshot_ref.is_none();` replaces the three `snapshot_ref.is_none()` gates (`mount.rs:412, 429, 437`) and also gates W12 and W13.
4. `fs.set_read_only(true)` when the access is `ReadOnly` (W14). Do not set it for a snapshot mount of a writable store: that keeps today's snapshot behaviour (scope guard; see Open Question 2).
5. Push `MountOption::RO` when `ReadOnly` or a snapshot.

`mount::start` holds steps 350-470 of today's `run_mount` (after the mountpoint check at 323 and the macOS backend choice at 332-341, which need the `mount` binary and FUSE-T). ## Q6. Header grammar (format 7), parse order, write order, messages

### Layout

```
slicefs-store 7 (store header with feature flags)
hash blake3-256
compat <name> <release>
ro_compat <name> <release>
incompat <name> <release>
```

Grammar (ASCII, `\n` line ends, the file ends with `\n`):

```
header     = first-line *( line )
first-line = "slicefs-store" SP number [ SP free-text ] LF   ; free text is ignored
number     = 1*DIGIT                                        ; no sign, no leading "+"
line       = flag-line / hash-line / other-line
flag-line  = class SP name SP release LF
class      = "compat" / "ro_compat" / "incompat"
name       = 1*64( lower-alnum / "-" ), starts and ends with lower-alnum, no "--"
release    = 1*32( VCHAR except SP )                        ; opaque: shown, never compared
hash-line  = "hash" SP hash-name LF                         ; a store setting, not a flag
other-line = word *( SP token ) LF                          ; a setting this build does not know
```

Rules:
- Bounded read: read at most 64 KiB (`File::take(65_537)`); more is an error (M10). Not UTF-8 is an error.
- The release token is shown in messages only. It is never parsed or compared, so the tag name stays open.
- One flag name appears once in the whole header (not in two classes). One `hash` line at most.
- Flags this build knows: `KNOWN_FLAGS: &[&str] = &[]` (empty in format 7). Tests write unknown, test-only names; no fake flag ships.

### Parse order (one function, in this order)

1. Read the file (bounded). Missing file → step "new store or refuse" (below).
2. First line: `slicefs-store <n>`. Not that shape → M4 (unknown format). `n < 7` → M2 (older; keep the existing texts for 4 and below "metadata in vt0/", 5 "224-bit object IDs"; add 6 "no feature flags"). `n > 7` → M3 (newer). Stop here: another number can have any layout.
3. Read every other line. Split on single spaces. Collect flag lines (first word is a class). A flag line with a bad shape or name → M9 naming the line. Duplicate flag → M9.
4. Unknown `incompat` flags → refuse (M5, names every unknown incompat flag with its release).
5. Unknown `ro_compat` flags → `Access::ReadOnly(first such flag)`; with `Want::Write` → refuse (M6w).
6. Only now the other lines: `hash` is checked as today (`write_hasher`, `content.rs:46-58`). Any other line kind is an error (M9, `unknown setting`). This is the locked rule of CONTEXT [Parse order]: flags first, so the error names the flag when there is one; then an unknown line kind is an error.

Cost of the locked rule (see Open Question 1): when a later feature adds a new setting line, an old binary refuses the store at step 6 even if the feature's flag is `ro_compat` or `compat` (it passes steps 4-5, then meets the unknown line). So with this rule a feature that adds a line is in effect `incompat` for old binaries, whatever its class. The class still matters for features that add no header line (for example a new record kind in packs).

Rewrite (`select_hash`): only a header that passed all six steps is rewritten, so its lines are `hash` and flag lines; every flag line (compat ones included, known or not) is written back in its order; only the `hash` line changes.

### New store or refuse (header missing)

"Has data" = `packs/` has any entry or `segments/` has any entry (a missing or empty directory is no data). Then:
- has data → refuse (M1), any `Want`;
- no data, `Want::Write` or `Want::Mount` → write the header (below), then go on;
- no data, `Want::Read` → no write; report an empty, header-less store as "no store here yet" (stats prints format `none`); see Open Question 3.

Note: `mount` already needs `segments/` (`mount.rs:67-72`), so a mount never meets a new store in practice; `seed` and the test builders do.

### Durable write order for a new store

1. `create_dir_all(store)`.
2. Write `FORMAT.tmp` with the full text, `sync_all`.
3. `rename(FORMAT.tmp, FORMAT)`.
4. `File::open(store)?.sync_all()` (the directory entry is durable).
5. Only now open the chunk store (it creates `packs/` and `index/`, `pack_io.rs:386-387`) and the segments.

This is `write_marker` (`content.rs:93-103`) with a new body. Since step 4 comes before any `packs/` or `segments/` entry, a crash cannot leave data with no header. A rewrite (`select_hash`) uses the same four steps and writes back every flag line in its order (rule above); only the `hash` line changes. So the signature changes from `write_marker(store, hasher)` to `write_header(store, &Header)`.

### Comparison with ext4

ext4 has three feature masks in the superblock [CITED: kernel.org/doc/html/latest/filesystems/ext4/super.html]:
- `s_feature_compat`: "Kernel can still read/write this fs even if it doesn't understand a flag".
- `s_feature_ro_compat`: "If the kernel doesn't understand one of these bits, it can still mount read-only."
- `s_feature_incompat`: "If the kernel or fsck doesn't understand one of these bits, it should stop."

The SliceFS classes copy these meanings. Differences: SliceFS flags are named text lines with a release token (so the error names the flag and the release; ext4 has only bit numbers); and SliceFS also has a format number for changes to the header layout itself. ext4 lists "Filesystem needs recovery (INCOMPAT_RECOVER)" as an incompat bit [CITED: same page]. In ext4, a read-only mount of a file system whose journal needs recovery still replays the journal, unless the device is read-only or `noload` is given [ASSUMED]. SliceFS takes the strict path: a read-only (ro-compat) mount never replays; it refuses (M7, M8), because the replay writes and the old binary cannot write this store.

### Anti-Patterns to Avoid
- **Only `MountOption::RO`:** the kernel stops writes from users, but the daemon still writes (spike 1). Always switch the daemon mode too.
- **A check in each command:** the CONTEXT wants one function at the open points. A command only says `Want::Read` or `Want::Write`.
- **Checking after a write:** `load_store` writes `mount.lock` before the first open point (`mount.rs:77-88` vs 101/103), and `gc_report` writes `gc.request` before `check_format` (`gc.rs:92-98`). Put the check first.
- **Comparing the whole first line:** `starts_with(FORMAT)` (`content.rs:77, 121`) breaks when the free text changes. Parse the number.
- **Parsing the release token:** it is opaque; a compare would need the tag scheme, which is open.
- **Reading `FORMAT` with `read_to_string` unbounded:** use a bounded read.
- **Relying on timing in the tracer:** assert that the threads were not started (a field of `Started`), not that no file appeared within some time.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Durable header write | a new write routine | the steps of `write_marker` (`content.rs:93-103`) | Already correct: temp, sync, rename, dir sync. |
| Pending-log detection | a new segment scan | `segment::scan_store_with_log` + `WriteLog::len` | Same logic as the replay; bounded memory. |
| Read-only chunk store | new guards in pack/index code | `Options { read_only: true }` via `content::store_io_read_only` | Every write site in `open_with`/`load`/`Index::opened`/`rebuild`/merges already checks it; `put` fails. |
| No-WAL metadata store | a fake WAL | no `set_wal` (or `WalConfig::NoWal`, `wal/mod.rs:430`) | `flush_wal`/`shutdown_wal` are Ok with no WAL (`store.rs:594-614`). |
| In-process destroy | a copy of destroy logic in the test | `fuser::Filesystem::destroy(&mut MountedFs)` as in `fuse_callbacks.rs:1119` | Tests the real path. |

## Common Pitfalls

### Pitfall 1: a transient write the diff cannot see
**What goes wrong:** `mount.lock` is created and removed; `gc-tmp` cleanup of a missing directory leaves no trace. A before/after diff passes.
**How to avoid:** a snapshot after setup and reads (before `destroy`), and bait files (`gc-tmp/bait`). Spike 1 shows both are needed.

### Pitfall 2: commit "succeeds" with no visible pack change
**What goes wrong:** a commit with no change de-duplicates all nodes, so `packs/` stays the same; only the segment rotation shows.
**How to avoid:** hash every file under `segments/` too, and compare names (files deleted and created).

### Pitfall 3: header check placed after the first write
**What goes wrong:** `load_store` takes the lock at `mount.rs:77`, `select_hash` creates the store dir at `content.rs:74`, `seed` creates it at `seed.rs:37`, `gc` writes `gc.request` at `online_gc.rs:313`.
**How to avoid:** call `header::check` as the first statement of each of these.

### Pitfall 4: an empty `segments/` from a test is "data"
**What goes wrong:** many tests do `create_dir_all(store/segments)` before the first open; if "has data" means "segments/ exists", every such test breaks.
**How to avoid:** "has data" = the directory has an entry, not "the directory exists" (CONTEXT [New store]).

### Pitfall 5: `load_store` signature churn
**What goes wrong:** adding a return value breaks about 25 test call sites that destructure `(meta, _io, _lock)`.
**How to avoid:** keep `load_store` for read-write; add `load_store_read_only` and choose in `mount::start`.

### Pitfall 6: snapshot mount semantics change by accident
**What goes wrong:** reusing the new gates could make a snapshot mount of a normal store skip the lock or the commit timer, or set the `read_only` flag.
**How to avoid:** `writable = access.is_read_write() && snapshot_ref.is_none()` only replaces existing snapshot gates; `fs.set_read_only` only for `Access::ReadOnly`. (Or decide Open Question 2.)

### Pitfall 7: the Docker VM runs out of memory
**What goes wrong:** a parallel build in the low-memory VM fails, and the run script stops.
**How to avoid:** `-j 1`; check `build-exit=0` in the committed log.

// Sources: mount.rs:91-108, content.rs:182-184, segment/mod.rs:129, 225
pub fn load_store_read_only(store: &Path, flag: &Flag)
    -> Result<(DictMetadataStore, Arc<Mutex<StoreIo>>), Box<dyn std::error::Error>> {
    if store.join("mount.lock").exists() { return Err(msg_lock_present(store, flag).into()); }
    let segs = store.join("segments");
    let (root, snapshots, log) = metadata::segment::scan_store_with_log(&segs)?;
    if !log.is_empty() { return Err(msg_log_pending(store, log.len(), flag).into()); }
    let root = root.ok_or_else(|| format!("no committed state found in segments at {}", segs.display()))?;
    let io = Arc::new(Mutex::new(crate::content::store_io_read_only(store)?));
    let mut meta = DictMetadataStore::load_from_root(io.clone(), &root)?;
    meta.set_snapshots(snapshots);
    Ok((meta, io)) // no WAL, no lock
}
```

fn tree(root: &Path) -> BTreeMap<String, String> {
    let mut out = BTreeMap::new();
    let mut todo = vec![root.to_path_buf()];
    while let Some(d) = todo.pop() {
        for e in std::fs::read_dir(&d).unwrap() {
            let p = e.unwrap().path();
            let rel = p.strip_prefix(root).unwrap().display().to_string();
            let m = std::fs::symlink_metadata(&p).unwrap();
            if m.is_dir() { out.insert(format!("{rel}/"), String::new()); todo.push(p); continue; }
            let mut f = std::fs::File::open(&p).unwrap();
            let (mut h, mut buf) = (blake3::Hasher::new(), vec![0u8; 64 << 10]);
            loop { let n = std::io::Read::read(&mut f, &mut buf).unwrap(); if n == 0 { break } h.update(&buf[..n]); }
            out.insert(rel, format!("{} {}", m.len(), h.finalize().to_hex()));
        }
    }
    out
}
```

## Open Questions

1. **Unknown setting lines next to an unknown flag (parse order).** What we know: CONTEXT locks "flags first, then an unknown line kind is an error", and "a new setting line always comes with a flag"; Q6 step 6 implements exactly that. What is unclear: the cost. With this rule, a later feature that adds a setting line makes every old binary refuse the store, even if its flag is `ro_compat` or `compat` (it is in effect `incompat`). Proposal (not in the plans unless the owner agrees): when any flag is unknown, keep unknown lines as they are and let the strongest unknown flag class decide (refuse / read-only / read-write); an unknown line is an error only when every flag is known. Then a `ro_compat` feature that adds a line still mounts read-only on an old binary, and a rewrite must also keep unknown lines. This matters for Phases 22 and 23 (the chunk profile would be a new setting line). Reversible before the format freeze.
2. **Snapshot mounts.** A snapshot mount of a normal store still writes (W1-W8, W12-W14). Recommendation: keep it as is in this phase (scope); with the `Access` wiring, making it read-only in the daemon is a one-line follow-up (`fs.set_read_only` and the read-only load). With an unknown ro_compat flag, `--snapshot` uses the read-only path. Owner may want the follow-up as an issue.
3. **Read command on an empty store with no header (A4).** `stats` of an empty `segments/` passes today (`stats.rs:363-377`). Recommendation: no write, format shown as `none`; JSON `"format": null`.
4. **`--hash` / `--auto-snapshot` on a ro-compat mount (A3).** Recommendation: refuse with one line each (the user asked for a write that cannot happen).
5. **`gc` while a newer binary has the store mounted.** With a ro_compat flag, `gc` is a write command and is refused by the header check before it looks at `mount.lock` (so no `gc.request` is written). Recommendation: as stated; no owner call needed.
6. **Daemon-level EROFS.** With `RO`, the kernel stops writes. If a platform ever passed a write through, the read-only chunk store fails `put` (EIO), and metadata changes stay in RAM and are lost at unmount (no commit). Recommendation: no per-handler EROFS in this phase; note it in the doc.
