   Results of the on-disk chunk index.

   The chunk store now keeps its index on disk: sorted runs of (ObjectId, Loc) in 4 KiB pages, one 8-byte fence per page and one Bloom filter (10 bits per key) per run in RAM, a memtable for new entries, a MANIFEST, and size-tiered merges on a background thread. The pack and .idx files did not change and stay the source of truth. Design: docs/design/chunk-store.md, section "Index on disk (#85)".

   Measured with benchmarks/index-bench (the #66 tool), warm cache, median of 3, commit {{commit}}, {{machine}}:

   | Objects | RAM B/object, new (steady) | RAM B/object, #66 | Open s, new | Open s, #66 | Hit ns, new / #66 | Miss ns, new / #66 | Create puts/s, new / #66 |
   |---|---|---|---|---|---|---|---|
   | (one row each for 1M, 10M and 100M on macOS, from the doc tables) |

   - Marginal RAM per object (10M to 100M): about {{marginal}} B. The rest is fixed (the memtable and the process).
   - Open reads only the MANIFEST, the run footers, tables and filters, and the records above the high-water mark. It does not read the entries.
   - A hit reads one 4 KiB page; a miss usually reads none (test hits_read_one_page_and_misses_read_almost_none).
   - Crash tests (in-process, no mount): a crash during a run flush or a merge loses no object and gives no wrong Loc (tests/index_crash_tests.rs).
   - GC tests: no lookup, and no put dedup check, returns an object that online GC removed, also after reopen and merges (tests/gc_tests.rs, tests/gc_fault_tests.rs).
   - GC reads its decisions from a run snapshot without the store lock; the longest lock hold of a GC with 3 of 4 objects live was {{gc lock 10m}} ms at 10M and {{gc lock 100m}} ms at 100M objects. A read error or a damaged page in a GC changes nothing (tests/gc_fault_tests.rs, src/race_tests.rs).
   - All tables, Linux included: docs/design/chunk-store.md, section "Index results (#85)".

   Follow-up issues: {{locality issue}} (a locality cache) and {{gc ram issue}} (RAM of the GC mark set).

   The acceptance items of this issue are met, so this issue is closed.
