**The two Phase 19 races**
- **D-26:** Fix both in this phase. Each fix starts with a test that fails before the fix. A deterministic form is preferred: a test-only pause hook (cfg(test) or a test feature) that holds one thread inside the window. Then the fix. Then a model or stress test that stays in CI.
- **D-27:** Race (a), one root and two windows (Phase 19 deferred items, 19-09 and 19-10): `setattr_size_closed` (`filesystem.rs`) changes the size of a closed file under the transient cell only, with no stripe. Window 1: an unlink reclaims the inode meanwhile, so a manifest entry and one refcount of the deleted inode remain, and the setattr returns EIO. Window 2: a setattr of other fields of the same inode shares no lock with it, so the two inode writes and their records can be in opposite orders and replay gives another mtime. The stated fix direction: re-check the inode under its stripe before the install; the install step must move out of the cell hold (a stripe is rank 3, below the cell at rank 4). Research confirms. Both windows get a test.
- **D-28:** Race (b): cross-directory rename has no ancestor check (19-CONTEXT Deferred, 19-RESEARCH: `simulate_rename` has no "source is an ancestor of target" check; the rename mutex, rank 2, is where it belongs). Fix: under the rename mutex, walk the parents of the target directory; if the source directory is on that path, return EINVAL. Research checks what the Linux kernel and FUSE-T already serialize or check for FUSE, so the failing test reaches the daemon path (an in-process test, not only a mount test). The fix goes in the daemon in any case.
- **D-29:** Fallback: if one race cannot be fixed in this phase, the Linux default becomes `--workers 1` (`default_workers` in `pool.rs`), and the issue stays open. Record which race and why.

**Deadlock-detect stress**
- **D-30:** Linux job, short. It runs `tests/stress_harness.rs` with `--features deadlock-detect` and several workers, with a wall-clock limit. ## Summary

Four of the six tools work on this code base with small changes, and two need design work. **loom** runs the real `pool.rs` after a pure import swap and finishes exhaustive searches of small configurations in under a second to 50 seconds (numbers below). **TSan** (nightly-2026-02-11, `-Zbuild-std`) builds and runs `pool_tests`, `multi_handle_posix`, `lock_free_io`, `dirty_budget_tests`, `flusher_tests` and a 10 s stress run with zero TSan reports on the Mac target. **Kani 0.68.0** installs and proves arithmetic and byte-level code in seconds, but the header parser as written (`str::contains`, `split`, `strip_prefix`, `parse`) does not finish in 120 to 150 s, so the pure-core split of D-23 is a plan task. **Miri** cannot run any test that reaches a chunk-store or metadata `unsafe` block today: file mmap, `madvise`, `fallocate`/`fcntl` punch hole and `getgid` are unsupported, and the zstd C library (`ZSTD_createCCtx`) aborts every test that compresses data. Miri still runs 71 of 127 chunk-store tests and 56 of 166 metadata tests (UB and data-race screening of the lock shim, index, run and WAL logic), and one new test-only anonymous mapping reaches `from_raw_parts` and `munmap`. All other `unsafe` goes to the review doc.

The two races are real in the code and have a common cheap fix that reuses an existing pattern: `open_logged` already takes `stripe(ino)`, counts the open, and releases the stripe before the cell work, so an unlinked inode stays an orphan (`filesystem.rs:4967-4985`). The closed-file size change should do the same: claim under the stripe (inode exists, transient cell inserted, open count +1), release the stripe, splice and install under the cell as today, then release the count with `uncount`. Race (b) needs one walk of `..` entries under the rename mutex. Both failing-first tests exist without a new hook: `rebase_hook` already sits between the splice and the install (`filesystem.rs:4186-4189`), and the ancestor test is single-threaded. On a Linux kernel mount the VFS probably serializes both races before the daemon sees them `[ASSUMED]`, so the fix matters most for FUSE-T/FSKit and in-process callers; the plan stays the same.

**Primary recommendation:** Use **loom (bounded, `LOOM_MAX_PREEMPTIONS=3`) on pinned stable** for three small models built on real code through a cfg(loom) backend of `chunk_store::sync` plus a `sync::raw` re-export module for the std primitives; run **Miri on a named allow-list** (no `-Zmiri-disable-isolation` for chunk-store, with it for metadata); run **TSan on the named set** plus a 10 s stress run; prove **Kani on a byte-level pure core**; and fix race (a) with the claim-under-stripe pattern and race (b) with an ancestor walk.

          +--> kani   (ubuntu, Kani 0.68.0) -> cargo kani -p slicefs-cli --lib   (harnesses in #[cfg(kani)] modules)

          +--> coverage (ubuntu, Docker harness) -> cargo llvm-cov (tests) + instrumented FUSE checks -> report, floor gate
          |
          v
   each job prints what it checked (test names, proof names, coverage numbers); non-zero exit fails the workflow
```

Data flow of the models: a loom test (`#[cfg(loom)] mod`) builds the **real** `Pool`, `FlushCtl`/`throttle` wait loop or `NamespaceLocks` + gate. Those types import their primitives from `chunk_store::sync` (parking_lot-shaped shim) or `chunk_store::sync::raw` (std-shaped re-exports). Under `--cfg loom` both resolve to loom types, so `loom::model` enumerates thread orders of the real code.

### Pattern 1: cfg(loom) backend of the shim (Decision 1)
**What:** In `chunk_store::sync`, keep the public API (`Mutex`, `RwLock`, `Condvar`, `MutexGuard`, `Rank`, `rank::*`, `WaitTimeoutResult`). Under `cfg(loom)` the inner types are `loom::sync::{Mutex, RwLock, Condvar}`; add `pub mod raw` that re-exports `Arc`, `Mutex`, `RwLock`, `Condvar`, `atomic::*`, `thread` from `std` or from `loom` by cfg, for the code that uses std types on purpose (pool, commit gate, `FlushCtl` atomics, `Mutex<StoreIo>` stays std and outside the models).
**Why it works / costs (all measured or read):**
- The spike swapped only the `use` lines of a copy of `pool.rs` (std `Mutex`, `Condvar`, atomics, `Arc`, `thread::Builder`) and it compiled and ran under loom 0.7.3 on stable. The only other edit was removing `chunk_store::sync::rank::*` calls.
- The shim API has the parking_lot shape: `Condvar::wait(&self, guard: &mut MutexGuard)` and `wait_for`, no poison. loom has the std shape (`wait(guard) -> guard`). The loom backend guard must hold `Option<loom::MutexGuard>` and move it out and back inside `wait`/`wait_for` (about 30 lines `[ASSUMED]`, not written yet). `WaitTimeoutResult` is `pub use parking_lot::WaitTimeoutResult` today; under loom define a two-line type with `timed_out()`.
- **Rank tracking must be compiled out under loom:** `HELD` and `NEED_GATE` are `std::thread_local!` (`sync.rs`). loom runs its model threads as coroutines (`loom-0.7.3/src/rt/scheduler.rs` uses the `generator` crate) and ships its own `loom::thread_local!` mock (`loom-0.7.3/src/lib.rs:388`), which says std `thread_local!` is not per model thread. Use `#[cfg(all(debug_assertions, not(loom)))]` on `track`, `Entry` internals and `rank::*` (the rules keep their 22 unit tests in normal builds). Otherwise the stack is shared between model threads and gives false `lock rank violation` panics. `[ASSUMED]` for the exact failure; the mock macro is the evidence.
- **`wait_timeout` never times out in loom 0.7.3 or shuttle 0.9.10** (`loom-0.7.3/src/sync/condvar.rs:44-53`: `// TODO: implement timing out` then `self.wait(guard)`; `shuttle-std-0.1.5/src/sync/condvar.rs:226`: `// TODO support the timeout case -- this method never times out`). This is good for this phase: production code that has a `WAIT_SLICE` safety net (`pool.rs`, `throttle_write`) hides lost wakeups; under the model a lost wakeup shows as a deadlock panic. The models must not need a timeout to finish. Time is real (`Instant::now()`), so set long limits (`throttle_wait_ms`, `SUBMIT_WAIT`) in the model.
- `Instant`, `SystemTime` and `Duration` stay std.
- **Scope of the one cfg point (grep, this session):** `parking_lot::` appears outside `sync.rs` only in `tests/stress_harness.rs:214` (the deadlock checker, not built under loom); the only `static` lock is `lock_stats.rs:181` (feature `lock-stats`, off). So `chunk_store::sync` plus the std imports of `pool.rs`, `filesystem.rs` (gate, atomics) and `commit_timer.rs` are the whole edit list `[VERIFIED: grep]`. That the three crates compile under `--cfg loom` and that M2 and M3 fit the bound-3 time budget are **not measured** (only the pool was timed): the first model task is `RUSTFLAGS="--cfg loom" cargo check --workspace --tests` and the second a timing of M2 and M3 at bound 2 and 3 (Assumption A13).

### Pattern 2: the three model units and their seams (Decision 1, D-21)
The whole `SliceFsFilesystem` cannot run in a model: it does file I/O, calls zstd C code, and uses raw std atomics. Each model runs a small real unit:

| Model | Real code under test | Seam / edit list | Actors | Invariants |
|-------|----------------------|------------------|--------|------------|

It cannot show the deadlock that STACK.md line 49 describes (a queued exclusive commit blocks new shared holds while a shared holder waits on the budget), and loom reports deadlocks and failed assertions, not starvation. That deadlock is covered structurally: `throttle_write` runs before the gate and panics in a debug build when any ranked lock is held (`filesystem.rs` `debug_assert!(sync::rank::held().is_empty()...)`), `gate_shared` panics on a second gate hold of one thread (`Rank::Gate` same-rank rule, test `gate_after_a_lock_panics`), plus the S5 gate-fairness spike and the stress harness. Say this in the model's doc comment and in the summary. |
| M4 per race (a) | the claim/install protocol of the size change vs unlink | only if the planner wants a loom form; the deterministic `rebase_hook` test and a short stress test are the required evidence | n/a | n/a |

`Mutex<StoreIo>` (std, rank 6, leaf lock, no condvar) stays out of the models: it is held for short store calls and the models replace the store with closures. It is covered by TSan and the stress run. `metadata` and `chunk-store` internals are not modeled.

### Pattern 4: Miri allow-list (Decision 2)
Measured, one test per process, `cargo +nightly-2026-02-11 miri test -p <crate> --lib -- --exact <name>`, 90 s limit, on a Mac at load 17 (so timeouts are not budget facts):

| Crate | Pass | Unsupported-op abort | Over 90 s on the loaded host | Total |
|-------|------|----------------------|------------------------------|-------|
| chunk-store | 71 | 17 | 38 (never judged; compute-heavy tests: 100k hashes in `bloom`, `locality_tests`, big `file::tests`) | 127 |
| metadata (with the getuid guard below) | 56 | 103 (96 `fcntl` command 0x63, the macOS punch-hole probe in `StoreIo::open`; 3 zstd; others) | 6 | 166 |

- An unsupported operation ends the **whole test binary** (the interpreter stops), so one such test in a combined run hides all later tests. Therefore use an **exact-name allow-list** (a text file, one `--exact` name per line, run through a loop or `xargs`), not an ignore list. `#[cfg_attr(miri, ignore = "...")]` (D-12) is still right for tests a reader would otherwise think Miri covers; the allow-list is what CI runs.
- Reasons seen: `ZSTD_createCCtx` (C code; any test that stores 'big enough' data, `MIN_COMPRESS`, because `put` calls zstd at `zstd_level > 0`), `madvise`, file-backed `mmap`, `fcntl` punch hole on macOS (`fallocate` on Linux is expected to be unsupported `[ASSUMED]`), `getgid`, `mkdir`/`getcwd` under isolation, `clock_gettime` REALTIME under isolation.
- **Isolation (measured both ways):** the 71 chunk-store tests were run once with `-Zmiri-disable-isolation` (71 pass) and again with isolation ON (58 pass, 13 fail: 11 in `lock_tail_tests`, 1 in `retry::tests`, 1 in `extsort::tests`, with `unsupported operation: gettimeofday not available when isolation is enabled` (12) and `mkdir` (1)). Metadata needs the flag too (`clock_gettime` REALTIME, tempdirs). Decision: `-Zmiri-disable-isolation` for both crates. It does not weaken UB or data-race detection; it only lets the interpreted program read the host clock and files. Tests must still not depend on real time limits.
- **Wall-clock watchdog tests fail under Miri** (`wal::tests::no_deadlock_between_append_cut_and_sync` panicked "did not finish within 5 s (deadlock)" at 16.7 s of interpreter time). Never put tests with real-time limits in the list.
- **Which `unsafe` Miri reaches today:** none. `RunMap::new` (mmap of a file) is the only constructor; `MemIo::map_run` returns `Ok(None)` (`mem.rs:711-713`), so no test with `MemIo` reaches `from_raw_parts`. A **test-only anonymous mapping** reaches `from_raw_parts` (`bytes`), `unsafe impl Send/Sync` (by moving a `RunMap` across threads) and `munmap` (Drop): spike in a scratch crate passed on `x86_64-apple-darwin` and `x86_64-unknown-linux-gnu` (`mmap(MAP_PRIVATE|MAP_ANON)` + `copy_nonoverlapping` + `from_raw_parts` + `munmap`: ok; `madvise`: `unsupported operation: can't call foreign function madvise` on both). So the new constructor must not call `madvise`. It is a `#[cfg(test)]` addition to `pack_io.rs`, about 15 lines. The metadata getuid/getgid and the `fcntl`/`fallocate`/`F_FULLFSYNC` calls cannot run: review doc.
- **Metadata `new` under Miri needs a guard** (`getgid` unsupported on the macOS target; `getuid` ran): `#[cfg(all(unix, not(miri)))]` on the `getuid`/`getgid` line and a `(0, 0)` fallback under miri, as the existing `not(unix)` branch does (`store.rs:425-431`). This is a prod-code cfg, no behavior change. But the `store::tests` still abort on `fcntl`/zstd, so the guard alone adds no passing tests; add it only if the planner wants `new` in a Miri test with `MemIo` and small data. Recommended: skip the guard; list metadata `unsafe` in the review doc.
- Budget: the 71 chunk-store passes sum to about 1,020 s of interpreter time on a loaded host (single interpreter thread inside one process), the 56 metadata passes to about 320 s. On a CI runner expect 5 to 10 minutes total; limit 30 is fine. Re-measure in the first CI run.
- The passing names are in Appendix A. The planner must regenerate and re-run them on Linux (the Linux target may differ: `fallocate`, `getuid`).

### Pattern 7: deadlock-detect stress (Decision 5)
- `deadlock-detect` forwards `parking_lot/deadlock_detection` in `chunk-store`, `metadata`, `slicefs-cli` (`Cargo.toml` features). Only `tests/stress_harness.rs` starts the checker thread (`start_deadlock_watchdog`, once, every 1 s `parking_lot::deadlock::check_deadlock()`, prints each thread with backtrace and `abort()`s on a cycle) [VERIFIED: read `stress_harness.rs:204-230`]. parking_lot detects cycles of parking_lot `Mutex`/`RwLock` only. It does not see std locks (commit gate, `Mutex<StoreIo>`, pool queue) and not condvar waits; the harness `watchdog` (abort after `secs + 60 + verify_secs`) catches stalls.
- Spike (debug build, stable 1.100.0, `--features deadlock-detect`): `STRESS_SECS=15 STRESS_THREADS=8 STRESS_FILE_MIB=16 STRESS_SERIALIZE=0 STRESS_MODE=both cargo test -p slicefs-cli --features deadlock-detect --test stress_harness -- --ignored --exact long_run --nocapture` passed, `max_inflight=8`, test time 31.5 s for both modes, total 69 s with an incremental build. No cycle reported.
- Decision: job `deadlock` runs that `long_run` in `--release` (as its `#[ignore]` text says) with `STRESS_SECS=20 STRESS_THREADS=8 STRESS_SERIALIZE=0 STRESS_MODE=both`, a fixed `STRESS_SEED`, `timeout 600` around cargo test, plus `serialize_off_target` (in the default suite). No mount-level run: a mounted daemon has no checker thread, and the existing Linux Docker job already mounts with `--workers 4` (pjdfstest, smoke, live checks); a mount stress adds Docker time and no detector.

### Pattern 8: Coverage (Decision 6)
- Tool: `cargo-llvm-cov 0.9.2` (installed locally). `cargo llvm-cov --fail-under-lines <MIN>` exits 1 below the floor [CITED: github.com/taiki-e/cargo-llvm-cov README]. `--json --summary-only --output-path cov.json` gives per-file lines; group by `crates/<name>/` with `python3`/`jq` to print per-crate numbers. Print one machine line: `COVERAGE workspace=<x.xx> chunk-store=<..> metadata=<..> slicefs-cli=<..> ...`. Exclude `tests`, `benchmarks`, `vendor`, `examples` with `--ignore-filename-regex '/(tests|benches|benchmarks|vendor|examples)/'` `[ASSUMED]` that this matches the macOS 90.05 % baseline definition; the floor comes from the Linux run anyway (D-32).
- Runner part (no FUSE): `cargo llvm-cov --workspace --locked` for the in-process tests that do not need `/dev/fuse` is only valid if the whole workspace test set passes without FUSE; `ci.yml` runs the tests inside Docker (with `/dev/fuse`), which suggests some do need it. Safer and in line with D-31: **one coverage job, entirely inside the Docker harness**, new mode `scripts/docker-linux-test/run.sh coverage`:

  ```
  [CITED: cargo-llvm-cov README, "Get coverage of external tests": `show-env`, `clean --workspace`, build, run, `report`]. ## Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---------|-------------|-------------|-----|
| Schedule exploration | A custom thread-interleaving test harness or sleeps | loom (`loom::model`) | Partial-order reduction, preemption bound, deadlock detection. |
| Lock cycle detection | A new daemon-side watchdog | parking_lot `deadlock_detection` in the existing harness | Deferred item "daemon-side watchdog" stays deferred. |
| Coverage merge across processes | Own `.profraw` merge | `cargo llvm-cov show-env` + `report` | Handles `llvm-profdata` and filters. |
| Proof of arithmetic | Long property tests only | Kani on `u64`/`usize` full range | Covers the whole input range for small functions. |
| TSan suppressions | Blanket ignore | One written reason per entry (D-17) | Hides real races otherwise. |
| Ancestor check | A new global directory graph | Walk `lookup(dir, "..")` under the rename mutex | The `..` entry is stored per directory and `set_parent` keeps it right. |
| Pin of an inode against reclaim | A new refcount | The existing `open_count`/`orphans` in `HandleTable` (`open_handle`, `uncount`, `drop_last_link`) | Same pattern as `open_logged`. |

**Key insight:** the hard part of this phase is the seams (small extractions so real code runs inside a model) and honest scope statements, not the tool commands.

## The two races (Decision 7)

### Race (a): size change of a closed file vs unlink and setattr

**Code path (all `crates/slicefs-cli/src/filesystem.rs`; lines 2096-2146, 4093-4195 and 4967-4985 read this session with the Read tool or sed, tag [VERIFIED: filesystem.rs]):**
- `setattr_logged` calls `setattr_size_logged` first, then `with_inode_locked` for the other fields (about lines 5102-5160).
- `setattr_size_logged` (about 4093-4150), case B (no open cell): `drop(self.ns.lock(&[ino]))`, then a transient `FileCell`, `lock_cell`, `cells.insert_new`, `setattr_size_closed`, `log(size_op())`, `g.retired = true`, `cells.remove`. No stripe is held.
- `setattr_size_closed` (4151-4195): `get_manifest`; **`decrement_refcount(&old_manifest[0])` before the splice**; `content::splice`; the pause point `rebase_hook` (lines 4186-4189, only reached when `new_size != 0`); then `set_manifest(ino, &[new_digest])`, `increment_refcount`, `stamp_size` (`modify_inode`, which returns NotFound for a deleted inode and gives `EIO`).
- Unlink side: `reclaim_inode` (2096-2109) skips a transient cell (`filter(|c| !c.transient)`), reads `manifest_digest(ino)`, deletes the inode; `release_content` (2112-2125) reads the manifest node and `decrement_refcount`s each entry. `drop_last_link` (2133-2146) keeps the inode as an orphan only if `open_count.contains_key(&ino)`.

**What goes wrong today (window 1):** unlink reclaims during the splice. Then `release_content` decrements the old root a second time (the setattr already decremented it before the splice), `set_manifest` re-creates a manifest entry for the deleted inode, `increment_refcount` leaks one reference, and `stamp_size` returns `EIO`. This is worse than the leak the Phase 19 note describes: a **double decrement of the old root** can free content that another file still shares. [VERIFIED: `store.rs:1357-1365` `manifest_digest` reads the manifest map and `manifest_entries` returns the entry keys; `store.rs:528-538` `decrement_refcount` removes the entry when `count <= 1`; so with two files sharing one root (count 2), the early decrement of `setattr_size_closed` plus `release_content` of the unlink leaves count 0 while another file still points at it.] The decrement placed before the splice also double-counts on any error path of the splice (store error returns `EIO` with the manifest still pointing at the old root).

**Window 2 (precise):** `with_inode_locked` takes the stripe, then reads `cells.get(ino)`, then locks the cell if there is one (`filesystem.rs:2897-2902`). In case B the transient cell is locked and inserted into the map **before** `setattr_size_closed` runs (`filesystem.rs:4130-4135` [VERIFIED: Read]), so a fields call that starts after the insert finds the cell and waits for the whole size change: it is safe. The unsafe window is only the span between the stripe round trip `drop(self.ns.lock(&[ino]))` and `cells.insert_new`: a fields call that read an empty map in that span holds no lock the size change needs. Then the inode writes can be in the order (size `stamp_size`, fields `modify_inode`) while the records are in the order (fields `log`, size `log`, which comes last at `:4137`): live mtime is the explicit one, replay applies the size record last and gives another mtime.

**Fix (reuses the pattern of `open_logged`, `filesystem.rs:4967-4985`, whose comment says the counted handle keeps an unlinked inode alive as an orphan and the cell work runs with the stripe released):**
1. Case B becomes a claim under the stripe: `let ns = self.ns.lock(&[ino]);` check `meta.get_inode(ino)` (map `NotFound` to `ENOENT`); create the transient cell; `lock_cell` it (new and uncontended; stripe 3 before cell 4 is the allowed order); `cells.insert_new`; increment `open_count` for `ino` (a small `pin_inode`, the count half of `open_handle`, with no `by_fh` entry); drop the stripe guard (keep the cell guard; the rank stack accepts out-of-order release, test `guards_drop_out_of_order`). This replaces `drop(self.ns.lock(&[ino]))` and its create-ordering purpose.
2. Run `setattr_size_closed` as today, but **move `decrement_refcount(old)` to after `set_manifest` succeeded** (once, no double count on errors).
3. After `log(size_op())`: `g.retired = true; cells.remove(&cell); drop(g);` then `self.uncount(ino)` (stripe, then reclaim and `release_content` if the inode was unlinked meanwhile and this was the last count). The cell must be dropped first: `uncount` takes the stripe (rank 3 below the held cell 4).
4. Window 1 closes because an unlink during the splice sees `open_count` set, so `drop_last_link` makes the inode an orphan (`nlinks = 0`, `orphans.insert`); the install writes a manifest on an orphan; `uncount` reclaims it with the new manifest. Window 2 closes because the transient cell is in the map before any later stripe holder reads the map: a fields call either ran before the claim (its record precedes the size record) or finds the cell and waits for it. Cost: that fields call waits on the cell **with its stripe held** for the duration of the splice (bounded, rechunk near the end only). It already could today whenever it read the map after the insert. Mention in the plan as a measured side effect (the `lock_wait_rows` test file can show it).
5. No new `Op` variant: the size record is still `Setattr` with `size: Some(new_size)`; no format change.
6. **Difference from the direction in D-27** (re-check under the stripe before the install, install moved out of the cell hold): the install stays inside the cell hold here. Moving it out would let an open or a second size change enter between the splice and the install (the cell lock is what orders them, `filesystem.rs:4121-4129`). The claim under the stripe plus the open-count pin gives the same guarantee (the inode cannot be reclaimed during the install, and the fields call is ordered by the stripe) without the move. The plan should record this as a research-confirmed variant of D-27.

**Deterministic failing tests (written before the fix), no new hook needed:**
- Window 1: build a closed file with content (for example 64 KiB so `new_size > 0` passes through the splice), `test_set_rebase_hook(Some(hook))` where `hook` sends "in window" on a channel and blocks on a second channel; thread A calls `test_setattr_size(ino, None, 1024)`; main thread waits for "in window", calls `simulate_unlink(parent, name)`, then releases the hook. Before the fix: A returns `Err(EIO)`, and a manifest entry and a refcount for the deleted inode remain (`meta.get_manifest(ino)` is Ok, the old root refcount is one too low). After the fix: A returns `Ok`, `test_orphan_count() == 0`, `get_manifest(ino)` is NotFound, refcounts balance. The hook runs on A's thread with the rank-4 cell held, so the unlink must run on a second thread (same-thread unlink would trip the rank checker in a debug build).
- Window 2 **needs a new test-only hook** (the `rebase_hook` pause is too late: at that point the transient cell is already in the map and a fields call blocks on it, so the test would pass before the fix). Add `test_set_stripe_hook` (same style as `rebase_hook`, `Option<Arc<dyn Fn() + Send + Sync>>` in a `sync::Mutex` of `Rank::Short`) called in `with_inode_locked` right after `cells.get(ino)` and before the closure runs. Sequence: (1) thread F calls `test_setattr_times(ino, None, Some((T, 0)))`: it takes the stripe, reads an empty map, hits the hook, signals "armed" and waits for `go1`. (2) Main thread starts thread S, `setattr_size_logged(ino, new_size, &mut |op| { send("size-at-log"); wait go2; record(op) })` through an in-crate test (the `LogOp` closure is the second pause: it runs after `stamp_size`, before the size record is appended). (3) Main waits for "size-at-log" with `recv_timeout(2 s)`. Before the fix S reaches its log (nothing blocks it); after the fix S is blocked on the stripe that F holds, the wait times out, and that is fine. (4) Main sends `go1`: F does `modify_inode(T)` and logs; then main sends `go2` and joins both. Assert: the last recorded op decides the live state. If the last record is the fields op, the live mtime must be `T`; if it is the size op, the live mtime must not be `T` (it is the size change's stamp). Before the fix the live mtime is `T` (F wrote last) but the last record is the size op (replay would end with the size stamp): the assertion fails. After the fix S claims under the stripe after F has finished, so S stamps last and logs last: the assertion holds. The short bounded wait is the only timing in the test.
- Fallback rule (D-29): if after the fix the window tests or the stress test still fail (`EIO` from a size change, a manifest of a deleted inode, a refcount mismatch), set `default_workers()` to 1 for Linux too (one `if` in `pool.rs`: `cfg!(target_os = "macos") || RACE_A_OPEN`), keep the issue open, and record which race and why. Also state in the summary that on a Linux kernel mount the VFS inode lock probably serializes truncate, chmod and unlink of one inode before the daemon sees them `[ASSUMED]`, so this fallback would be conservative.

**Stress test that stays in CI (short):** `tests/race_closed_size_tests.rs` with 4 rounds of 2 threads: thread X creates and closes a file with content, then loops `test_setattr_size` while thread Y unlinks and recreates the name; assert every size result is `Ok` or `ENOENT` (never `EIO`), and after joining that no manifest exists for a deleted inode and `refcounts` sum equals the live manifests (use the existing GC check helper in `gc_online_tests.rs` or `store.check` if present; the planner finds the helper). Keep it under 5 s.

### Race (b): cross-directory rename with no ancestor check
- Code [VERIFIED: filesystem.rs `rename_held`, read this session]: `rename_held` (about lines 4721-4830). `lock_namespace(parent_ino != newparent_ino, ...)` takes the rename mutex first for a cross-directory rename; then `src_is_dir` is known; there is no check that `src_ino` is `newparent_ino` or an ancestor of it.
- Fix: after `src_is_dir` is computed, `if src_is_dir && parent_ino != newparent_ino { walk }`: `cur = newparent_ino; loop { if cur == src_ino { return Err(libc::EINVAL) } ; let up = meta.lookup(cur, "..")?; if up == cur { break } cur = up; depth += 1; if depth > LIMIT { return Err(libc::ELOOP) } }`, root is its own parent (`directory.rs:274` `d.put("..", parent_ino)` with the root's parent being itself `[ASSUMED]`; the test confirms). The walk reads `..` of directories that are not stripe-locked; this is safe because the rename mutex (rank 2) excludes every other cross-directory move, `rmdir` removes only empty directories and `mkdir` does not move any. It runs before any mutation and before `log(op())`, so a refused rename writes no record and no new `Op` is needed.
- Failing-first test (single-threaded, deterministic, in-process): `mkdir a`, `mkdir a/b`; `simulate_rename(ROOT, "a", b_ino, "c", 0)`. Before the fix it returns `Ok` and leaves a detached cycle (`a` has no entry in the root; `b/c -> a`); after the fix `Err(EINVAL)`. Also `rename(a, a/x)` (`newparent == src`).
- Stress or model that stays in CI: two or four threads doing random cross-directory directory renames over a small tree; at the end, from every directory follow `..` to the root with a depth bound (no cycle, root reachable). Under the rename mutex the outcome is serial, so this checks the walk and the lock together; keep it under 3 s.
- Reachability: the Linux VFS rejects a directory moved into its own subtree with `EINVAL` before FUSE sees the request (`rename(2)`: "EINVAL: An attempt was made to make a directory a subdirectory of itself") `[CITED: man7.org/linux/man-pages/man2/rename.2.html; the VFS enforcement for FUSE is [ASSUMED]]`. macOS FUSE-T and FSKit behavior is `[ASSUMED]` not guaranteed, so the daemon must check. The fix goes in the daemon in any case (D-28).

## Common Pitfalls

### Pitfall 1: `unexpected_cfgs` breaks the clippy gate
**What goes wrong:** `#[cfg(loom)]` and `#[cfg(kani)]` produce `unexpected cfg condition name` warnings; `-D warnings` makes them errors.
**How to avoid:** `[lints.rust] unexpected_cfgs = { level = "warn", check-cfg = ['cfg(loom)', 'cfg(kani)'] }` in each crate that uses them (the spike `Cargo.toml` used this form). `cfg(miri)` is a known cfg and needs nothing.
**Warning signs:** the clippy job fails on a file that has no lint issue.

### Pitfall 2: loom's dependency does not build on the pinned nightly
**What goes wrong:** `generator 0.8.12` (loom 0.7.3) uses `cfg_select!`, which `nightly-2026-02-11` rejects: `error[E0658]: use of unstable library feature cfg_select` in `generator-0.8.12/src/stack/unix.rs:20` [VERIFIED: compile error in the spike]. Stable 1.100.0 builds it.
**How to avoid:** the model job uses `RUST_STABLE`, never `NIGHTLY`. loom and shuttle are `[target.'cfg(loom)'.dependencies]` entries, never plain `[dev-dependencies]`: a plain dev-dependency would build in the Miri and TSan jobs (they run `cargo test`) and break them. `Cargo.lock` still lists loom and its tree after the change; commit it and run CI with `--locked`.

### Pitfall 3: the rank stack is thread-local
**What goes wrong:** under loom, model threads share one OS thread, so the `HELD` stack mixes threads. False `lock rank violation` panics, a leaked `require_gate(true)`.
**How to avoid:** compile rank tracking out under `cfg(loom)` (Pattern 1). The 22 rank unit tests stay in normal builds.

### Pitfall 4: a lost wakeup hidden by a timeout
**What goes wrong:** production waits use `WAIT_SLICE` (1 s) and `THROTTLE_SLICE`, so a missed notify costs a second and passes tests. In a model `wait_timeout` never times out, so the same bug is a deadlock report, which is the wanted result. The model must not rely on a timeout to finish; if a model deadlocks, first read the loop for a real lost wakeup before raising a limit.

### Pitfall 5: a failing model on a test that is not a model
**What goes wrong:** under `--cfg loom` every test that touches a shim lock outside `loom::model` fails with "cannot access Loom execution state from outside a Loom model".
**How to avoid:** `model.sh` filters `-- loom_` and the loom tests are named `loom_*`; no `#![cfg(loom)]` blanket in shared test files.

### Pitfall 6: Miri aborts the whole binary on one unsupported call
**What goes wrong:** one test with zstd (`ZSTD_createCCtx`), file mmap, `fcntl` or `getgid` stops the run, so an ignore list hides later tests and fails CI at random as tests change.
**How to avoid:** exact-name allow-list; a unit test that imports a new C call goes in or out of the list on purpose. Re-run the probe loop when adding tests. Do not put tests with real-time watchdogs in the list (`no_deadlock_between_append_cut_and_sync` panicked under Miri).

### Pitfall 7: Miri timings from a loaded host
Local Miri runs had load 17 and a parallel Kani job; 38 tests hit 90 s. Treat only "unsupported" and "pass" as facts. Re-measure the 38 on the CI runner before dropping them (`locality_tests`, `bloom`, and big `file::tests` are likely too slow for Miri anyway: 100k BLAKE3 hashes).

### Pitfall 8: TSan on the ubuntu runner and in a small Docker VM
The runner kernel's `vm.mmap_rnd_bits` can make TSan abort (Pattern 5). In this session's Docker VM only 0.8 GiB was free, and `core` with TSan was OOM-killed. The orchestrator note (Docker VM 13 GiB, `-j 1`) applies: a Docker TSan run is not needed because TSan runs on the runner (D-15); only coverage and FUSE checks use Docker.

### Pitfall 9: the pause hook runs inside the cell hold
`rebase_hook` runs on the size-change thread with the rank-4 cell held. A hook that calls unlink on the same thread panics the rank checker (stripe 3 after cell 4) in a debug build. Always run the competing operation on a second thread and coordinate with channels (no sleeps).

### Pitfall 10: fields setattr waits on the cell with its stripe held
After the claim-under-stripe fix, `with_inode_locked` of a concurrent fields call holds `stripe(ino)` while it waits for the transient cell. The splice is bounded, but a stripe is shared by about 1/256 of all inodes. Mention it in the summary; measure with `lock_wait_rows` if an owner wants numbers.

### Pitfall 11: Kani on strings
`from_utf8`, `contains(&str)`, `split`, `format!` and `parse::<u32>` blow up CBMC; symbolic slicing `&buf[..n]` is also slow. Use the byte-level core and fixed arrays (Pattern 6).

### Pitfall 12: coverage profiles lost when the daemon dies
A daemon killed with SIGKILL or aborted (the pool abort-on-panic tests) writes no profile. Only clean unmount exits count. Do not treat missing `fuse_callbacks.rs` lines from crash tests as a bug.
