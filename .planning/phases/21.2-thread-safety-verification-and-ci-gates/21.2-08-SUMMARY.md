# Phase 21.2 Plan 08: Kani proofs of the header core and the size arithmetic Summary

Kani 0.68.0 proves nine harnesses in slicefs-cli free of panic and overflow: the byte-level core of the store header parser, `workers_for_cpus`, `stripe`, the write end check, the hard cap and the dirty total move. A planted overflow in `first_line_number` makes Kani fail. `scripts/safety/kani.sh` is the command for the `kani` CI job of plan 21.2-11.

## What was built

- **Header core (header.rs, no behavior change).** `valid_name_bytes`, `valid_release_bytes`, `first_line_number(&[u8]) -> Option<u32>` (prefix, cut at the first space, digits only, value built with `checked_mul(10)` and `checked_add`) and `pub Class::from_word_bytes`. `parse` calls them with `.as_bytes()`. `Class::from_word` stays `pub` and calls `from_word_bytes`. The str forms `valid_name`, `valid_release` and the old first line parser are removed. The texts, rules and messages are the same; `FORMAT_NUMBER` stays 7.
- **Extractions (filesystem.rs, no behavior change).** `pub(crate) fn write_end(offset, len) -> Option<u64>` (both write end checks of `write_in_cell` call it: the first gives EFBIG on None for a non-append write, the second uses the end or gives EFBIG). `fn hard_cap_of(limit)` holds the saturating sum of `hard_cap`. `enum DirtyMove { Add, Sub }` and `fn dirty_move(old, cost)`; `sync_dirty` applies the move with `fetch_add`/`fetch_sub` as before.
- **Unit tests.** `header::tests::the_byte_core_keeps_the_header_rules` (the table of the plan), `filesystem::tests::write_end_gives_the_end_or_none`, `filesystem::tests::dirty_move_keeps_the_sum`.
- **kani.sh.** Sources toolchains.sh; installs `kani-verifier $KANI_VERSION` with `--locked` and runs `cargo kani setup` when `cargo kani --version` does not show the pin; prints `KANI version=0.68.0 (Kani uses its own bundled nightly, not NIGHTLY=...)`; runs `cargo kani --manifest-path crates/slicefs-cli/Cargo.toml --lib --output-format terse` under `timeout 1800` (env `KANI_HARNESS` adds `--harness`); prints `KANI harness=<name> result=<r> secs=<s>` per harness; fails when the `Complete - ...` line is missing, the failures are not 0, the cargo exit is not 0, or the verified count differs from the source count; ends with `KANI ok harnesses=<n>`.

## Deviations from Plan

1. **[Rule 3] kani.sh uses `--output-format terse`.** The regular output is about 2500 lines per harness. The terse form keeps every line that the per-harness parser and the `Complete` check need.
2. **[Rule 1] Single-harness mode.** With `KANI_HARNESS` set, kani.sh expects 1 verified harness. Without this, the plan's single-harness green run of step 5 fails the count check.
3. **Kani installed before kani.sh existed.** The same pinned command (`cargo install --locked kani-verifier --version 0.68.0`, then `cargo kani setup`) ran at the start, so the install was ready for the red run. kani.sh still holds the install step; on CI it installs on the first run.
4. **Gate cap 3600 s, not 2400 s.** Orchestrator rule (the gate takes about 50 min on this Mac).
5. **Ledger base.** Plans 07, 09 and the owner committed between 96f361d and this plan's first commit, so `plan_head_before` is 7b03ae7 (the parent of 7ed9a2f), and the commit count covers only this plan's commits.
6. **Coordinator note on b742f8b.** The note said to add the kani job to safety.yml. This plan forbids editing safety.yml (plan 21.2-11 adds the job), so safety.yml is not changed here. The `on:` block of b742f8b (v* tags and workflow_dispatch) stays as it is. The `KANI_VERSION: "0.68.0"` pin is still in the env block.
