## Summary

Scope: `git diff d0708f51 HEAD` (HEAD 3c1e813, branch `feature/phase-21.2-thread-safety`) for the
82 listed files under `crates/`, `scripts/` and `.github/`. `*.log` files and `vendor/` are out of
scope. I did not report the unsafe-review findings that are already filed (#196 kill pid<=1,
#197 errno in the signal handler, #198 FD_CLOEXEC, #199 SAFETY comments). I found nothing that makes
them worse than described.

**Race fixes: no defect found.**
- **Race (a), `setattr_size_logged` / `setattr_size_closed`.** The claim (inode exists, transient
  cell locked and inserted, `pin_inode`) runs under `stripe(ino)`. Then the stripe is dropped, the
  splice and the install run under the cell, then the cell is dropped and `uncount` runs. The ranks
  are 3, then 4, then 5. `uncount` takes the stripe only after the cell is released, so it cannot
  deadlock with a `with_inode_locked` caller that holds the stripe and waits for the transient cell.
- **Window 1 (unlink during the splice).** The pin makes `drop_last_link` keep an orphan, and
  `uncount` reclaims it. The log order is Unlink, then Setattr, or Setattr, then Unlink. Replay
  reaches the same state in both orders, because Setattr on a reclaimed inode is skipped
  (`oplog.rs:301`). `modify_inode` is an atomic read-modify-write, so `stamp_size` cannot lose an
  `nlinks = 0` written meanwhile.
- **Window 2 (setattr of other fields).** Every inode write and record of the size change happens
  under the transient cell. A fields setattr either ends before the claim, or finds the cell under
  the stripe and waits. So the order of the inode writes is the same as the order of the records.
- **Old-root release.** The old root is now released after `set_manifest`, so no error path
  decrements it without a new manifest (before the fix this was a double release).
- **Race (b), `check_not_ancestor`.** `set_parent` has one caller (`rename_held`, under the rename
  mutex), so `..` cannot change during the walk. The check comes before any write and before the
  NOREPLACE and ENOTEMPTY checks, so the errno order matches Linux.

**Extracted seams: behaviour-preserving.** I compared each extracted function line by line with the
code it replaced: `throttle_wait`, `request_stop`, `hold_shared`, `hold_exclusive`, `write_end`
(both call sites), `hard_cap_of`, `dirty_move`, and the header byte core.
- `first_line_number` against the old `parse_first_line`: the digit check comes before parsing
  (so `+7` is refused), and the result is `None` above `u32::MAX`.
- `valid_name_bytes`: the `windows(2)` check is the same as the old `contains("--")`.
- The `as_chunks` rewrites, the `unsupported_if` guard and the let-chain rewrites keep the same

**cfg gates.** `cfg(loom)` and `cfg(kani)` gate only the loom adapter, the `raw` loom exports, the

## Warnings

### WR-01: The lint-reason check in clippy.sh only finds some allow attributes (the D-09 gate can be bypassed)

**File:** `scripts/safety/clippy.sh:26-27`
**Issue:** The check is one `grep` for `(allow|expect)\((clippy::|dead_code|unused|deprecated|unreachable)`
on a single line, then it drops the lines that contain `reason =`. It does not find:
- an allow of any other lint, for example `#[allow(non_snake_case)]`,
  `#[allow(non_camel_case_types)]`, `#![allow(missing_docs)]` or `#[allow(unsafe_code)]`;
- an attribute that is split over lines, for example `#[allow(\n    clippy::too_many_arguments\n)]`
  (rustfmt makes this form for long lint lists);
- a line where `reason =` is in a comment or a string, but not in the attribute.

Failure scenario: a contributor adds `#[allow(non_snake_case)]` with no reason, or rustfmt wraps a
two-lint allow over lines. Both pass clippy.sh, and the release gate goes green with an allowed lint
that has no reason. That breaks D-09 ("an allowed lint needs a written reason").
**Fix:** Let clippy enforce the rule on the AST, and keep the grep only as a fallback:
```bash
cargo +"$RUST_STABLE" clippy --locked --workspace --all-targets -- -D warnings \
  -D clippy::allow_attributes_without_reason
```
Or add `allow_attributes_without_reason = "deny"` under `[lints.clippy]` (workspace lints) in each
crate.

### WR-02: release.yml can tag a commit of any branch or tag, and the gate jobs come from that same ref

**File:** `.github/workflows/release.yml:9-14, 44-63`
**Issue:** `workflow_dispatch` runs from the ref that the user selects in "Use workflow from". This
can be any branch or tag, and no step checks it. Two consequences:
1. A user with write access can make a `v*` release tag on the head of an unreviewed feature branch.
2. The called `ci.yml`, `safety.yml` and `release.yml` are read from that ref. A branch that edits
   `safety.yml` (for example to remove the `miri` job, or to make a script `exit 0`) still gets a
   tag from the "release gate".

The workflow comment says "normally main", but nothing enforces it. This matters more because the
next milestone (#178) will publish binaries from these tags.

Release has no `concurrency` group. Two dispatches at the same time each run the full gate. They
race on the push, and the loser fails only after about 12 minutes.
**Fix:**
```yaml
concurrency:
  group: release
  cancel-in-progress: false
jobs:
  check:
    if: github.ref == 'refs/heads/main'
    ...
```
Also add a repository tag ruleset for `v*` (an owner step) so that only the release workflow can
create these tags. Then "tag exists" means "gate passed".

### WR-03: The coverage gate runs on a Rust toolchain that is not pinned, so its result can change with no code change

**File:** `scripts/docker-linux-test/Dockerfile:1, 7-13` (used by `scripts/safety/coverage.sh:26`)
**Issue:** The other release-gate jobs pin their toolchain in one place (D-04:
`RUST_STABLE`, `NIGHTLY`, `KANI_VERSION`). The coverage job builds and measures with the toolchain
of `FROM rust:1-bookworm`, which moves to every new stable release. `cargo-llvm-cov` is pinned
(0.9.2), and `llvm-tools-preview` follows the image. The floor (`coverage-floor.txt` 90.27) was
measured with one compiler version.

Failure scenarios:
- A new Rust release changes its LLVM profile format to one that cargo-llvm-cov 0.9.2 cannot read.
  The job then fails at `cargo llvm-cov report`.
- A new release changes the line attribution, so the workspace number moves by a fraction of a
  point.

Either way the release gate goes red on an unchanged commit, and the safety.yml comment ("The
toolchain is the one of the Docker image") does not tell the owner why.
**Fix:** Pin the image to the same version as `RUST_STABLE`, for example
`ARG RUST_IMAGE=rust:1.100.0-bookworm` and `FROM ${RUST_IMAGE}`. Pass the version from
`coverage.sh` with `docker build --build-arg RUST_IMAGE=rust:${RUST_STABLE}-bookworm`. Then the one
pin in safety.yml covers this job too. (This changes the image of the `ci.yml` Linux job too. That
can be deliberate, or that job can keep a second tag.)

## Info

### IN-01: The version check in release.yml uses line-based grep, and some versions that pass it are not valid tags

**File:** `.github/workflows/release.yml:30-34`
**Issue:**
- `echo "$VERSION" | grep -Eq '^v...$'` passes if any one line matches. An input sent through the
  API, such as `gh workflow run -f version=$'v2.3.0\nx'`, passes the check.
- The pre-release part `(-[0-9A-Za-z.]+)?` accepts strings that git refuses in a ref name, for
  example `v1.0.0-..` or `v1.0.0-a.lock`.
- `git ls-remote --exit-code` exits with 128 on a network or auth error, and the `if` treats that
  as "tag not taken".

None of these creates a wrong tag, because `git tag -a` or the push refuses it. But each one fails
only in job `tag`, after the 12 to 40 minutes of gates.
**Fix:** Use `[[ "$VERSION" =~ ^v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z]+(\.[0-9A-Za-z]+)*)?$ ]]`.
Add `git check-ref-format "refs/tags/$VERSION"`. Handle exit code 2 of `ls-remote` as the only
"absent" result:
`rc=0; git ls-remote --exit-code ... || rc=$?; [ $rc -eq 2 ] || { [ $rc -eq 0 ] && echo exists; exit 1; }`.

### IN-02: The tag that GITHUB_TOKEN pushes does not start other workflows

**File:** `.github/workflows/release.yml:63`
**Issue:** A push made with `GITHUB_TOKEN` starts no workflow runs. This is correct today, because
safety.yml does not run a second time on its own `push: tags: v*` trigger. But a future workflow
that publishes binaries on a `v*` tag push (#178) will never start for these tags. This is easy to
miss when that milestone starts.
**Fix:** Chain the publish job inside release.yml (`needs: tag`), or push with a GitHub App token.
Write the choice down in the release.yml header comment.

### IN-03: The test pause hook runs on the production path of every fields setattr and xattr change

**File:** `crates/slicefs-cli/src/filesystem.rs:3049` (and `1462-1467`)
**Issue:** `with_inode_locked` calls `self.pause(Pause::FieldsStriped)` in every build. Each
setattr (non-size part), setxattr and removexattr locks the global `pause_hook` mutex and clones an
`Option<Arc>` while it holds `stripe(ino)`. With 2 to 8 workers, all these requests now meet at one
global lock inside a stripe hold, only to read `None`. It is correct (Short rank 5 is above Stripe
rank 3), but it is test-only cost on a hot request path.
**Fix:** Keep a `pause_armed: AtomicBool` that `test_set_pause_hook` sets. Do the fast path
`if !self.pause_armed.load(Relaxed) { return; }` in `pause()`. Or gate the call sites behind a
`test-hooks` feature.

### IN-04: The closed-file size change returns ENOENT for every metadata error

**File:** `crates/slicefs-cli/src/filesystem.rs:4256-4258`
**Issue:** `if self.meta.get_inode(ino).is_err() { return Err(libc::ENOENT); }` turns
`MetaError::Io` or `Corrupted` into ENOENT. A truncate that fails because of a store read error then
tells the client that the file does not exist, not EIO. This is the same pattern as `open_logged`
(`5155`), so it is consistent, but it hides store faults.
**Fix:** `self.meta.get_inode(ino).map_err(|e| meta_error_to_errno(&e))?;` (NotFound still gives
ENOENT).

### IN-05: The M3 gate model does not cover the commit path that really holds the gate exclusively

**File:** `crates/slicefs-cli/src/commit_timer.rs:72-76`
**Issue:** `commit()` still has its own copy of the `hold_exclusive` steps (rank entry, then
`exclusive_wait`, then `gate.write()`). The loom model `loom_gate_commit_excludes_requests` runs
`hold_exclusive`. If the two copies drift, for example if the counter is moved after the `write()`
in one place only, the model still passes, and the doc comment of the model already says so.
**Fix:** Have `commit()` call `crate::filesystem::hold_exclusive(gate, &fs.gate_xwaiters)` (through a small `pub(crate)` accessor, because the field is private). Keep
the returned `GateGuard` for the span of the cut, and drop it where `all` and `rank` are dropped now.

### IN-06: The script time limits are longer than the job limits, so their messages never print in CI

**File:** `scripts/safety/tsan.sh:97,113,116,119`, `scripts/safety/deadlock.sh:38,59`,
`scripts/safety/kani.sh:24`, `.github/workflows/safety.yml:57,71,83`
**Issue:**
- The `tsan` job limit is 10 minutes. tsan.sh uses `timeout 2400` for the build and `timeout 1200`
  for each entry.
- The `deadlock` job limit is 10 minutes. deadlock.sh uses `timeout 1800` and `timeout 900`.
- The `kani` job limit is 30 minutes. kani.sh uses `timeout 1800`, and the install also runs inside
  that job time.

On a stall, GitHub cancels the job first. So the `TSAN target=... result=fail` line, the
`DEADLOCK fail ...: stall (timeout)` text (`reason()`) and the `KANI fail` line never print. The
owner sees "The job exceeded the maximum execution time" with no entry name.
**Fix:** Make the script limits a little shorter than the job limit. Each script can read an
optional environment variable, for example `SAFETY_ENTRY_SECS`, that safety.yml sets per job.

### IN-07: A failed merged-report step makes the coverage job fail and can leave copied smoke profiles behind

**File:** `scripts/docker-linux-test/coverage.sh:91-98`
**Issue:** The header says the FUSE smoke part is "information only". But under `set -e`, a failure
of `cargo llvm-cov report` (line 96) or of `summary` (line 97) ends the script with a non-zero code
and fails the gate. It also skips the `rm` (line 98), so the copied `*.profraw` files stay in
`$CARGO_TARGET_DIR`, which is the persistent `slicefs-target` volume when the script runs locally.
A later `COVERAGE_REPORT_ONLY=1` run (which skips `cargo llvm-cov clean`) then counts the smoke
profiles in the gated "tests" number.
**Fix:** Wrap the merged block in a `trap 'rm -f "${copied[@]}"' RETURN` subshell, or remove the
files on every path. Run it with `|| echo "COVERAGE merged=fail"` so it cannot change `$gate`.

### IN-08: The workspace coverage number includes unit-test code in `src/`

**File:** `scripts/docker-linux-test/coverage.sh:25`
**Issue:** `IGNORE='/(tests|benches|benchmarks|vendor|examples)/'` leaves out only directories.
Test modules in `src/` are counted as product lines that are almost always covered. Examples:
`chunk-store/src/race_tests.rs`, `locality_tests.rs`, `lock_tail_tests.rs`, and every
`#[cfg(test)] mod tests`, including the about 1,000 test lines that this phase added to
`filesystem.rs`. Because of this, the 90.27 floor overstates product-code coverage, and new test
code moves the gate up.
**Fix:** Also ignore `_tests\.rs$`. Record in coverage-floor.txt that the number includes inline
`mod tests`, or move large in-crate test modules to their own `*_tests.rs` files.

### IN-09: The macOS job of the release gate tests on the runner's default Rust, not on RUST_STABLE

**File:** `.github/workflows/ci.yml:64-65` (called from `.github/workflows/release.yml:36-38`)
**Issue:** The release gate now runs `ci.yml`. Its macOS job runs `cargo test --workspace` with
the default toolchain of the `macos-latest` image. The Safety jobs use the `RUST_STABLE` pin. The
release can therefore pass on a compiler that is different from the one the clippy gate checked. The
code now needs recent stable features (`try_update`, let chains, `as_chunks`, `is_multiple_of`), and
the repository has no `rust-version`, so an older image toolchain fails with compile errors that do
not explain themselves.
**Fix:** Add `rust-version` to the workspace `Cargo.toml`. In the macOS job of `ci.yml`, run
`rustup toolchain install 1.100.0` and use `cargo +1.100.0 test` (or `source
scripts/safety/toolchains.sh`), so the release gate uses one compiler.
