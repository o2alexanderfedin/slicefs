# Phase 20 deferred items

- **Commit timer during unmount (found in 20-03, older than Phase 20).** The commit timer stops only after `mount()` returns. A timed commit can still run while `destroy` runs its own commit. Commits are serialized, and the 20-03 shutdown test passed 10 of 10 runs. Decision (orchestrator, reversible): not in Phase 20 scope; the Phase 20 code review checks it. If the review finds a real race, a fix plan stops the timer in `shutdown` before the destroy work.
- **Empty flusher passes from the kick (found in 20-05).** A write that finds the total at or above half the budget wakes the flusher. When the only dirty file is hot (at its own limit, written all the time), the pass finds no candidate. Decision (orchestrator, reversible): accept; a pass with no candidate is cheap. The 20-07 run reports the `passes` count; if the count costs measurable CPU, skip the kick when the last pass found no candidate.
- **Harness time near the 10 s limit (found in 20-05).** Five `stress_harness` runs took 9.38-10.45 s at a load average of about 19; the runs alone were under 10 s. The harness starts no flusher; the new work per write is one clock read. Decision (orchestrator): accept; the load caused the spread. Check again at phase close on a quiet machine.
- **No upper bound on `--dirty-budget` / `--dirty-limit` (found in 20-06).** Decision (orchestrator, reversible while there are no deployments): no upper bound. Overflow is safe (`saturating_add`). The help text says the budget is memory the daemon may use.
- **`--dirty-limit` and the stream reorder window (found in 20-06, older than Phase 20).** A stream can hold out-of-order pending writes up to `REORDER_WINDOW` (fixed 64 MiB), whatever `--dirty-limit` is. Decision: plan 20-08 documents it in the help/docs text; tying the window to the limit is a later item.
