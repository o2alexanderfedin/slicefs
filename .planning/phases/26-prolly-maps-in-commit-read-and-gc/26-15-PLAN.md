<objective>
Convert `xattr_data` to the owner's design of 2026-11-27: one tree entry per xattr name, a small value inline in the leaf, a large value spilled and stored like file content, so that every xattr call costs one entry (or one range of chunks) and no call loads the xattr set of a file whole.

Task 1 converts the store (encodings, owned tree keys and the prefix scan, per-name calls with the bounded read API, delete, commit, load, GC, rehash). Task 2 adds the integration tests (many xattrs on one file, one large spilled value, list order, remove, a reused number, races, GC of spilled values). Task 3 adds the crash case on the harness of plan 26-05 and the memory-bound test, and runs the gates.

Decisions this plan implements (26-CONTEXT.md "On-disk format"): "**Xattrs by name (owner, 2026-11-27, replaces the per-set encoding):** `xattr_data` key = ino (8 bytes, big endian) || xattr name bytes; value = 1-byte tag + either the inline value bytes (when key + value fit `MAX_ENTRY`) or the `ObjectKey` of a spilled value. A spilled value is stored like file content: chunks plus a manifest, so it is read and written in parts, never whole in RAM. getxattr/setxattr/removexattr touch one entry (O(tree height)); listxattr is a range scan over the inode's prefix, streamed node by node; a read with an offset (macOS resource fork) reads only the chunks it needs. Memory per xattr operation is bounded by one request, not by the size or count of the xattr set, so no per-file xattr limit is needed. No xattr set object exists any more."; "Value encodings (owner, after research): ... xattr values carry a 1-byte tag (inline value or spilled value)"; "Scope: rehash is ported to rebuild the trees".

Discretion choices (record in the SUMMARY): tag 0 = inline, tag 1 = spilled; the inline rule `4 + 8 + name + 1 + value <= MAX_ENTRY` (prolly leaf entry header, ino, name, tag, value); names of 1 to 255 bytes (Linux `XATTR_NAME_MAX`); the xattr overlay shards by the ino, so the names of one inode are in one shard; the pending copy of a scan holds keys only (no values); a spilled value is metadata (`Ref::Node`), not file content.

The fs layer (getxattr size queries, ERANGE, the streamed listxattr reply, the macOS getxattr position) uses these calls in plan 26-16. The `MetadataStore` trait does not change.

Purpose: PMAP-03 and PMAP-06 for `xattr_data`; PMAP-08 for its entries and spilled values.
Output: the xattr tree, the bounded calls, tests, `runs/gate-26-15.log`.
</objective>
