<objective>
Run the acceptance check of #98 on the final code: a 1 GiB and a 4 GiB random-write workload in Docker under one VmHWM cap. Set the final dirty limit from the measured runs. Update the two design notes.

Decision IDs (14-CONTEXT.md has no IDs; the planner numbers the bullets in order, as in plan 14-01): D-02 [memory of an open file bounded by a fixed limit; Docker 1 GiB and 4 GiB under the same VmHWM cap], D-08 [deterministic chunking; no forced cut; exact zero shortcut], D-09 [no rebase at fsync], D-10 [dirty limit per open file; start at 32 MiB, final value from measured runs], D-11 [the Docker memory test uses the per-op log; log-mode and replay RAM are follow-ups], D-05 [relog of the extents since the last rebase].

This plan implements D-02 (Docker part), D-10 (final value), and documents D-05, D-08, D-09, D-11.

Cap rule (fixed now, before any measurement; the Phase 13 rule adapted to one cap for two sizes):
1. P1 = "VmHWM after cmp" of a measure-only run of 1024 MiB on the final code (CAP_MIB empty).
2. If P1 <= 170 MiB (2/3 of the 256 MiB example in #98): CAP_MIB = 256. Else CAP_MIB = 1.5 x P1 rounded up to a multiple of 64. If that is 1024 or more, stop: the bound is not met; report the numbers and do not go on.
3. Set CAP_MIB and run 1024 and 4096 in check mode. Both must pass. If the 4096 run is above the cap, stop and report P1, P4 and the CAS bytes; do not raise the cap.

Expected bound (record it, do not gate on it): E = DIRTY_LIMIT + REORDER_WINDOW + H1, where H1 is the "VmHWM after cp" of the same run (the fixed costs of the daemon, the chunk index and the copy path). The per-handle peak is about max(REORDER_WINDOW, DIRTY_LIMIT) + one write + the rebase work space, so E is a high estimate. If P1 > 2 x E, write a FLAG line in the SUMMARY with the numbers: some memory grows that this phase did not plan for.

Dirty-limit rule: keep 32 MiB if the slowest single write ("max write" of rw.py) is at most 2000 ms in both sizes. Else set 16 MiB, rerun both sizes once, keep the value with the smaller slowest write that still passes the cap, and report both runs.

Purpose: the Linux libfuse number is the acceptance test of #98; the design notes keep the reasons for the next phases (#85 index, #21 locks).
Output: CAP_MIB in bigwrite.sh, the final DIRTY_LIMIT, two updated design notes.
</objective>
