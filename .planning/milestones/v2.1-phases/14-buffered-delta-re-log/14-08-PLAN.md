BEGIN 14-issue-98-comment.md
Fixed in #{{PR}} (merge {{MERGE_SHA}}, CI: {{CI_RUN_URL}}). A random write no longer loads the file into RAM, at any place in the daemon.

What changed:
- A handle that gets a random write is an overlay on the last stored content. The base stays in the chunk store and is in the manifest at once. Only the written bytes are in RAM.
- When the written bytes of a file reach the dirty limit ({{LIMIT_MIB}} MiB per open file), and at close, the file is chunked again only near the changed bytes, and the new chunk references go into the manifest tree (`splice` in `crates/chunk-store/src/file.rs`). Unchanged chunks and unchanged manifest nodes keep their IDs.
- A commit logs only the bytes changed since the last rebase, in records of at most 1 MiB (#93).
- fsync does not chunk the file again. The write log makes the bytes durable.
- Online GC cannot start during a rebase (the rebase holds the commit gate shared), and the base of each open file is a GC root.
- The commit gate is never held exclusively (timed commit, GC start) for a hash of file content. A rebase holds the gate shared, as every request does. So a rebase over long repeating data that is not zeros (chunked again to the end of the file) can make a timed commit or a GC start wait until that request ends.

Evidence:
- Docker, Linux libfuse, release build, per-op log, online GC off: 512 MiB of random writes (1 MiB and 4 KiB blocks) on a file copied in with cp. Daemon peak RSS (VmHWM): before this change {{BEFORE_MIB}} MiB for a 1 GiB file. Now {{P1_MIB}} MiB for 1 GiB and {{P4_MIB}} MiB for 4 GiB. Cap: {{CAP_MIB}} MiB for both sizes. cmp passes after the writes and after a remount. Run: `scripts/docker-linux-test/run.sh bigwrite`.
- Peak heap in the process for 16 MiB and 48 MiB files, random and repeating content: {{PEAKS}}. Limit 12 MiB. Test: `an_open_file_uses_memory_bounded_by_the_dirty_limit_not_the_file_size`.
- A 4 KiB change in a 32 MiB file adds {{NEW_OBJECTS}} objects and chunks {{RECHUNK_KIB}} KiB again. Tests: `a_small_change_adds_only_the_changed_chunks`, `a_rebase_rechunks_only_near_the_change`.
- Replay after a crash gives the same content, size and times with the per-op and the flush-on-fsync log: `an_overlay_replays_after_a_crash_with_each_log_mode`.
- Online GC during a rebase loses no chunk: `online_gc_during_a_rebase_keeps_every_chunk`, `gc_start_waits_for_a_rebase_in_a_callback`.
- The splice gives the same key as a full write of the same bytes: `a_splice_gives_the_same_key_as_a_full_write`.

Limits, in new issues:
- #{{ISSUE_A}}: one memory limit for all open files. Today each open file has its own limit.
- #{{ISSUE_B}}: the flush-on-fsync and periodic log modes, and replay, keep written bytes in RAM.

Note: chunking stays canonical (the same bytes give the same chunks on every node). On long repeating data that is not zeros, a rebase can chunk to the end of the file. CPU grows with that run; memory does not.
END

BEGIN 14-followup-global-limit.md
Title: One memory limit for all open files

Each open file has its own memory limit. A file with random writes holds up to the dirty limit of written bytes (DIRTY_LIMIT, {{LIMIT_MIB}} MiB, #98). A file that streams holds up to 64 MiB of out-of-order writes (REORDER_WINDOW). So N open files can hold N times these limits.

Proposal: one budget for all open files. When the sum is above the budget, the file with the most bytes rebases (overlay) or settles its pending writes (stream) first.

Acceptance: a test with many open files, each with random writes, keeps the daemon peak RSS below one fixed cap.
END

BEGIN 14-followup-log-ram.md
Title: Write log modes flush-on-fsync and periodic, and replay, keep written bytes in RAM

The flush-on-fsync and periodic log modes keep each record, with its data, in RAM until the next sync (`crates/metadata/src/wal/flush_on_fsync.rs`, `crates/metadata/src/wal/periodic.rs`). Replay at mount loads every record after the last root into RAM before it applies them (`crates/metadata/src/segment/mod.rs`). This memory grows with the bytes written since the last sync or commit. It does not grow with the file size, so #98 did not change it. The per-op mode (the default) does not have the first problem.

Proposal: write records to the segment file at once and sync later; stream the records into replay.

Acceptance: the bigwrite Docker check with `--wal-strategy flush-on-fsync` stays below the same cap as with per-op, and the replay of a large log stays below a fixed cap.
END
