<objective>
Add the chunk-list splice API to `crates/chunk-store/src/file.rs`: a streaming re-chunk of only the regions near the changed bytes, with the result spliced into the manifest tree, and unchanged chunks and whole unchanged nodes reused by ID. The output tree is the tree a full write of the same bytes makes.

Decision IDs (14-CONTEXT.md has no IDs; the planner numbers the bullets in order, as in plan 14-01): D-04 [rebase re-chunks only near the dirty extents and replaces that range of chunk references], D-07 [open question: can a range of chunk references be replaced without a full rewrite of the chunk list? Answer: yes, this plan], D-08 [chunking stays deterministic: the same bytes give the same chunks and the same file key; no forced cut; zero runs may use the exact shortcut that keeps chunk IDs], D-13 [the splice API in chunk-store/src/file.rs is in scope now; the old deferral of "an incremental CDC re-chunk or splice API in chunk-store" in the Deferred Ideas list is void by this decision]. The CLI flag for the limit and the Streaming-pending relog reduction stay deferred and are not in this plan.

This plan implements D-04 (re-chunk part), D-07 (answer), D-08, D-13. It changes no slicefs-cli file; plan 14-05 wires it in.

Purpose: with the splice, a rebase costs O(change + resync + tree depth) on random data, not O(file). Memory is fixed in every case, also on zero and periodic data where FastCDC resync can run to EOF (14-RESEARCH.md Q3).
Output: the splice, its cursor and writer helpers, and oracle tests in `file::tests`.
</objective>

Interface for plan 14-05 (keep these names and signatures exactly):
- `pub trait SpliceSource { fn read(&mut self, offset: u64, len: usize) -> Result<Vec<u8>>; }`: exactly `len` bytes of the NEW content at `offset` (the splice asks only inside [0, new_len)).
- `#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)] pub struct SpliceStats { pub rechunked: u64, pub reused_entries: u64, pub reused_nodes: u64, pub zero_runs: u64 }`. `rechunked` = the sum of the lengths of the chunks that the re-chunk loop emitted through FastCDC (not the bytes read from the source, and not the chunks of the zero shortcut, which `zero_runs` counts). `reused_entries` = old level-0 entries copied one by one; `reused_nodes` = whole old nodes pushed as one entry.
- The re-chunk loop reads the source in pieces of at most 2 x CHUNK_MAX (64 KiB), so a small edit reads about 2 x CHUNK_MAX around it, not a large piece.
- `pub fn splice(store: &ChunkStore, base: Option<ObjectId>, keep: u64, changed: &[Range<u64>], new_len: u64, src: &mut dyn SpliceSource) -> Result<(ObjectId, SpliceStats)>`. Meaning of the new content at byte x < new_len: the source byte if x is in a changed range; else the base byte if x < keep; else zero. Preconditions (an Error if broken, never a panic): keep <= base length, keep <= new_len, `changed` sorted, non-overlapping, inside [0, new_len).
