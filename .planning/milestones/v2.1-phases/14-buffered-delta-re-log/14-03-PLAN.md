<objective>
Add a by-hand Docker check for #98: random writes on a 1 GiB and a 4 GiB file, with the daemon peak RSS (VmHWM) measured on Linux libfuse. In this plan it only measures. Plan 14-07 sets the cap by a rule fixed in advance and runs both sizes on the final code.

Decision IDs (14-CONTEXT.md has no IDs; the planner numbers the bullets in order, as in plan 14-01): D-02 [memory of an open file is bounded by a fixed limit; tested in Docker with a 1 GiB and a 4 GiB random-write workload under the same VmHWM cap], D-11 [the Docker memory test uses the default per-op log; RAM of the flush-on-fsync and periodic modes and of replay are follow-up issues], D-12 [the switch log text and the Docker checks change together].

This plan implements the test tool of D-02 and the per-op pin of D-11. It uses the log text `switches to overlay`, the same literal that plan 14-04 puts in the switch log line and in the Phase 13 check (D-12).

Purpose: the Docker number is the acceptance test of #98 (the in-process allocator test in plan 14-04 does not see the kernel, the FUSE buffers or the chunk index). A run on the code before the change shows that the check detects the whole-file buffer.
Output: bigwrite.sh (new), a bigwrite mode in run.sh, a measured "before" number for the #98 comment.
</objective>

Per D-02, D-11, D-12.

1. New executable `scripts/docker-linux-test/bigwrite.sh` (bash, `#!/bin/bash`, house style of verify-phases.sh, short plain comments). Header: what it measures (#98), usage `bigwrite.sh <slicefs-binary> [size-MiB ...]` (default `1024 4096`), and that it runs inside the container. Variables: `CAP_MIB=` (empty in this plan: measure only; plan 14-07 sets it), `VOL_MIB=512`, `SEED=98`, `SWITCH_TEXT="switches to overlay"`, `R=/tmp/bw`.
2. Copy the helpers ok, bad, step, mnt, umnt, cas and hwm from verify-phases.sh. `mnt` passes `--wal-strategy per-op --gc-interval 0` (D-11: per-op log; GC off so the GC mark set, which grows with the store, is not in the number).
3. Write `$R/rw.py` from a heredoc, as the Large copy section does. Arguments: target, reference, seed, volume in MiB. One `random.Random(seed)`. Open both files O_RDWR (no truncate). Loop until the volume is written: one 1 MiB write, then 256 writes of 4 KiB, each at a random 4 KiB-aligned offset inside the file size, data from `rnd.randbytes`, the same offset and bytes to both files (a short pwrite loops). Time each pwrite on the target. fsync the target after each 64 MiB of volume (timed), and at the end. Print one line: `writes N, max write X ms, max fsync Y ms`.
4. Per size S (MiB), with a fresh store each time: seed an empty store (`$B seed <store> <empty dir>`), `head -c` S MiB of /dev/urandom to `$R/ref.bin`, mount, then steps with timeouts that fit a 4 GiB file: `bw-cp-S` (cp into the mount; 900 s), `bw-random-write-S` (python3 rw.py; 1800 s), `bw-cmp-S` (600 s). Read hwm after each of the three. Count `SWITCH_TEXT` lines in mount.log for this daemon (count before and after). Print the info line `bigwrite S MiB: VmHWM after cp A, after random write B, after cmp C MiB (cap CAP or "measure only"); <rw.py line>; overlay switches N; CAS bytes X; times cp/rw/cmp T1/T2/T3 s`. If CAP_MIB is set: `ok/bad bw-rss-bounded-S` (C <= CAP_MIB) and `ok/bad bw-overlay-used-S` (N >= 1). Then umnt, mount again, `bw-cmp-after-remount-S`, umnt, delete the store and the reference file.
5. End with `RESULT bigwrite: PASS|FAIL` and the exit status, as verify-phases.sh does.
6. run.sh: add the mode `bigwrite` that builds `cargo build -q --release -p slicefs-cli`, waits until the container is 45 s old, then runs `/dk/bigwrite.sh /target/release/slicefs` with the extra arguments of run.sh (pass them through `bash -c '...' _ "$@"`). Add bigwrite to the usage comment at the top and to the usage line of the `*)` case, with the note "by hand; not in CI". Change no other mode.
