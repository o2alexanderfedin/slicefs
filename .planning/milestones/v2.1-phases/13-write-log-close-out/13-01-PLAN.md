Facts the planner checked at HEAD ba34257 (the executor confirms them in Task 1, it does not take them on trust):
- `crates/metadata/src/wal/flush_on_fsync.rs`: `FlushOnFsyncWal` keeps records in `buffer: Mutex<Vec<WalEntry>>`. Only `flush_and_sync` and `rotate` call `SegmentWriter::write_entry`, and both sync right after. No Drop implementation exists in `crates/metadata/src/wal/` or `crates/metadata/src/segment/`. `SegmentWriter` wraps a `BufWriter<File>`, whose own drop only writes bytes that `write_entry` already put in it.
- `crates/slicefs-cli/src/handlers.rs`: `handle_release` and `handle_flush` log records but do not sync. `handle_fsync` and `handle_fsyncdir` call `fs.meta().flush_wal()`.
- `crates/metadata/src/wal/per_op.rs`: PerOp syncs only non-Op records at once. Op records wait in the BufWriter until a sync, so the existing `check()` helper (PerOp plus its own `flush_wal()`) is not usable for the rename test.
- `new_fs_with` (test file l.27) creates segment 1 and commits, which rotates to `segment-000002.seg`. `reload_and_replay` (l.39) creates segment 99 when it runs, so a torn-tail test must cut the file before it calls `reload_and_replay`.
- `crates/slicefs-cli/src/mount.rs` (about l.357-366): a mount runs `load_store_with_log`, then `oplog::replay`, then `MetadataStore::commit`, then `flush_wal`.

Patterns to copy from the test file: `fsynced_buffered_bytes_survive_a_commit_and_a_crash` (FlushOnFsync, hand-rolled crash), `a_file_still_open_at_the_crash_keeps_its_fsynced_bytes` (lookup + `test_read` check), helpers `create`, `write`, `fsync`, `release`, `data`, `dump`. The torn-tail cut is the same as `crates/metadata/tests/segment_frame_tests.rs` l.44 (`set_len(end - 3)`).

8. `reload_and_replay` again: `after.bin` and `kept.bin` read back their bytes, and `d/renamed` exists.
