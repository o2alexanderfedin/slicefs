<objective>
Make the index cheap in RAM and in disk reads: a blocked Bloom filter per run, the sharded memtable, and lookups whose page read happens outside the store lock, with a revalidation rule so that no lookup returns an object that GC removed or moved.

Purpose: IDX-01 ("at most one disk read on a hit and usually none on a miss"), IDX-02 ("cold open reads only the run footers and filters"), and the RAM target (a few bytes per object).
Output: bloom.rs, the filter in the run format, the sharded memtable and lookup protocol, MemIo read counters, race tests, IDX-01 and IDX-02 tests.
</objective>

Project rules: `export PATH="$HOME/.cargo/bin:$PATH"`; targeted cargo commands; no mounts; no sleeps in the race tests (they use a hook).

Why a revalidation rule: the locked [Locking] decision checks the memtable again under the lock before an append, but that covers only the miss path. A dedup hit (or a Loc for read) decided on a snapshot goes stale if a full gc_begin..gc_finish runs between the lookup and the store lock: put would skip the write of an object that GC removed (silent loss), and read would open a deleted pack. Today put and read are atomic under one lock, so this risk is new.

fastbloom (already in the workspace, used by crates/cas-local) is not used: its bit layout belongs to that crate and can change between versions, so its bits are not safe to persist [Filter type].

Write the tests first (unit tests in bloom.rs and run.rs), run them, then implement [Layout: Bloom 10 bits per key] [Filter type]:
1. crates/chunk-store/src/bloom.rs (new, mod bloom; pub(crate)): a blocked Bloom filter with 512-bit (64-byte) blocks. Block count = max(1, ceil(n x bits_per_key / 512)). Probes come straight from the 32 digest bytes, no hashing (the keys are uniform BLAKE3 digests): block index = the high 64 bits of (u64 LE of digest 0..8) x (block count) as u128; h1 = u64 LE of digest 8..16; h2 = (u64 LE of digest 16..24) OR 1; bit i (i in 0..k) = (h1 + i x h2) mod 512 inside the block (Kirsch-Mitzenmacher). k = round(bits_per_key x 0.693), clamped to 1..=16 (7 at 10 bits), so the footer needs no k field. Serialize as little-endian u64 words. Only the digest is a filter key (not the tag), so two IDs with the same digest and another tag share filter bits; that is only a false positive.
2. A small filter interface in run.rs (an enum or a trait with may_contain) with filter type 0 = none (always maybe) and 1 = blocked Bloom; the footer type byte selects it and the bits-per-key byte is stored.
3. RunWriter takes the entry count up front (the memtable length for a flush; the sum of the input entry counts for a merge, an upper bound), sizes the filter from it, and inserts each digest while the entry streams through. It never keeps the digests: for a 100M-entry merge they would need about 3 GB, which breaks the memory rule; the filter itself is about 1.25 B per entry. It writes the filter block before the footer, with its offset, length and CRC32C.
4. Run::open reads and checks the filter block (its length must be block count x 64 for the stored parameters, checked arithmetic); Run::get calls may_contain on the digest before the page read and returns None on a negative. Run::get on a tombstone still needs the filter to answer maybe: tombstones are inserted into the filter too.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| lookup outside the store lock -> decision under the lock | the snapshot can be older than a GC that ran in between |
| disk -> filter block | filter length and parameters are untrusted |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-17-09 | Tampering | put and read after a concurrent GC | critical | mitigate | gen is read before the lookup and bumped by every flush, merge install and GC tombstone install; under the store lock put and read compare gen and the memtable and look up again if either changed; tombstones go into the memtable before any pack change; three hook-driven race tests, each of which asserts that its hook ran |
| T-17-10 | Tampering | bloom.rs parse, Run::open filter block | medium | mitigate | the filter length must equal block count x 64 for the footer parameters (checked arithmetic); a CRC32C covers the block; a length that is zero or not a multiple of 64 is refused (unit test) |
| T-17-11 | Denial of service | lock order store lock then shard lock | medium | mitigate | one fixed lock order (store lock, then a shard); lookups take only a shard lock and the run-set read lock, never the store lock while holding a shard |
