<objective>
Make SHA-256 a production write hash of a store, end to end, with the header flag that keeps an older build away from SHA-256 objects. A store can be seeded or mounted with `--hash sha256`; BLAKE3-256 stays the default.

Task 1 is the tracer of the phase: the thinnest path through every layer this plan changes. It adds the hasher and its crate, the flag in the first header write, and one end-to-end test: `seed --hash sha256` makes a store whose header has the flag, whose objects all carry tag 0x12, whose files read back, and which scrub accepts. Task 2 adds the parse rule, the flag on the `mount --hash` path, and the flag-only write that rehash step 2 needs. Task 3 removes the unused crate, documents the flag, and runs the plan gates.

Decisions this plan implements: D-01, D-03, D-09, D-10, D-11 (flag, pairing rule, flag kept), R-09, and the step-2 helper of D-18. Discretion choices (reversible, recorded here): the flag name stays `hash-sha256`; the release word comes from the new constant `HASH_SHA256_RELEASE` with the value `v2.2` until the owner names the release, as `CHUNK_PROFILE_RELEASE` (tests use the constant, never the text); the flag line comes right after the hash line in a new header and at the end of the lines in a rewrite; `Sha256` is not re-exported from the crate root (that would edit `lib.rs`, which plan 23-03 owns in this wave).

Purpose: HASH-01, and the header flag that every later plan relies on.
Output: the hasher, the dependency change, the header flag and rule, the content helpers, tests, the store-format doc rows.
</objective>

<assumption_delta_decision>
The detector fired (pluralization: "from one hash algorithm to another"). The noun that is primary is already the general one: an `ObjectId` names its hash (tag byte + digest), each object is verified by the hasher of its own tag, and the write hash is a per-store setting (since v2.0). SHA-256 is one more `ObjectHasher`.
- Primary noun: the tagged object ID (`ObjectId` / `ObjectKey`), not "the BLAKE3 digest".
- Decision: no-change. The generalization was promoted when tagged IDs and `ObjectHasher` came in; this phase adds a variant, it does not add an identity model alongside the old one.
- Invariant test (added in Task 1): `every_known_hasher_round_trips` puts and reads an object under every hasher of `hashers()` and checks the tag, so a later singular assumption turns it red.
</assumption_delta_decision>
