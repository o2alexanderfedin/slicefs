# Phase 21.1: Store header and format policy (#154) - Context

**Gathered:** 2026-11-24 (auto mode; orchestrator decisions, all reversible: no deployments, no store backward compatibility)
**Status:** Ready for planning

<domain>
## Phase Boundary

One store header that names the store format and its feature flags, so later phases (22 chunk profiles, 23 hashes) can add a change as a flag and not only as a new format number (#154).

- The header file at the store root holds a store format number and three flag sets: compat, ro-compat, incompat (ext4 model).
- Open refuses an unknown incompat flag; an unknown ro-compat flag gives a read-only mount; a store with data and no header is refused.
- `slicefs stats` shows the format number and the flags.
- `docs/design/store-format.md` holds the layout, the flag classes, the flag list, the error messages and the format policy; README has one line and a link.

Out of scope: the format freeze (an owner decision, later), the chunk-profile and hash flags themselves (Phases 22 and 23 add them), a public `--read-only` mount option, any migration of old stores.

</domain>

<decisions>
## Implementation Decisions

### Header file
- [Header] Keep the existing text marker `<store>/FORMAT` (`crates/slicefs-cli/src/content.rs`) and grow it into the header. Text, one item per line, so a person can read it and an error can name a flag. It stays written durably (synced temp file, rename, directory sync) as `write_marker` does today.
- [Number] The first line becomes `slicefs-store 7 ...`. Reason: a format-6 binary ignores unknown lines, so it would ignore an incompat flag. The number change makes every older binary refuse a format-7 store. A format-6 store is refused with the existing "made by an older SliceFS" message (no migration, as decided).
- [Flags] Three line kinds, for example `compat <name> <release>`, `ro_compat <name> <release>`, `incompat <name> <release>`: a flag is a short kebab-case name plus the lowest release that knows it. So an old binary can name both in its error ("needs SliceFS <release> or later"). The exact line syntax is the planner's choice, documented.
- [Parse order] (review 2026-11-24; refined after research) Read all lines and collect the flags first. If any flag is unknown, the strongest unknown flag decides (incompat: refuse; ro_compat: read-only; compat: go on), and unknown lines are allowed in that case (they belong to the unknown feature). If no flag is unknown, an unknown line kind is an error. Rule for later phases: a new setting line always comes with a flag, so an old binary never meets an unknown line without an unknown flag.
- [Number parse] Parse the format number from the first line (`slicefs-store <n> ...`); do not compare the whole first line as today (`starts_with(FORMAT)`).
- [Hash line] The `hash <name>` line stays a store setting (not a flag) in this phase. Phase 23 decides whether a new hash also adds a flag.
- [Initial flags] Format 7 starts with an empty flag list. Tests use test-only flag names (for example written by a test helper) to prove the three rules; no fake flag ships.
- [Release numbers] Do not write a real release number in the doc, the messages or the tests: the tag name for this milestone is still open with the owner. Tests use test-only values. The policy states that the format is not frozen yet.

### Open rules
- [Durable first] For a new store the header is written durably before `packs/` or `segments/` exist, so a crash cannot leave data with no header.
- [New store] The header is written only when the store is new: no `packs/` data and no `segments/` (or the directory is missing or empty). Today `content::open` writes a marker for any store without one; that changes: a store with data and no header is refused with a clear message that names the missing file.
- [Incompat] Any unknown incompat flag: refuse every command that opens the store (mount, gc, stats, scrub, snapshot, seed into an existing store). The message names the flag and its release.
- [Ro-compat] Any unknown ro-compat flag:
  - `mount` mounts read-only (FUSE `RO`) and prints one line that names the flag and why;
  - in that mode the daemon writes nothing to the store: no write-log replay, no flusher, no commit timer, no online GC, chunk store and index opened read-only (the `read_only` open of `Index::open` exists);
  - if the write log has records to replay, refuse the mount (a newer binary must replay them) with a message that says so;
  - commands that write (gc, seed, snapshot create) refuse; read commands (stats, scrub without repair) run.
- [Compat] Unknown compat flags are kept as they are when the header is written again (for example by `select_hash`), never dropped.
- [Where] One module owns the header (parse, write, check). The check runs at the open points, not in each command: inside `content::open`, `open_read_only`, `store_io` and `store_io_read_only`, and before anything writes (today `select_hash` in `mount.rs` ~101 and `seed.rs` ~38, and `create_dir_all` in `open`, write before `check_format` runs). Today `check_format` is called by mount, gc, stats and scrub only; `snapshot.rs` (create, list, switch: lines ~64 and ~161) calls `store_io` with no check. `stats` and `scrub` already open read-only (`store_io_read_only`). The planner picks the module and the crate.
- [Mount lock] `mount.lock` (`crates/metadata/src/mount_lock.rs`) is a file in the store root that marks a mount in progress; a lock left by a crash triggers write-log replay. It is crash detection, not exclusion. A ro-compat (read-only) mount does not create it. If it exists at a ro-compat mount (a crash, or a writer daemon now running), the mount is refused (a newer binary must replay first).
- [Ro tracer] The read-only mode must be proved in the daemon, not only by FUSE `RO` (the kernel gives EROFS as soon as `RO` is set; snapshot mounts set it today and still reuse the writable store handle). Tracer and must-have: an in-process test (runs on macOS CI too) that opens a store with an unknown ro-compat flag through the mount path's own setup, reads files, and shuts down as `destroy` does; the store tree is then unchanged (file list, sizes, content hashes). It must be red with only `RO` set. Expected write paths to close: the commit in `destroy`/`shutdown`, the write-log segment open, the `gc-tmp` cleanup of a writable open, index rebuild or flush, the marker rewrite in `select_hash`, `auto_snapshot`, atime updates, and `mount.lock`.

### Output
- [Stats] `slicefs stats` prints the format number and each flag set (with `--json`, as fields).
- [Doc] `docs/design/store-format.md`: header layout with an example, the three classes and what an old binary does with each, the flag list (empty now, with the rule for adding one), every error message, and the format policy: the format number changes only when an old binary cannot parse the header safely; any other change adds a flag; the format number is separate from the release number. The README gets one line and the link.

### Tests (keep short)
- unknown incompat flag refused; unknown ro-compat flag gives the read-only decision (unit test of the open decision, plus a Linux Docker mount check that the mount is read-only and a write fails with EROFS); ro-compat with records in the write log refused; a store with data and no header refused; a new store gets a header; format 6 refused; compat flags kept on rewrite; `stats` shows the header.
- No macOS mounts locally; macOS CI as before.

### Settled after research (orchestrator, 2026-11-24, reversible)
- [Snapshots] Snapshot mounts of a normal store keep their current behavior in this phase (they still write); recorded as a deferred item. The new read-only wiring makes the later fix small.
- [Empty store reads] A read command (stats, scrub) on an empty store with no header writes nothing and shows the format as `none` (JSON `null`).
- [Ro options] A ro-compat mount refuses `--hash` and `--auto-snapshot` (both write).
- [Ro requests] No per-request EROFS check in the daemon; the FUSE `RO` option stops write requests in the kernel.
- [Plan split] As proposed in 21.1-RESEARCH.md: 01 tracer (header core, read-only daemon mode, `mount::start`/`Started::stop` split, tracer test red first, refusals for a pending log and `mount.lock`); 02 the check at every open point before any write, all refusals, compat kept on rewrite, the test-site fixes; 03 `stats` output and the Docker ro-compat EROFS check (tar-stream method, `cargo build -j 1`, `build-exit=0`); 04 `docs/design/store-format.md` and the README line.

- Exact line syntax, module and type names, the error text wording (plain, short), how the read-only daemon mode is wired.

<specifics>
## Specific Ideas

- No backward compatibility for stores; no user paths in public text; no license talk.
- Never hold whole files in RAM; keep tests short.
- Test stores: the `check_format` comment says test code makes stores with no marker (about 5 test files use `content::open`/`store_io` directly, and unit tests in `content.rs`, `seed.rs`, `scrub.rs`). New stores still get a header on first open, so most keep working; count the sites that make a store with data and no header, and give them one test helper that writes the header.
- Docker (Linux mount checks): the Docker VM is low on memory; build with `cargo build -j 1`, and every committed Docker log must show `build-exit=0` (the run script stops on a failed build).

</specifics>
