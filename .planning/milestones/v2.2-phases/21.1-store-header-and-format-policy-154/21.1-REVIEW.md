## Summary

Scope: `git diff 89556f5..HEAD -- crates scripts`. The review read the code of the changed files. It also read the code that they call: the read-only open of the chunk store (`ChunkStore::open_with`, `FileIo::prepare`, `Index::open`, `Index::rebuild`), `scan_store_with_log`, `GcHandle`, the online GC loop, the commit timer, `MountedFs::destroy` and the flush and fsync handlers.

Items that were checked and are correct:

- **Header check before writes.** At each open point, the header check comes before the first write to the store. The open points are `content::open`, `open_read_only`, `store_io`, `store_io_read_only`, seed, gc (also the online GC request), snapshot create, switch and list, stats, scrub, `run_mount`, `start` and `load_store`. Before the check, `run_mount` writes only the mount point directory. Each other non-test caller of `StoreIo::open`, `ChunkStore::open_with` and `FileIo::new` is in a `#[cfg(test)]` module or in `tests/`.
- **Read-only daemon mode.** It does not replay the write log. It does not start the flusher, the commit timer, the online GC or the segment GC. It does not make `mount.lock`. `test_destroy` returns before the commit. The chunk store opens with `read_only: true` and `gc_tmp_dir: None`. With `read_only`, `FileIo::prepare` makes no directory, `Index::opened` and `Index::rebuild` write nothing, the pack scan does no `set_len` and writes no `.idx`, `punches` is false, so there is no punch probe, and `put` fails. A write that the two tree compares cannot see (a file that is made and then deleted) was not found in this code.
- **`mount::start` and `Started::stop`.** In `start`, no `?` comes after the first thread starts (`mount.rs:466-517`). In `run_mount`, no `?` comes between `start` (`mount.rs:664`/`666`) and `started.stop()` (`mount.rs:742`). `stop` runs before `mounted?`, so a failed `fuser::mount` stops and joins all four threads, then drops the lock.
- **M7 (pending write log).** `scan_store_with_log` does not count the records after a broken link (`segment/mod.rs:180-181`). Thus such records do not cause a false M7 refusal.

No Critical issue was found. The four warnings are: a race in the header create; the read-only mount leaves no sign that a newer SliceFS can see; a `select_hash` print guard that is always true; and one unnecessary `create_dir_all`.

The task gives these items as known and out of scope, so this review does not report them again: `unmount --store`, snapshot mounts of a normal store, and the items of `deferred-items.md`. Item 5 of `deferred-items.md` (no EROFS check for each request) is one of them. Note: there is no evidence that FUSE-T on macOS obeys the `ro` option. The Linux Docker check is the only EROFS evidence.

## Warnings

### WR-01: Two parallel creates of a new store can install an empty FORMAT, and both fail

**File:** `crates/slicefs-cli/src/header.rs:437-466` (also `header.rs:398-404`)
**Issue:** `check` accepts `AlreadyExists` from `create` "for a parallel create". But `create` is not safe when it runs in parallel:
- `create` first tests `exists()`, then writes (a check-then-act race).
- `write_text` uses the fixed temp name `FORMAT.tmp`.

Failure scenario: two `slicefs seed` commands start on the same new directory. Call them P1 and P2.
1. P1 makes `FORMAT.tmp`, writes it and syncs it.
2. P2 calls `File::create(FORMAT.tmp)`. This truncates the same inode to 0 bytes.
3. P1 renames `FORMAT.tmp` to `FORMAT` and syncs the directory. `FORMAT` is now the empty inode that P2 writes to.
4. P1 reads the header again. It gets `""` or part of the text, and fails with M4 (`unknown store format ""`).
5. P2's rename gets `NotFound`, not `AlreadyExists`. Thus P2 also fails.

If the power fails after step 3 and before P2 syncs, the empty `FORMAT` is durable. Each later command then refuses the store with M4 until a person deletes `FORMAT`. The same shared temp name also lets a `select_hash` rewrite and a `create` damage each other.
**Fix:** Use a unique temp name, and install the new header with an operation that does not replace an existing file:
```rust
fn write_new(store: &Path, text: &str) -> std::io::Result<()> {
    use std::io::Write;
    let tmp = store.join(format!("{FORMAT_FILE}.tmp.{}.{}", std::process::id(), nonce()));
    { let mut f = std::fs::File::options().write(true).create_new(true).open(&tmp)?;
      f.write_all(text.as_bytes())?; f.sync_all()?; }
    let r = std::fs::hard_link(&tmp, store.join(FORMAT_FILE)); // AlreadyExists if another create won
    let _ = std::fs::remove_file(&tmp);
    r?;
    std::fs::File::open(store)?.sync_all()
}
```
Use `write_new` in `create`. In `write_header`, use a unique temp name and `rename`.

### WR-02: A read-only mount leaves no sign, so a newer SliceFS can GC the store under it

**File:** `crates/slicefs-cli/src/mount.rs:134-166`, `crates/slicefs-cli/src/gc.rs:97`, `crates/slicefs-cli/src/stats.rs:224`
**Issue:** A ro_compat (read-only compatible) mount takes no `mount.lock` and writes nothing. This is by design. But the other commands use `mount.lock` to find a live mount:
- `gc_report` sends the GC to the mount only if `mount.lock` exists. Otherwise it runs an offline GC.
- `snapshot create` and `snapshot switch` refuse a mounted store only if `mount.lock` exists.

Thus a newer SliceFS that knows the flag (the only binary that can write this store) cannot see the live read-only daemon. Failure scenario: SliceFS A mounts a ro_compat store read-only. A newer SliceFS B runs `slicefs gc --full` on the same store. B sees no `mount.lock` and runs an offline GC that deletes or compacts packs. A's in-memory index still points into those packs, so reads through A's mount get EIO. Also, `slicefs stats` shows `Mounted : no` for the live read-only mount.

This is a one-way door: when this release ships, a later release cannot detect readers of this release.
**Fix:** Make the read-only daemon advertise itself without a write to the store. For example, hold a shared `flock` on `<store>/FORMAT` (or on the store directory) for the life of the mount, and document that writers and GCs of later releases must take an exclusive `flock` first. A `flock` does not change the store tree, so the tracer stays green. As a minimum, describe the gap in `docs/design/store-format.md`.

### WR-03: The `select_hash` print guard is always true; `seed --hash` on a new store prints the hash-change line

**File:** `crates/slicefs-cli/src/content.rs:78-87`, `crates/slicefs-cli/src/seed.rs:39-41`
**Issue:** `select_hash` prints "New objects use hash X (was Y)" only when `FORMAT` existed before its own check. The 21.1-02 SUMMARY says "a new store seeded with --hash prints nothing, as before". But `run_seed` calls `header::check(Want::Write)` at `seed.rs:39`, and this check makes `FORMAT` before `select_hash` runs at `seed.rs:41`. The other production caller, `load_store` (`mount.rs:108`), runs only on a store with data, so its header also exists. Thus `existed` is always true in production, and the guard does nothing.

Failure scenario: `slicefs seed --hash <a second hash> newstore src` prints "New objects use hash ... (was blake3-256); stored objects stay readable." for a store that has no objects. It also writes the header two times. Today a release build knows only `blake3-256` (`chunk-store/src/hash.rs:71-75`), so the problem shows only with `test-hasher`. Phase 23 adds hashes, and then the problem shows in release builds.
**Fix:** Let `run_seed` send the "was new" state to `select_hash`. Or, in `run_seed`, call `select_hash` before the header check when `FORMAT` is missing, and let `select_hash` write `marker(new)` through `create`, so that a new store gets one header write with the right hash.

### WR-04: Already-defended-elsewhere — `create_dir_all` in `run_seed` after the header check

**File:** `crates/slicefs-cli/src/seed.rs:40`
**Category:** necessity
**Issue:** When `header::check(store_path, Want::Write)` at `seed.rs:39` succeeds, the store directory always exists. There are two cases:
- `FORMAT` was there, so the directory exists.
- `FORMAT` was missing, so `create` ran `std::fs::create_dir_all(store)` (`header.rs:438`).

Thus line 40 never does work. The 21.1-02 SUMMARY says that the line stays only as "the end of the awk range of the seed gate" (a grep gate of the plan), not for a run-time need.
**Fix:** Remove the line, and end the gate range at `select_hash`. Or put a comment on the line that says why it stays.

## Info

### IN-01: The `--json` error output is not valid JSON for the new messages

**File:** `crates/slicefs-cli/src/main.rs:36-37` (the same pattern for each command); `crates/slicefs-cli/src/header.rs:187`, `header.rs:234`
**Issue:** `main` prints `{"error": "{e}"}` and does not escape the text. M4 and M9 put `{line:?}` in the text, and this adds `"` characters. Example: `slicefs --json stats <store>` on a header with a bad line prints `{"error": "... FORMAT line 3: unknown setting: "x""}`. A JSON reader cannot parse it. The pattern existed before this phase, but M9 is new.
**Fix:** Print `serde_json::json!({ "error": e.to_string() })`.

### IN-02: `stats` cannot show an incompat flag; the incompat branch is dead

**File:** `crates/slicefs-cli/src/stats.rs:153-170`, `stats.rs:330-337`; `crates/slicefs-cli/src/header.rs:365`
**Issue:** `decide` refuses an unknown incompat flag for `Want::Read` too, so `store_stats` returns an error before `header_fields`. Also, `KNOWN_FLAGS` is empty. Thus `flags.incompat` is always empty, and `known` is always false. This agrees with [Incompat], but the JSON field and the text branch do no work today.
**Fix:** No change is necessary. Add a comment that says that the list fills only when a known incompat flag exists (Phase 22 and later).

### IN-03: The strict parse refuses a store for whitespace

**File:** `crates/slicefs-cli/src/header.rs:279-351`
**Issue:** The parse splits on `'\n'` and `' '` only. Failure scenarios after a hand edit:
- A blank line at the end gives `Line::Other("")`, and the store is refused with "unknown setting".
- A trailing space on `hash blake3-256 ` makes the line `Other`.
- A trailing space on a flag line gives "bad feature flag line".
- A CRLF file with the first line `slicefs-store 7\r` gives M4.
- A number above `u32::MAX` on the first line gives M4 ("unknown store format") and not M3 ("newer SliceFS").
**Fix:** Ignore empty lines, and trim `'\r'` and trailing spaces before the split. Alternatively, write these rules in `store-format.md`, because the grammar is the part that an older SliceFS must always read. For a number that does not fit in a `u32`, give M3.

### IN-04: `content::write_hasher` has no production caller and skips the open decision

**File:** `crates/slicefs-cli/src/content.rs:43-46`
**Issue:** Only `tests/hash_change_tests.rs:178` calls this `pub` function. It parses the header but does not call `decide`. Thus a future caller gets a hasher for a store with an unknown incompat flag and no refusal.
**Fix:** Make it `#[cfg(test)]` or `pub(crate)`, or let it call `header::check(store, Want::Read)`.

### IN-05: `Started` has no `Drop`

**File:** `crates/slicefs-cli/src/mount.rs:338-358`
**Issue:** If a caller drops a `Started` and does not call `stop`, the flusher, the online GC and the commit timer continue. Also, the drop of the `MountLock` field removes `mount.lock` while these threads can still write. Today, each caller calls `stop`. A panic between `start` and `stop` in `run_mount` (for example, a failed thread spawn in `spawn_unmount_watcher`) takes this path.
**Fix:** Move the body of `stop` into `impl Drop for Started`, and make `stop` a call to `drop(self)`.

### IN-06: The Docker FMT-02 check compares the store tree only after the unmount

**File:** `scripts/docker-linux-test/verify-phases.sh:56-66`
**Issue:** While the store is mounted, the check looks only at `mount.lock` (`ro-no-lock`). A file that the daemon makes during the mount and removes at the unmount is not seen. The in-process tracer covers this case, but only for the in-process setup and not for a real FUSE session.
**Fix:** Run `snap $R/sf` one time more after `ro-cat` and before `umnt`, and compare it with `$R/sf.before`.

### IN-07: `create` does not sync the parent directory of a new store directory

**File:** `crates/slicefs-cli/src/header.rs:438`
**Issue:** `create_dir_all(store)` can make the store directory, but only the store directory is synced (`header.rs:465`). After a power loss, the new store directory entry can be missing from its parent. The old `write_marker` had the same gap.
**Fix:** When `create` made the directory, also sync `store.parent()`.

### IN-08: A read-only mount prints a false hole-punch line

**File:** `crates/slicefs-cli/src/mount.rs:432-436`
**Issue:** `open_with` sets `punches = !opts.read_only && io.can_punch()`, so a read-only mount always prints "this file system cannot punch holes; GC frees space by compaction only.", also on a file system that can punch holes. A read-only mount runs no GC.
**Fix:** Do not print the line when `access` is `ReadOnly`, or print "Chunk store: read-only."
