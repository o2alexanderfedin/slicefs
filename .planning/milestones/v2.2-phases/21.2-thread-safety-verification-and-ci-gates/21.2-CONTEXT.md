# Phase 21.2: Thread-safety verification and CI gates - Context

**Gathered:** 2026-11-24 (auto mode; orchestrator decisions, all reversible)
**Status:** Ready for planning

<domain>
## Phase Boundary

Tool evidence of thread safety on every build. The owner asked twice: "ensure to run on every build formal verification and static analysis tools to check safety, especially threading."

- One new CI workflow runs on every push to any branch and on every PR. It fails on any finding: clippy, Miri, ThreadSanitizer, a model-checking job, Kani, a `deadlock-detect` stress run and a coverage gate. Each job has a time limit.
- The two Phase 19 races that the multi-worker Linux default (Phase 21: 2 to 8 workers) made reachable are fixed, each with a test that failed before the fix.
- The `unsafe` blocks that Miri does not run get a written review.

Out of scope: new features, Phase 22 and later, any store format change, the macOS worker default, the other Phase 19 to 21 deferred items (see Deferred).

</domain>

<decisions>
## Implementation Decisions

### Workflow
- **D-01:** One new file `.github/workflows/safety.yml`. Triggers: `push` (all branches) and `pull_request`. `ci.yml` keeps its triggers (main and develop) and does not get these jobs.
- **D-02:** A `concurrency` group per workflow and ref with `cancel-in-progress: true`, so a PR branch with push and pull_request runs does not queue old runs. (Resolved here; not in the orchestrator list.)
- **D-03:** All jobs run in parallel (no `needs:`). Every job has `timeout-minutes`. Start values (the planner may tune them after the first runs, and records the measured times): clippy 15, miri 30, tsan 30, model 20, kani 30, deadlock stress 15, coverage 30. Keep waits short (owner rule).
- **D-04:** The nightly toolchain is pinned to one dated version, written in one place only (a workflow-level `env` such as `NIGHTLY: nightly-2026-02-11`, the date already in local use). Miri and TSan use it. No `rust-toolchain.toml` is added (the repo has none; adding one changes every local build). (Resolved here.)
- **D-05:** Each job calls a script under `scripts/safety/` (for example `clippy.sh`, `miri.sh`, `tsan.sh`, `model.sh`, `kani.sh`, `deadlock.sh`, `coverage.sh`), so a developer runs the same command locally. Linux-only jobs that need FUSE run through the existing Docker harness. (Resolved here.)
- **D-06:** The jobs fail the workflow. Making them required checks in branch protection is an owner step; the phase summary lists the job names for that. No agent changes GitHub settings.
- **D-07:** `ci.yml` Linux job gets `timeout-minutes` (closes that part of #174). Also add it to the macOS job of `ci.yml` if it lacks one.

### Clippy
- **D-08:** `cargo clippy --workspace --all-targets -- -D warnings` on stable. Fix all current findings first, in their own commits, with no behavior change.
- **D-09:** An allowed lint needs a written reason at the allow site (`#[allow(clippy::x, reason = "...")]` or a comment on the same item). No crate-wide blanket allow without a reason per lint.
- **D-10:** Clippy runs on Linux and on macOS (a two-row matrix), because macOS-only code (FUSE-T and FSKit paths, `cfg(target_os = "macos")`) is not compiled on Linux. (Resolved here.)
- **D-11:** `vendor/fuser` is outside the workspace (`exclude` in `Cargo.toml`), so the clippy gate does not cover it. Its `unsafe` is covered by the review doc (D-24). (Resolved here.)

### Miri
- **D-12:** Miri runs the unit tests (`--lib`) of `chunk-store` and `metadata` on the pinned nightly. Tests that do real file IO Miri cannot run, or FFI (mmap, madvise, munmap, fcntl, fallocate, getuid), get `#[cfg_attr(miri, ignore = "<reason>")]` with a reason.
- **D-13:** Research decides whether `-Zmiri-disable-isolation` is used (it lets plain file IO tests run, so fewer tests are ignored) and whether the run fits in its time limit. If the full set is too slow, Miri runs a fixed, named list of test modules, written in the script, that reach `unsafe` code or the lock shim (`sync.rs`). (Resolved here.)
- **D-14:** Every `unsafe` in `chunk-store/src` is in `pack_io.rs` (mmap, madvise, munmap, fcntl, fallocate, and `unsafe impl Send/Sync for RunMap`). Research lists which of these Miri can execute. The ones it cannot go to the review doc (D-24). (Resolved here.)

### ThreadSanitizer
- **D-15:** Linux job on the runner (not in Docker; the tests are in-process): `RUSTFLAGS=-Zsanitizer=thread`, `-Zbuild-std`, target `x86_64-unknown-linux-gnu`, pinned nightly with `rust-src`.
- **D-16:** It runs a fixed, named set of tests, written in the script: the multi-worker and concurrency tests (for example `pool_tests`, `multi_handle_posix`, `lock_free_io`, `dirty_budget_tests`, `flusher_tests`, `reply_after_locks`; the planner fixes the final list), plus a short run of `tests/stress_harness.rs` with a fixed seed and a time bound.
- **D-17:** A TSan suppressions file is allowed only with a written reason per entry, the same rule as clippy allows. (Resolved here.)

### Model checking
- **D-18:** loom or shuttle is decided by research with a spike. Rule: pick the one that needs the fewest code changes to model the worker pool, the shared dirty budget and the commit gate, with parking_lot in use. A cfg-gated sync shim is acceptable.
- **D-19:** Prior research and this phase disagree, and the spike decides. `.planning/research/STACK.md` chose shuttle and said "No loom" (loom's state space was judged too large). The REQUIREMENTS Out of Scope table lists `loom` as a dependency not to add. Success criterion 2 says "every thread order", and shuttle is random/PCT, not exhaustive. So research must state whether the chosen tool has a bounded exhaustive mode (loom; or shuttle's DFS scheduler) and which mode CI runs. A dev-only test dependency is allowed in this phase; the Out of Scope row is about runtime dependencies. (Resolved here.)
- **D-20:** The models check the real code through the shim, not a separate copy of the protocol (a copy drifts). The cfg point is `crates/chunk-store/src/sync.rs`, which already wraps the parking_lot `Mutex`, `RwLock` and `Condvar`. The commit gate (`std::sync::RwLock` in `filesystem.rs`, `GateHold`/`GateGuard`) and `Mutex<StoreIo>` are std types outside the shim; the plan must route them through the shim under the model cfg, or say why a model of them is sound without it. (Resolved here.)
- **D-21:** The models cover the worker pool (`pool.rs`: submit, queue, drain, shutdown), the shared dirty budget (`pay_budget`, flusher, throttle waits) and the commit gate (shared request holds against the exclusive commit). One model per race fix is also kept (D-27).

### Kani
- **D-22:** Kani proves free of panic and overflow: the store header parser (`crates/slicefs-cli/src/header.rs`) and the size and limit arithmetic (for example `MAX_FILE_SIZE` checks on offset plus length in write and setattr, the dirty budget sums, `workers_for_cpus`). The planner lists the final functions.
- **D-23:** `header::parse` takes `&Path` and `&str` and returns `io::Result`. Proofs use a bounded input; the bound is written in each harness. A small pure core may be split out of the parser for the proof (no behavior change); that is inside the scope fence. Research checks that the Kani toolchain builds this code (the header code needs Rust 1.89 or later for std file locks; if Kani's bundled toolchain is older, the proofs target a module that does not use the file locks, or the Kani version is chosen to fit). The Kani version is pinned in the workflow. (Resolved here.)

### Unsafe review
- **D-24:** `docs/design/unsafe-review.md` has one entry per `unsafe` block or `unsafe impl` that Miri does not execute, in every crate: `chunk-store` (`pack_io.rs`), `metadata` (getuid/getgid), `slicefs-cli` and `vendor/fuser`. Each entry: file and item, what it does, the safety argument (which invariant holds and why), and how it is tested. (Scope widened here from the roadmap's "slicefs-cli and vendor/fuser" to every crate.)
- **D-25:** Counts at the start of the phase (`unsafe` tokens): chunk-store 18 (9 in `src`), metadata 2 (both in one line of `src/store.rs`), slicefs-cli 56 (19 in `src`), vendor/fuser 36 (30 in `src`). Entries count blocks and `unsafe impl` items in non-test code; `unsafe` in test code is listed in one summary line per file. The planner re-counts.

### The two Phase 19 races
- **D-26:** Fix both in this phase. Each fix starts with a test that fails before the fix. A deterministic form is preferred: a test-only pause hook (cfg(test) or a test feature) that holds one thread inside the window. Then the fix. Then a model or stress test that stays in CI.
- **D-27:** Race (a), one root and two windows (Phase 19 deferred items, 19-09 and 19-10): `setattr_size_closed` (`filesystem.rs`) changes the size of a closed file under the transient cell only, with no stripe. Window 1: an unlink reclaims the inode meanwhile, so a manifest entry and one refcount of the deleted inode remain, and the setattr returns EIO. Window 2: a setattr of other fields of the same inode shares no lock with it, so the two inode writes and their records can be in opposite orders and replay gives another mtime. The stated fix direction: re-check the inode under its stripe before the install; the install step must move out of the cell hold (a stripe is rank 3, below the cell at rank 4). Research confirms. Both windows get a test.
- **D-28:** Race (b): cross-directory rename has no ancestor check (19-CONTEXT Deferred, 19-RESEARCH: `simulate_rename` has no "source is an ancestor of target" check; the rename mutex, rank 2, is where it belongs). Fix: under the rename mutex, walk the parents of the target directory; if the source directory is on that path, return EINVAL. Research checks what the Linux kernel and FUSE-T already serialize or check for FUSE, so the failing test reaches the daemon path (an in-process test, not only a mount test). The fix goes in the daemon in any case.
- **D-29:** Fallback: if one race cannot be fixed in this phase, the Linux default becomes `--workers 1` (`default_workers` in `pool.rs`), and the issue stays open. Record which race and why.

### Deadlock-detect stress
- **D-30:** Linux job, short. It runs `tests/stress_harness.rs` with `--features deadlock-detect` and several workers, with a wall-clock limit. Only that harness calls `parking_lot::deadlock::check_deadlock`, so a daemon built with the feature detects nothing by itself; the job relies on the in-process harness. The parking_lot detector cannot see the std locks (commit gate, `Mutex<StoreIo>`); the job also fails on a stall past its limit, and the models (D-20) cover the gate. Research decides whether a short mount-level stress run in Docker is also practical. (Resolved here.)

### Coverage
- **D-31:** `cargo-llvm-cov` on Linux, line coverage, the numbers printed in the job log (workspace and per crate). The FUSE checks are included if practical (instrumented build run inside the existing Docker harness); if not practical, the job records why and covers the in-process tests.
- **D-32:** Gate: workspace line coverage must not fall below a floor. The floor is the first Linux CI number minus 1 point, written in one place in the repo (the coverage script or a small file next to it). The macOS baseline of 90.05 % (slicefs-cli 85.4 %, `fuse_callbacks.rs` 9.7 %) is context only; the floor comes from the Linux run. (Resolved here.)

### Scope fence
- **D-33:** No new features. Phase 22 and later untouched. No store format change. Behavior changes are only the two race fixes (and D-29 if needed).

### Claude's Discretion

- Whether Miri uses `-Zmiri-disable-isolation` (D-13).
- How the test-only pause hooks are built (D-26).

<code_context>
## Existing Code Insights

### Reusable Assets
- `crates/chunk-store/src/sync.rs`: the lock shim (`Mutex`, `RwLock`, `Condvar` over parking_lot, with a `Rank` and a debug-build rank checker). The natural cfg point for a loom or shuttle build.
- `crates/slicefs-cli/tests/stress_harness.rs`: the in-process stress harness (SPIKE-02); under `deadlock-detect` it starts a `check_deadlock` thread.
- Feature `deadlock-detect` in `slicefs-cli`, `metadata` and `chunk-store` (`parking_lot/deadlock_detection`).
- `crates/slicefs-cli/tests/pool_tests.rs`, `multi_handle_posix.rs`, `lock_free_io.rs`, `dirty_budget_tests.rs`, `flusher_tests.rs`, `reply_after_locks.rs`: candidates for the TSan set.

### Established Patterns
- Lock order: gate (1), rename (2), stripes (3, ascending), file cell (4), short maps (5), store (6). Debug builds panic on a violation. Race fixes must keep this order.
- The commit gate is a `std::sync::RwLock<()>` (`filesystem.rs`, `commit_gate`, `GateHold`, `GateGuard`), kept std on purpose (Phase 19 D-16, D-18). The rank checker sees it through `rank::enter`.
- `default_workers()` in `pool.rs`: 1 on macOS, else half the CPUs, clamped to 1..8.

### Integration Points
- `filesystem.rs`: `setattr_size_closed` (race a), `rename_logged` / `rename_held` and the rename mutex in `locks.rs` (race b), `pay_budget` (budget model).
- `crates/slicefs-cli/src/header.rs`: `parse`, `decide`, `MAX_HEADER` (Kani).
- `filesystem.rs`: `MAX_FILE_SIZE`, `DIRTY_LIMIT` (Kani).
- `crates/chunk-store/src/pack_io.rs`: all chunk-store `unsafe` (Miri or review doc).
- No `rust-toolchain` file and no `rust-version` in the repo.

</code_context>
