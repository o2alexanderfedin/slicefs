## RunMap test (Task 2, D-14)

- `#[cfg(test)] RunMap::anon_for_test(&[u8])`: `mmap(PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANON)`, `MAP_FAILED` checked, `copy_nonoverlapping`, no `madvise`, a panic on 0 bytes. Each unsafe block has a SAFETY comment.
- Test `pack_io::tests::a_run_map_reads_back_moves_across_threads_and_unmaps`: `bytes()` reads back, a `thread::scope` thread reads by reference (Sync), a `thread::spawn` thread gets the map, reads it and drops it (Send, munmap). It passes in `cargo test` and under Miri on macOS and Linux.
- Red step: before the constructor, the test failed to build (E0599, no `anon_for_test`).
- Guard mutation (not committed): `unsafe { *map.bytes().as_ptr().add(map.len()) }` in the test. Miri stopped with `error: Undefined Behavior: attempting a read access using <281504> at alloc116873[0x5], but that tag does not exist in the borrow stack for this location` at the read. Reverted.
- What Miri checks here: the pointer, the thread move and the unmap, not the length. The error above is a borrow-stack error at offset 0x5 inside the allocation, so the Miri mapping is longer than 5 bytes (a page). A check run on a scratch copy (not committed) with `len: len + 1` in the constructor gave only the test assertion failure (`left == right`), with no UB report, also for the `munmap` of that length during unwinding. So a `len` that is too long by less than a page, in `bytes` or in `munmap`, is not a Miri error. Plan 21.2-09 must argue the length (`len` comes from `file.metadata()` in `RunMap::new`).

## Deviations from Plan

1. **[Rule 3 - Blocking] Rerun of the timeout tests with 4 jobs, not 1.** 41 tests at 300 s one at a time is about 3.4 h. The reruns ran in two extra containers with `MIRI_PROBE_JOBS=4` and their own target dirs (`/target/slow`, `/target/slowmd`), so the build of the first probe was not changed. The VM has 32 cores, and the load in it stayed between 3 and 9.
2. **macOS probe on scratch copies.** The macOS probe ran on two copies of the tree outside the repository, because batch B edits started during the probe. The first copy was slow (2 jobs); its remaining tests were made to fail fast by a dependency line in that copy's Cargo.toml (no process was killed), and the 48 Linux-pass tests it had not reached ran in the second copy (all pass). Its metadata probe ran in the second copy.
3. **Batches A and E had no workspace gate** (orchestrator rule: a commit of only CI, scripts or docs needs no full gate; the script it adds was run instead). The plan rule 2 asked for one.
4. **Workspace gates stopped at the 3600 s cap** (B and C), with every finished binary green; the cut binaries then ran alone (orchestrator rule), all green.
5. **D-13 module list.** The full run was over 1200 s, so the plan fallback was applied: `MIRI_MODULES` in miri.sh (default per crate, `all` for every test). The header of miri.sh says that only the listed modules are checked in CI.
6. **Linux and macOS logs come from trees equal to the commits.** The final Linux run used the tar of the working tree after the batch C gate, before its commit; `diff -r` of crates/ and scripts/safety/ of that tar against the tree after commit 91a00aa is empty. The macOS module-list run used a scratch copy; its `diff -r` against the repository is empty.
7. **miri.sh extras:** `rustup component add --toolchain "$NIGHTLY" miri rust-src` (need_toolchain skips an installed toolchain, as in clippy.sh), the per-module guard, and stderr shown after each crate run (so a Miri report never splits a `test <name> ... ok` line).
8. **The probe log is at a3b6bbe** (127 chunk-store tests); the RunMap test came after it, in batch B.
