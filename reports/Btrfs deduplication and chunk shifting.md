# One inserted byte breaks Btrfs deduplication

Btrfs can deduplicate data, but **only out-of-band**: a userspace tool (bees, duperemove, dduper, rmlint, jdupes) finds duplicate ranges and asks the kernel to share them through the `FIDEDUPERANGE` ioctl. The kernel locks both ranges, compares them byte by byte, and remaps the destination onto the source extents if they match ([btrfs docs](https://btrfs.readthedocs.io/en/latest/Deduplication.html)). No in-band (on-write) dedup exists in mainline. A Fujitsu patch series went through about 15 versions from 2015 to 2018, was never merged, and its leftover hooks were removed in v5.4. Every sharing operation must start at a 4 KiB-aligned offset in both files, and the on-disk extent format cannot express references at a finer granularity. As a result, Btrfs dedup **survives a changed byte** (at the kernel level only the 4 KiB block that holds it is lost; extent-based tools such as duperemove lose more) but **does not survive an inserted or removed byte**: every byte after the edit moves to a new position modulo 4096, and nothing after that point can be shared again. Content-defined chunking does not fix this on Btrfs, because the limit is about *where* a chunk sits, not how long it is. ZFS and dm-vdo have the same weakness. Windows Server Data Deduplication and every major backup tool solve it with CDC above the block layer, which is the same design choice SliceFS has made: its live FUSE write path already uses CDC.

## Btrfs shares extents only on request, after a kernel byte compare

The official documentation is blunt: "BTRFS implements **only out-of-band** type", and duplicates "have to be actively looked for and deduplicated by the user application" ([btrfs docs: Deduplication](https://btrfs.readthedocs.io/en/latest/Deduplication.html)). The in-band attempt was real but did not finish. Version 14.5 of "Btrfs In-band De-duplication" (Lu Fengqi, Qu Wenruo) was posted in December 2017. By v11 it had been cut back to an in-memory hash backend only ([LWN](https://lwn.net/Articles/741224)), and LWN's coverage of an earlier version notes that it trusted hash matches and did not byte-compare ([LWN 679031](https://lwn.net/Articles/679031/)). A v15 rebase came in November 2018 ([lore](https://lore.kernel.org/linux-btrfs/20181106064122.6154-1-lufq.fnst@cn.fujitsu.com/)). Maintainer David Sterba then put it on hold because no persistent on-disk hash tree had even been prototyped ([lore](https://lore.kernel.org/linux-btrfs/20181113134545.GY24115@twin.jikos.cz/); this comes from a search summary, because the message itself returned 403). In July 2019 the commit "btrfs: Remove leftover of in-band dedupe" removed the remaining hooks because "it's unlikely in-band dedupe is going to land" ([commit mirror](https://lab.nexedi.com/kirr/linux/-/commit/330a582790452a159686c5dab8f4286babd9c00e)). The changelog through kernel 7.3 (October 2026) has no in-band entry ([Kernel-by-version](https://btrfs.readthedocs.io/en/latest/Kernel-by-version.html)).

The kernel interface is small and conservative. `FIDEDUPERANGE`, made generic from the Btrfs-private `BTRFS_IOC_FILE_EXTENT_SAME` in Linux 4.5, takes one source range and many destinations. It is **atomic against concurrent writes**, and "if even a single byte in the range does not match, the deduplication request will be ignored" ([ioctl_fideduperange(2)](https://man7.org/linux/man-pages/man2/ioctl_fideduperange.2.html)). The VFS caps one request at **1 GiB**. Btrfs then works through it in **16 MiB** pieces (`BTRFS_MAX_DEDUPE_LEN`), and it rejects dedupe between files with different checksum/NOCOW status ([fs/remap_range.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/remap_range.c); [fs/btrfs/reflink.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/reflink.c)). The man page still says the per-call limit is "typically 16 MiB" and is enforced silently, so callers must always check `bytes_deduped`. `FICLONERANGE` (reflink) uses the same remap path without the compare. Kernel 7.2 (August 2026) added an ioctl that returns raw data checksums to userspace as a dedup hint, so tools can skip reading blocks. The final comparison is still byte-exact, and compressed or inline extents do not expose checksums through it ([btrfs docs](https://btrfs.readthedocs.io/en/latest/Deduplication.html)).

The tools differ in strategy, not in the unit they work with. **bees** is a whole-filesystem daemon. It hashes every 4 KiB block into a fixed-size, mlocked table of 16 bytes per entry (about 128 MB per TB of unique data for a ~128 KiB average dedup extent). It crawls only new extents by transaction ID and grows a match outward from a single hit ([bees config](https://github.com/Zygo/bees/blob/master/docs/config.md); [how it works](https://github.com/Zygo/bees/blob/master/docs/how-it-works.md)). **duperemove** is file-list based and incremental through an sqlite hashfile. It matches whole extents by default and uses 128K blocks for optional partial matching ([duperemove(8)](http://markfasheh.github.io/duperemove/duperemove.html)). **dduper** reads the existing Btrfs checksum tree instead of the data, and needs patched btrfs-progs ([dduper](https://github.com/Lakshmipathi/dduper)). rmlint and jdupes dedupe only whole identical files. The current docs name only bees and duperemove as maintained and widely used.

Two Btrfs-specific costs shape all of them. First, "btrfs cannot partially overwrite extents—the _entire_ extent must be replaced". If only part of an extent is deduped, the leftover "bookend" references keep the whole old extent allocated, so bees copies the unmatched remainder into a new extent to free the original ([bees how-it-works](https://github.com/Zygo/bees/blob/master/docs/how-it-works.md)). Second, deduping an extent that snapshots share forces a 16 KB metadata-page CoW in every snapshot, which can mean "100x growth in metadata size" with 100 snapshots ([bees gotchas](https://github.com/Zygo/bees/blob/master/docs/gotchas.md)). Compressed extents are capped at 128 KiB, which also caps the dedup unit for compressed data ([fs/btrfs/compression.h](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/compression.h)).

## A changed byte costs at least 4 KiB; an inserted byte costs the rest of the file

The deciding constraint lives in two places, and neither can be worked around by a tool. The VFS check `generic_remap_checks()` requires that "the start of both ranges must be aligned to an fs block" and returns `-EINVAL` otherwise. Lengths are rounded down to whole blocks. The only exception is a partial last block that ends at EOF in *both* files ([fs/remap_range.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/remap_range.c)). Below that, the Btrfs tree-checker rejects any file extent item whose file offset, `disk_bytenr`, `offset` or `num_bytes` is not a multiple of `sectorsize`, for compressed extents as well ([fs/btrfs/tree-checker.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/tree-checker.c)). The minimum sectorsize is 4 KiB (`BTRFS_MIN_BLOCKSIZE`) ([fs/btrfs/fs.h](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/fs.h)). A file extent *can* point into the middle of a shared extent, but only at a sector boundary. Byte-granular references cannot be expressed on disk.

The three edit cases therefore behave very differently:

| Edit near file start | Kernel-level outcome | What tools actually recover |
|---|---|---|
| **Change** 1 byte (same length) | Only the 4 KiB block holding the byte differs; all others still match at identical aligned offsets | duperemove's default whole-extent matching loses the whole changed extent; `partial` mode likely loses one 128K `-b` block; bees rewrites around the change |
| **Insert** 1 byte | Every following byte shifts by 1 mod 4096; no aligned block of the new file equals an aligned block of the old one | Nothing after the edit, including the tail block (the files no longer end at congruent offsets) |
| **Remove** 1 byte | Same as insert, shifted the other way | Nothing after the edit |
| Insert/remove exactly k·4096 bytes | Alignment preserved | Everything except the edited region |

The derivation is simple. If B = one byte + A, block k of B holds A[4096k−1, 4096k+4095), and that can equal an aligned block of A only by coincidence, such as all-zero or periodic data (which bees turns into holes anyway). This is the classic boundary-shift problem: "if one or several bytes are inserted at the beginning of a file, all current chunk cut-points ... will be shifted and no duplicate chunks will be detected" ([FastCDC, USENIX ATC'16](https://www.usenix.org/system/files/conference/atc16/atc16-paper-xia.pdf)). This result comes from the kernel's rules, not from a benchmark. No bees or duperemove document discusses the shift case explicitly, and no measured shifted-dataset run on Btrfs was found. Smaller hash blocks in a tool cannot help, because 4 KiB is already the floor for bees (`BLOCK_SIZE_CLONE = 4096`), for duperemove (`MIN_BLOCKSIZE`) and for the filesystem itself ([bees src/bees.h](https://raw.githubusercontent.com/Zygo/bees/master/src/bees.h)).

## Variable-size chunks fit Btrfs only in 4 KiB steps, and shifting still breaks them

Btrfs is not limited to fixed-size sharing. It can dedupe a 12 KiB range or a 52 KiB range, extents can be any sector multiple up to 128 MiB, and one shared range can span many extents ([fs/btrfs/fs.h](https://raw.githubusercontent.com/torvalds/linux/master/fs/btrfs/fs.h)). So the answer to "can it work with non-equal chunks?" is yes in length and **no in position**. A content-defined chunk of 13,377 bytes that starts at byte 7 cannot be referenced. Rounding CDC boundaries to 4 KiB does not solve this. CDC solves the *boundary* problem by choosing cut points from content, but Btrfs adds a *placement* problem: a chunk can be shared only if it sits at the same residue modulo 4096 in both files. In a POSIX file, a byte's position is fixed by everything before it, so a dedup agent working at the filesystem level cannot choose placement. Even a perfect CDC index would find that after a 1-byte shift almost none of its chunks land at congruent offsets. Trimming CDC chunks inward to their aligned interiors also wastes about 4 KiB per chunk even without a shift, which makes small-average CDC a poor fit from the start. No tool or paper was found that layers CDC on Btrfs reflink dedup.

Two workarounds exist. The first is producer-side alignment: the 2024 GNU tar `--reflink` patch "aligns file data on a 4k block boundary" by padding headers with an ignored pax comment record ([bug-tar](https://lists.endsoftwarepatents.org/archive/html/bug-tar/2024-10/msg00028.html)). Unchanged members then stay shareable, but byte inserts inside one member still break sharing for the rest of that member. Whether the patch was merged into a release was not confirmed. The second is an indirection layer *above* the block filesystem whose map is byte-granular, of the form (file_offset, chunk_id, chunk_offset, length). Btrfs's own `offset`/`num_bytes` fields are exactly this kind of indirection, but clamped to sectors, so a byte-granular version would be an on-disk format change. The limit is not unique to Btrfs. XFS goes through the same `generic_remap_file_range_prep` checks, and mainline ext4 has no `remap_file_range` hook at all ([fs/xfs/xfs_reflink.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/xfs/xfs_reflink.c); [fs/ext4/file.c](https://raw.githubusercontent.com/torvalds/linux/master/fs/ext4/file.c)).

## Block-level systems share the flaw; the CDC systems all sit above the block layer

The comparison splits cleanly. Systems that dedupe fixed, aligned blocks fail on shifted data, whether they dedupe inline or after the fact. Systems that use CDC survive shifts, and none of them is a block filesystem.

| System | When | Chunking | Unit | Survives 1-byte insert? |
|---|---|---|---|---|
| Btrfs (bees, duperemove) | Out-of-band | Fixed, aligned | 4 KiB sector / extent | No |
| ZFS (classic and 2.3 fast dedup) | Inline | Fixed record | recordsize (default 128 KiB) | No |
| dm-vdo (Linux 6.9+) | Inline | Fixed | 4 KiB | No |
| Windows Server Data Dedup | Post-process | Rabin CDC | 32–128 KB, ~80 KB avg | Yes |
| restic / borg / Kopia / Duplicacy | Backup time | Rabin/buzhash CDC | ~1–4 MiB avg | Yes |
| casync | Image build | buzhash CDC | 64 KiB avg | Yes |

**ZFS** keeps one global, pool-wide dedup table keyed on whole records. Each cached entry costs "slightly more than 320 bytes" of RAM, partial records count as full records, and a table that spills out of RAM turns every write into a random read: about 400 KB/s on one 7200 RPM disk with 4 KB blocks ([OpenZFS tuning](https://openzfs.github.io/openzfs-docs/Performance%20and%20Tuning/Workload%20Tuning.html)). OpenZFS 2.3 "fast dedup" (January 2025) adds a sorted, batched log, a table quota and `zpool ddtprune` ([release](https://github.com/openzfs/zfs/releases/tag/zfs-2.3.0); [zpool-ddtprune(8)](https://openzfs.github.io/openzfs-docs/man/master/8/zpool-ddtprune.8.html)). These changes reduce the cost of the table, not its matching rule. Over quota, a write "is converted to a regular non-dedup write" ([TrueNAS](https://truenas.com/docs/references/zfsdeduplication)). **dm-vdo** dedupes inline at a maximum 4 KiB block with a 16-byte non-cryptographic hash. Its default UDS index holds 64 million records, which is a dedup window of about 256 GB ([kernel docs](https://docs.kernel.org/admin-guide/device-mapper/vdo-design.html)). Both fail on byte shifts for the same reason Btrfs does.

**Windows Server Data Deduplication** is the closest shipped analogue to SliceFS. It writes files normally, then a scheduled job will "break files into variable-size chunks", put unique chunks in a chunk store, and replace the file with a reparse point that the Dedup.sys filter resolves on read ([MS Learn](https://learn.microsoft.com/en-us/windows-server/storage/data-deduplication/understand)). Its design paper makes two points that matter here. 64 KB fixed blocks gave clearly lower savings than ~64 KB CDC "because chunking with fixed size blocks does not support the identification of duplicate data when its duplicate occurrence is not aligned along block boundaries". And ~80 KB average chunks with compression saved about as much as 4 KB chunks with compression, with an index of about 6 bytes of RAM per chunk ([El-Shimi et al., ATC'12](https://www.usenix.org/system/files/conference/atc12/atc12-final293.pdf)). Microsoft chose post-processing because inline dedup "introduces additional write latencies and reduces write throughput".

Measured numbers show how large the gap can be. In FastCDC's Table 4, 10 KB fixed-size chunking matched CDC on aligned data (Linux sources 96.5% vs ~97%, VM backups 95.7% vs ~96%). It collapsed on streams where content shifts: tar archives 12.2% vs 47–50%, Redis backups **9.8% vs 95–97%**. FastCDC with normalized chunking also gave the best ratio while running about 10x faster than Rabin ([FastCDC PDF](https://www.usenix.org/system/files/conference/atc16/atc16-paper-xia.pdf)). The row-to-dataset mapping was rebuilt from extracted PDF text and cross-checked against Table 5, not against the rendered table. Backup tools tune CDC for repository-scale indexes: restic uses 512 KiB–8 MiB Rabin chunks ([restic](https://restic.readthedocs.io/en/latest/100_references.html)), and borg's buzhash targets ~2 MiB, at a memory cost of about 164 bytes per chunk ([borg internals](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)). Duplicacy recommends fixed chunks for files updated in place, such as VM disks and databases ([Duplicacy wiki](https://github.com/gilbertchen/duplicacy/wiki/Chunk-Size)), which is a reminder that CDC's advantage is specific to the workload.

## SliceFS already sits on the right side of the divide

SliceFS dedups in-band: on write, file bytes go into the `blockset` engine, which chunks them, builds a SHA-224 Merkle tree, and stores each chunk under its hash, so an identical chunk is stored once ([README.md](../README.md)). The README used to say the composed `Chunker` was "default: fixed-size"; that line was stale and has been corrected. The live FUSE write path ([filesystem.rs](../crates/slicefs-cli/src/filesystem.rs) lines ~780, 1197, 1568, 1600) and the seed command ([seed.rs:116](../crates/slicefs-cli/src/seed.rs)) chunk content with `blockset::State::push_all` from the data-id crate, which is content-defined. Per the Phase 4 research, "data-id's CDC has no configurable chunk size — boundaries emerge from content via digest comparison", with dedup verified across 10 identical files. The same document reports "54 entries for 1MB file, logarithmic growth", but those are Merkle-tree entries, not chunks, so SliceFS's average chunk size has not been measured ([04-RESEARCH.md](../.planning/phases/04-full-posix-write-path/04-RESEARCH.md)). `FixedChunker` in `crates/cas-local` is a Phase 1 trait implementation that the live path does not use.

Architecturally, SliceFS is the "indirection layer above the block filesystem" that the Btrfs analysis points to. Its metadata tree maps logical bytes to content IDs, so chunk placement is not tied to any host filesystem's 4 KiB residue, and a CDC boundary can fall at any byte. By design, a 1-byte insert near the start of a file should cost only the chunk or two around the edit, which is the behavior Btrfs, ZFS and dm-vdo cannot offer. **This has not been benchmarked.** Identical-file dedup is the only verified case, and no shift test against SliceFS's CDC is recorded. The average chunk size is also unmeasured, so it is not yet known how SliceFS compares with Windows' ~80 KB or casync's 64 KiB on index size per byte stored. Whatever that cost is, SliceFS pays it on the write path, the cost Microsoft avoided by deduping after the fact. Running SliceFS on top of Btrfs or XFS is also safe from this perspective: those filesystems would only store aligned chunk objects, so their alignment rules never touch the logical byte stream.

## Conclusion

The question "can Btrfs dedup survive a shifted byte?" turns out to be a question about the on-disk format, not about tools. Better hashing, CDC, or the new 7.2 checksum ioctl can make Btrfs dedup cheaper, but none of them can make it shift-tolerant while every reference must be sector-aligned. The industry answer has been consistent across Windows, casync and every major backup tool: put a byte-granular map from logical bytes to content-defined chunks *above* the block layer, and let the block layer store opaque objects. SliceFS already has this design, which makes its open questions empirical rather than architectural.

The next useful steps follow from that. Add a regression test that inserts, changes and removes one byte near the start of a large file and asserts that only O(1) new chunks are stored, because that is the property that separates SliceFS from ZFS and Btrfs and it is currently unverified. Measure the real average chunk size, index size and write latency, and compare them with the ATC'12 finding that ~80 KB chunks plus compression save about as much at a fraction of the index cost, keeping in mind that v2.0 removed write-path compression, which changes that trade-off.
